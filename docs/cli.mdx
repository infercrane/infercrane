# CLI reference

The public CLI uses Cobra for grouped help, typo suggestions, aliases, and shell completion. It talks to the authenticated control-plane API and never opens PostgreSQL directly. Run `infercrane help` for the current command tree and `infercrane version` for the build version. `infercrane version --output json` returns `version` plus a `build` object with the Go version, platform, and, when the binary embeds them, the source `commit`, `commit_time`, and `modified` flag. Build fields that were not embedded are omitted, never guessed.

## Global conventions

- Commands that return data accept `--output human|json`. It can follow the command's arguments or come before the command: `infercrane --output json status qwen-prod`.
- With `--output json`, a successful command writes JSON to stdout and every failure, including a usage error, writes one JSON error object to stderr. The CLI never prints Go's flag usage text.
- A resource argument such as `DEPLOYMENT` or `ID` comes right after the command or action, before flags. If it is missing, or a flag stands in its place, the command fails with a usage error before contacting the control plane. An extra positional argument is also a usage error, so a later `--output` is never silently ignored.
- `status --watch --output json` emits one JSON document per state refresh.
- `logs --output json` emits JSON Lines: one event object per line, including while `--follow` streams new events. Parse it line by line, not as one document.
- Mutation commands accept `--idempotency-key`; generated keys are printed in human and JSON output and attached to uncertain-request errors. Reuse the same key after an uncertain result.
- `--wait` polls persisted operation state and prints only changed progress. In a terminal it redraws one progress line with a spinner and prints a line as each phase finishes; otherwise it prints one line per change on stderr. Closing the client does not cancel server-side work; the operation ID and exact `infercrane operation watch ID` resume command are printed before waiting begins.
- `--wait-timeout 20m` bounds the local watcher without cancelling the durable operation. Resume with `infercrane operation watch ID`; cancel only with `infercrane operation cancel ID`.
- JSON failures contain `code`, `category`, `message`, `retryable`, `remediation`, and provider HTTP status when available.
- Command help is available before authentication: `infercrane COMMAND --help` never contacts the control plane.
- `infercrane --context NAME COMMAND` selects a context for one invocation.
- `--no-color`, before or after the command, and the standard `NO_COLOR` environment variable disable ANSI styling. Redirected output and JSON are never decorated. See [Terminal output](#terminal-output).
- When a dashboard is configured, human output from `deploy`, `apply`, `endpoint create`, `rollout`, `optimize create|approve|report`, and `auth status` ends with `View in dashboard → URL`. See [Sign in the CLI](/features/cli-login#dashboard-links).

## Words

Help and human-readable output use the dashboard's words. Command names, flag names, and
`--output json` keep the control API's names, so scripts keep working:

| You read | In commands, flags, the API, and JSON |
|---|---|
| run, optimization run | optimization campaign: `/api/v1/optimization/campaigns`, `campaign`, `campaign_id` |
| setup | candidate: `candidates`, `candidate_id`, `--candidate`, `--max-candidates` |
| current setup, baseline | the campaign control: `"control": true` |
| roll out a setup | `optimize activate`, `rollout promote`; state `promoted` |
| roll back | `rollout rollback` |

A deployment's staged revision is still the candidate revision (`--revision candidate`,
`candidate_revision_id`), and an endpoint's staged serving plan is its candidate plan.

Control API error messages use the same words, so the CLI and the dashboard read alike:
`optimization run was not found`, `setup was not found in this run`. Error codes are identifiers
that clients match on and keep the API's names, for example `campaign_state_conflict` and
`candidate_not_decided`.

Where the CLI turns a state into words, a run or setup the API calls `promoted` reads
`rolled out` (`live` in `optimize report`), and the current setup reads `baseline` where the API
says `rejected` because another setup was chosen. That applies to the styled `optimize list` and
`inspect`, to `optimize watch`, `results`, and `report`, and to shell completion. Plain `list` and
`inspect` output and JSON print the API's own state.

## Terminal output

In a terminal, human output is styled like the dashboard: state badges such as `● SERVING`,
before → after changes in green when better and red when worse, aligned tables with relative
times, and cards for `optimize report`. Every color repeats a word that is printed next to it, and
unknown values stay `unknown`. Layouts fit an 80-column terminal and use the extra width of a
wider one.

Output stays plain, with no ANSI escape codes and no prompts, when:

- stdout is redirected or piped, as it is for scripts, CI, and coding agents;
- `NO_COLOR` or `--no-color` is set;
- `TERM=dumb`;
- `--output json` is used.

JSON output is exactly what earlier versions printed, so anything that parses it keeps working.
Plain output keeps its layout and prints states and codes as the control API names them; its
labels use the [words](#words) above, for example `Optimization run ID · STATE` and `SETUPS`.

Colors follow the terminal's background when it sets `COLORFGBG`. Otherwise the CLI uses mid-tone
colors that read on dark and light backgrounds. It never queries the terminal, so a command never
waits on one.

For example, `infercrane optimize list` in an 80-column terminal:

```text
RUN                               STATE                CREATED
──────────────────────────────────────────────────────────────
83ccd598540e2dd1f9c897040c1ea503  ● RANKED              2h ago
  Qwen/Qwen3-0.6B · interactive
4f1c2d9e0b7a4e63a1d2c3b4a5f60718  ● AWAITING APPROVAL   4m ago
  meta-llama/Llama-3.1-8B-Instruct · cost-efficiency
```

and `infercrane deploy MODEL --wait` while it runs:

```text
  ✓ CHECKING CAPACITY     1s
  ✓ WAITING FOR CAPACITY  2s
  ✓ PREPARING ARTIFACT    1s
⠙ ━━━━━━━━────  70%  STARTING RUNTIME  starting vllm  1m53s · check 5/120
```

Two commands ask before they act, and only in a terminal:

- `delete DEPLOYMENT` without `--yes` shows the deletion plan and asks you to type the deployment
  name. Without a terminal, or with `--output json`, it still requires `--yes`.
- `optimize approve` shows the spend cap, when the approval expires, and every setup the run
  starts, then asks `Approve spending up to $25.00? [y/N]`. `--yes` approves without asking.
  Without a terminal it approves as before, without a prompt.

## Configure and diagnose

### `login`

Sign the CLI in through the dashboard. The terminal and the browser show the same one-time code;
approving it issues a key with your role and scopes, stored in the OS keychain when available and
otherwise in the `0600` config file. The key is never printed.

```bash
infercrane login
infercrane login --no-browser
infercrane login --url http://127.0.0.1:8080 --console-url http://127.0.0.1:3200
```

| Flag | Default | Meaning |
|---|---|---|
| `--url` | context URL | Control-plane base URL |
| `--console-url` | `INFERCRANE_CONSOLE_URL`, the control plane's advertised dashboard, or the hosted dashboard | Dashboard that approves the sign-in |
| `--context` | current context | Context to store the key in |
| `--no-browser` | off | Print the URL and code instead of opening a browser |
| `--output` | `human` | `human` or `json`; JSON never contains the key |

`auth login` is the same command. Details, storage, and revocation are in
[Sign in the CLI](/features/cli-login).

### `logout`

Revoke this CLI's key on the control plane and remove it from the keychain and config file. The
context keeps its URLs. A key pasted with `init` is removed locally but stays active on the control
plane; revoke it with `principal revoke`. `auth logout` is the same command.

```bash
infercrane logout
infercrane --context staging logout --output json
```

### `open`

Open a dashboard page for a resource, or print its URL with `--no-browser`.

```bash
infercrane open
infercrane open endpoint support-bot
infercrane open deployment qwen-prod
infercrane open run RUN_ID
infercrane open model Qwen/Qwen3-8B
infercrane open operation OPERATION_ID --no-browser
```

### `init`

Validate and store a control-plane URL and an already-issued credential in a named private client
context. Prefer `login` on a workstation; use `init` or `INFERCRANE_API_KEY` for service accounts
and CI.

```bash
INFERCRANE_API_KEY='ISSUED_CREDENTIAL' \
  infercrane init --context production --url https://infercrane.example
```

| Flag | Default | Meaning |
|---|---|---|
| `--url` | `http://127.0.0.1:8080` | Control-plane base URL |
| `--context` | `default` | Context name to create and select |
| `--api-key` | environment | Existing credential; prefer `INFERCRANE_API_KEY` to avoid shell history |
| `--output` | `human` | `human` or `json` |

`init` verifies authentication through the read-only identity endpoint before writing configuration. Use `--skip-check` only when intentionally configuring an offline control plane. It does not create or enroll a principal.

### Contexts and authentication

```bash
infercrane context list
infercrane context show
infercrane context use production
infercrane --context staging status qwen-prod
infercrane auth status
infercrane auth status --output json
infercrane whoami
```

JSON output uses stable lowercase fields (`id`, `tenant_id`, `name`, `role`, `kind`, and `scopes`)
under `principal`, plus `context`, `control_url`, `console_url`, and `credential_source` (where the
key was found: the keychain, the config file, or `INFERCRANE_API_KEY`), so authentication checks can
be consumed directly by scripts without depending on Go field names. `whoami` is the same as
`auth status`.

Legacy single-context configuration is migrated on the next `init`. Context listing and display
never print stored credentials.

### Shell completion

```bash
infercrane completion bash
infercrane completion zsh
infercrane completion fish
infercrane completion powershell
```

Homebrew installs generated completions automatically. Completion suggests real values from the
configured control plane:

| What you type | Suggestions |
|---|---|
| `status`, `delete`, `logs`, and other deployment commands | deployment names, with state and model |
| `endpoint inspect` and other endpoint actions | endpoint names, with state |
| `optimize report`, `inspect`, `results`, `watch`, `approve`, `activate`, `cancel` | optimization run IDs, with model and state |
| `optimize activate RUN --candidate` | that run's setup IDs, with state |
| `optimize propose`, `deploy`, `plan`, `apply` | catalog models |
| `--gpu`, `--region`, `--provider`, `--cloud` | values from the sourced GPU price catalog, narrowed by the provider and GPU already typed |
| `--target-deployment` | deployment names |
| `--objective`, `--output`, `--compute`, `--strategy` | their fixed values |

zsh and fish show the description next to each value. Completion only reads, gives up after 1.5
seconds, and stays silent when the control plane is unreachable or the CLI is not signed in: it
never prints an error and never mutates anything. A GPU or region suggestion says where it is
offered, not that capacity is available.

### `doctor`

Ask the control plane to check its own dependencies.

```bash
infercrane doctor
infercrane doctor --cloud
infercrane doctor --serverless --output json
infercrane doctor --aws
infercrane doctor --gcp
infercrane doctor --kubernetes
infercrane doctor coder-production --window 1h
```

`--cloud` adds SkyPilot credentials and RunPod advisory accelerator availability; `--serverless`
adds RunPod Serverless credentials and template validation; `--aws` performs a read-only role
assumption and dependency probe for the configured AWS BYOC adapter; `--gcp` checks Application
Default Credentials, every configured Compute dependency, immutable images, and Private Google
Access; `--kubernetes` checks the explicit context, optional KServe CRD, and required namespaced
permissions. Diagnostics are read-only and do not create provider resources.
The capability table distinguishes `supported`, `unsupported`, and `unknown`. InferCrane never
silently changes hardware, and never claims cache or fast-resume behavior that an adapter cannot
observe.

### Local accelerator discovery

Inspect NVIDIA GPU inventory without installing a runtime or changing the host:

```bash
infercrane discover local
infercrane discover local --output json
```

Discovery reports its evidence source and limitations. It does not infer runtime compatibility,
model fit, or performance from a device name alone. `infercrane agent detect` also reports Apple
Silicon and AMD GPUs, with their unknown fields named, and the model servers on this machine.

### Run the control plane

```bash
infercrane serve
```

`serve` starts the control plane and inference gateway from validated environment configuration.
Production deployments should use the container and service guidance in
[Production operations](/production), including PostgreSQL, TLS, bootstrap authentication,
stable instance identity, and graceful shutdown.

## Operations workspaces

### `inbox`

```bash
infercrane inbox
infercrane inbox --limit 100 --output json
```

The inbox reads tenant-scoped endpoint, deployment, and optimization run summaries, ranks
non-serving state and staged candidate revisions and plans deterministically (an `observing` endpoint is observe-only
by design and is not listed), and prints the exact persisted field behind each item. It fails the
whole read if any of those APIs is unavailable, so a partial inventory cannot look healthy. It does
not run Doctor implicitly and never reads prompt or response content.

Optimization runs appear with the same rules as [run notifications](/features/optimization#get-told-when-a-run-needs-you):
a run waiting for spend approval, a result waiting for your decision (critical once its approval is
about to end), a running run whose approval is about to end, setups that have waited more than five
minutes for your signed evaluation or for the eval set the run names, and a run that failed in the
last 24 hours. Each item names the next command, such as `infercrane optimize approve` or
`infercrane evaluation set upload`. The inbox reads the newest 100 runs.

### `observe`

```bash
infercrane observe coder-production
infercrane observe qwen-prod --watch
infercrane observe coder-production --diagnose
```

The default snapshot is read-only. Endpoint snapshots combine logical identity, serving plans,
Guard, admission, and alerts; deployment snapshots combine lifecycle, traffic, active operation,
Guard, and events. `--diagnose` explicitly persists a fresh deterministic Doctor evaluation.
A field the control plane has not recorded prints as `none` (for example, no staged candidate plan)
or `unknown`. JSON keeps the raw values and reports an unstaged candidate as `"candidate_plan": null`.

### `telemetry collect dcgm|amd`

```bash
infercrane telemetry collect dcgm coder-production \
  --url http://127.0.0.1:9400/metrics \
  --selector deployment=coder-production \
  --replica replica-03 --ttl 2m

infercrane telemetry collect amd qwen3-8b-mi300x \
  --url http://127.0.0.1:5000/metrics \
  --selector pod=qwen3-8b-mi300x-0
```

`dcgm` reads NVIDIA's dcgm-exporter and `amd` reads the AMD Device Metrics Exporter (default port
5000; `--metric-prefix` if it sets one). The command parses a bounded, documented subset of the
exporter's Prometheus metrics locally and sends normalized content-free evidence through the
authenticated control API. Use `--file SNAPSHOT` for
offline input. The snapshot is immutable, active-revision-bound, and becomes stale at its declared
TTL; arbitrary Prometheus metrics are not accepted.

`--interval 15s` keeps collecting until stopped; each snapshot stays fresh for three intervals.

### `profile`

```bash
infercrane profile coder --engine-url http://127.0.0.1:8000 --trace-dir /profiles --duration 10s
infercrane profile coder --trace ./profiles --no-upload
infercrane profile coder --list
infercrane profile coder --compare gpc-BEFORE,gpc-AFTER --output json
```

Run on the GPU host (or in a sidecar that shares the trace volume): the command records a bounded
trace through vLLM's or SGLang's own `/start_profile` and `/stop_profile`, analyzes it locally, prints
the verdict and the numbers behind it, and records the capture against the deployment's active
revision. It states that the replica slows while the profiler runs and asks before starting; `--yes`
skips the question. `--dcgm-url` samples dcgm-exporter during the capture. `--trace` analyzes existing
Kineto JSON, rocprofv3 CSV, or Nsight Systems CSV files; with `--no-upload` it needs no sign-in.
`--open` opens the capture in the dashboard. `--output json` prints the stable
`infercrane.profile-result/v1` document. See [GPU profiling](/features/gpu-profiling).

### `finops collect opencost`

```bash
infercrane finops collect opencost coder-production \
  --url http://127.0.0.1:9003/allocation \
  --window 24h --aggregate controller \
  --allocation coder-production --currency USD
```

The command selects exact OpenCost allocation keys, records a currency-explicit average hourly rate
against the active immutable revision, and creates a persisted FinOps report. Multiple exact keys may
be comma-separated. `--allocation` and `--currency` are mandatory; cluster-wide attribution and
currency conversion are never inferred. Use `--file allocation.json` for offline evidence.

### `artifact`

```bash
infercrane artifact inspect ARTIFACT_ID
infercrane artifact prefetch ARTIFACT_ID --provider aws --location cache://models
infercrane artifact observe ARTIFACT_ID --provider aws --location cache://models \
  --state present --source aws-ebs-adapter --ttl 10m
```

Prefetch records durable intent; only a fresh provider observation is cache-hit evidence.

### `evaluation`

```bash
infercrane evaluation keygen --file quality-evidence.key
infercrane evaluation ingest DEPLOYMENT REVISION --result evaluator-result.json \
  --key quality-evidence.key --file evidence.json --attach
infercrane evaluation sign DEPLOYMENT REVISION --suite SUITE --suite-version VERSION \
  --evaluator NAME --evaluator-version VERSION --score 0.95 --passed=true \
  --samples 100 --artifact-digest sha256:DIGEST \
  --key quality-evidence.key --file evidence.json
infercrane evaluation verify evidence.json
infercrane evaluation attach DEPLOYMENT --file evidence.json
infercrane evaluation list DEPLOYMENT

# Eval sets for the built-in answer check
infercrane evaluation set default > eval-set.json
infercrane evaluation set digest eval-set.json
infercrane evaluation set upload eval-set.json
infercrane evaluation set inspect sha256:DIGEST
infercrane evaluation set delete sha256:DIGEST
```

`ingest` accepts the strict evaluator-result v1 interchange contract, rejects unknown content fields,
binds it to one immutable revision, signs it, and optionally attaches it. Evidence is
signature-verified and contains aggregate values only. The evaluator name `infercrane-builtin` is
reserved for InferCrane's own answer check and is refused.

`evaluation set` manages the prompt sets that replace the built-in prompts of an optimization run's
answer check. `default` prints the built-in suite to copy and adapt, `digest` validates a file
without uploading it, and `upload` prints the digest a run names with `--eval-set`. See
[Semantic quality evidence](/features/semantic-quality#built-in-answer-check).

### `mcp`

```bash
infercrane mcp
```

Starts a stdio MCP server with read-only deployment, endpoint, request, operation, and curated-recipe
tools. No mutation tool is registered. See [MCP for coding agents](/integrations/mcp).

## Admission and async inference

```bash
infercrane admission get coder-production
infercrane admission set coder-production --max-concurrency 32 --max-queue 64 \
  --queue-timeout-ms 5000 --max-output-tokens 8192 --priorities normal,high

infercrane async submit coder-production --file request.json \
  --idempotency-key document-42
infercrane async get JOB_ID
infercrane async cancel JOB_ID
```

`async submit` persists protocol-native request content only after explicit encrypted-storage
consent, returns a durable job ID, and does not depend on the client remaining connected. See
[Admission and async inference](/features/admission-async) for retry, retention and webhook rules.

### Terminal

```bash
infercrane ui
```

The terminal workspace is reconnectable, supports state-valid guarded actions, and can be forced
read-only with `infercrane ui --read-only`. It requires an interactive terminal and never uses tmux
for persistence. See [Terminal operations workspace](/features/terminal-ui).

## Plan and deploy

### `optimize propose`

Preview the setups a run would measure, as inspectable DeploymentSpecs, without contacting a
control plane or provider. Check the optional estimator first:

```bash
infercrane optimize doctor
```

The default `--source auto` uses the pinned AIConfigurator adapter only when its exact supported
Python tuple is available and visibly falls back to the reviewed catalog otherwise. Use `--source
catalog` for a deterministic offline proposal, or `--source aiconfigurator` to require the estimator
and fail rather than falling back.

```bash
infercrane optimize propose mistral-7b-instruct \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --profile interactive \
  --source auto --target-concurrency 8 \
  --max-ttft-p95-ms 200 --max-tpot-p95-ms 25 \
  --write-dir .infercrane/setups/mistral-interactive
```

Catalog output is `unmeasured`; AIConfigurator output is `modeled`. Neither is qualified. Use
`--output json` to retain the input digest, source version, modeled-result digest, compatibility
evidence, missing evidence, and limitations. `--workload-fingerprint` can bind a content-free
observed workload identity to the proposal. Simulated compatibility is excluded unless
`--include-simulated` is explicit. The command refuses to overwrite a non-empty output directory.

The reviewed catalog spans instruction, reasoning, coding, embeddings, multimodal, and
enterprise-text workloads. A profile for one model is never evidence for another model, precision,
GPU, runtime, or topology. See [Evidence-gated optimization](/features/optimization).

### `optimize create`

Create a run: persist the proposal and its setups without provider mutation, then grant bounded
paid authority explicitly:

```bash
infercrane optimize create llama-3.1-8b-instruct \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --max-candidates 3

# Safely evolve an existing production deployment instead.
infercrane optimize create llama-3.1-8b-instruct \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --max-candidates 3 \
  --target-deployment llama-production
infercrane optimize inspect RUN_ID
infercrane optimize approve RUN_ID --max-cost-usd 20 --expires-in 1h
infercrane optimize watch RUN_ID
infercrane optimize results RUN_ID
infercrane optimize activate RUN_ID --candidate SETUP_ID   # roll out the winning setup
infercrane operation watch ROLLOUT_OPERATION_ID
infercrane optimize cancel RUN_ID
```

In a terminal, `optimize approve` first shows the spend cap, when the approval expires, and every
setup the run starts, and asks before approving. `--yes` skips the question; scripts, pipes, and
`--output json` never see it. Approval retries do not extend the first persisted expiry. Creation and inspection allocate no
infrastructure. The default `new_endpoint` intent stops after qualification and waits for you to
roll out the winner. `--target-deployment` selects `evolve_endpoint`, which must also pass Release
Guard before it waits for you. `optimize activate` rolls out the winning setup in both cases: it
marks the qualified new deployment active, or hands an evolution to the existing guarded rollout
operation. Retrying the command adopts the same durable operation; InferCrane never rolls out a
setup from the optimizer loop.

`optimize watch` follows a run live and `optimize results` prints the same summary once: each setup
by name, the current setup first, which setup and measured turn the run is on, time elapsed, the
control plane's estimate of time left, spend so far against the cap (estimated from the quoted
rate), the measured comparison, the answer checks, and the decision with the exact `activate`
command. `inspect` is the full record, with every setup's name next to its ID. See
[Follow a run live](/features/optimization#follow-a-run-live).

Every setup's answers are checked before ranking. By default InferCrane runs its built-in answer
check against your current setup. `--eval-set sha256:DIGEST` replaces the built-in prompts with an
uploaded eval set, and `--quality-check customer_evidence` makes every setup wait for evidence you
sign and attach instead. `inspect` prints each setup's answer-check result and, while a setup
waits on you, the exact command that unblocks it. `--output json` returns the control API's
`quality` object for every setup, under `candidates`.

`--migrate-from ENDPOINT/BINDING` makes the run a [migration Proof](/features/migration): the closed
API behind that endpoint's external binding is the baseline, `--workload-fingerprint` must name a
trace captured from that endpoint (`infercrane migrate capture`), and `--eval-set` must name a graded
set of at least 30 prompts. `--dialect openai` sends `max_completion_tokens` to OpenAI's API;
`openai-compatible` (the default) sends `max_tokens`. `--max-quality-drop` (default 5) is the
largest graded-quality drop, at the upper bound of the paired-bootstrap interval, a setup may show
and still pass. `optimize activate` on a migration run starts a 5% canary on the closed API's
endpoint.

`inspect`, `results`, `approve`, `activate`, and `cancel` print a **Proposal warnings** block when
the run's proposal recorded warnings, such as skipped speculative-decoding setups.
`--output json` keeps `warnings` as the control API returned it: an empty list means none were
recorded, and an absent field means the stored proposal could not be read. Warnings are not
performance evidence.

### `artifact optimize`

Plan and attest an externally built optimized checkpoint, speculator, or TensorRT engine:

```bash
infercrane artifact optimize plan BASE_ARTIFACT_ID \
  --preset eagle3 --tool-version 0.6.0 \
  --builder-image-digest sha256:BUILDER_DIGEST \
  --license-spdx Apache-2.0
infercrane artifact optimize start OPTIMIZED_ARTIFACT_ID
infercrane artifact optimize attest OPTIMIZED_ARTIFACT_ID \
  --state ready --output-repository hf://ORG/MODEL \
  --output-revision IMMUTABLE_COMMIT --output-digest sha256:OUTPUT_DIGEST \
  --evidence-file build-evidence.json
infercrane artifact optimize qualify OPTIMIZED_ARTIFACT_ID \
  --candidate-run SETUP_ID --quality-evidence QUALITY_EVIDENCE_ID
```

Presets are `fp8`, `awq`, `gptq`, `nvfp4`, `eagle3`, `mtp`, and `dflash`. There is no TensorRT engine
preset: TensorRT-LLM removed its engine backend, and its PyTorch backend loads checkpoints directly.
An engine built by an earlier TensorRT-LLM release can still be recorded with `--plan-file`. Builders
are never executed inside the InferCrane API process, and no optimized artifact qualifies without
exact setup, revision, digest, and semantic-quality evidence.

### `workload`

Create a repository-local inference project, validate it without allocating a GPU, and use the same
DeploymentSpec for build, plan, and deployment:

```bash
infercrane workload init ./fraud-explainer \
  --recipe mistral-7b-instruct \
  --profile vllm-interactive
infercrane workload validate ./fraud-explainer
infercrane workload plan ./fraud-explainer
infercrane workload deploy ./fraud-explainer --wait
```

`workload init --recipe NAME --profile PROFILE` pins a reviewed model commit and writes the selected
profile's runtime version, immutable workload when present, GPU type and count, provider hint,
replica bounds, and routing policy. The default profile is
the recipe's general starting point; profiles are not benchmark claims. `workload build --tag IMAGE` performs a
local Docker Buildx build for custom OCI projects; add `--push` to record a registry-confirmed
immutable digest. `workload dev` binds a custom OCI workload only to loopback. See
[Inference projects](/features/inference-projects).

### `plan`

Preview semantic changes without provider or database mutation.

```bash
infercrane plan Qwen/Qwen3-8B \
  --name qwen-prod \
  --cloud runpod \
  --gpu L40S \
  --min 1 \
  --max 4
```

Provisioned and serverless plans include an explicit readiness-evidence boundary:

```text
Readiness: unavailable: fresh provider capacity and artifact-cache observations are not available during this static plan; no startup time is fabricated
Artifact cache: unknown
Capacity:       unknown
Startup stages: capacity -> container -> artifact -> runtime -> readiness
```

This is intentionally not a time estimate. If the tenant has at least three successful historical
observations for the exact provider adapter, runtime, region, and GPU, `plan` instead shows an
`observed` p50 from durable replica intent through runtime readiness. It shows p95 only after twenty
successes and labels the sample count and boundary. That is historical evidence, not a capacity
guarantee. For a DeploymentSpec pinned to an immutable model revision, `plan` can additionally show
per-stage observed p50 after three successes and p95 after twenty only when model commit, runtime
version and arguments, provider, region, GPU type/count, and compute mode all match. A stage with no
provider marker or insufficient samples remains absent/unknown. Once an operation starts, durable
events replace unknown stages with fresh provider and runtime observations where those boundaries
are actually exposed.

### `deploy` and `apply`

`deploy` creates a cloud or existing-target deployment. `apply` declaratively converges a deployment using the same input shape.

```bash
infercrane deploy Qwen/Qwen3-8B \
  --cloud runpod \
  --gpu L40S \
  --min 1 \
  --max 4 \
  --idempotency-key qwen-prod-initial \
  --wait

infercrane apply examples/infercrane.yaml \
  --idempotency-key qwen-prod-spec-01
```

| Flag | Default | Applies to | Meaning |
|---|---|---|---|
| `--name` | derived from model | all | Logical deployment name |
| `--targets` | none | existing | Comma-separated registered targets |
| `--cloud` | `runpod` on primary path | elastic/serverless | Registered provider cloud; `runpod`, `aws`, and `kubernetes` have distinct qualification states |
| `--backend` | standard provider path | elastic | `dynamo` expands to the safe aggregated Dynamo baseline; advanced topology uses YAML |
| `--provider-adapter` | selected from cloud/runtime | provisioned | Exact adapter identity; advanced escape hatch, normally inferred by `--backend` or YAML |
| `--runtime` | `vllm` | provisioned | `vllm` or `sglang` where the selected adapter has compatible evidence |
| `--gpu` | `L40S` on primary path | elastic/serverless | Requested GPU |
| `--region` | provider-selected | provisioned | Provider region; required for AWS BYOC and ignored by the namespace-scoped Kubernetes adapter |
| `--compute` | `elastic` | provisioned | `elastic` or `serverless` |
| `--min` | `1`; serverless defaults to `0` | provisioned | Minimum replicas/workers |
| `--max` | `1` | provisioned | Maximum replicas/workers |
| `--wait` | false | mutations | Follow durable progress to a terminal state |
| `--wait-timeout` | unlimited | waited mutations | Stop the local wait after a Go duration such as `20m`; the operation continues |
| `--idempotency-key` | generated | mutations | Stable safe-retry identity |
| `--compute-connection` | none | elastic | Deploy on your own RunPod account: the name or ID of a verified compute connection (add one in the dashboard under Settings → Connections) |
| `--infercrane-cloud` | false | elastic | Deploy on InferCrane Cloud, paid from prepaid credits |
| `--stop-after` | `1h` | `--infercrane-cloud` | Stop the deployment after this long, in whole minutes from `15m` to `24h` |
| `--output` | `human` | all | `human` or `json` |

The two self-serve destinations of a hosted workspace are `--infercrane-cloud` and
`--compute-connection NAME`; they cannot be combined with each other, `--targets`, `--backend`, or
`--compute serverless`.

```bash
infercrane deploy Qwen/Qwen3-8B --infercrane-cloud --stop-after 6h
infercrane deploy Qwen/Qwen3-8B --compute-connection my-runpod --gpu L40S
```

A YAML path cannot be combined with deployment flags. See [DeploymentSpec](/deployment-spec).
Custom OCI uses the YAML form because its runtime contract is part of the immutable revision.
Advanced Dynamo topology also uses YAML. See [SGLang](/integrations/sglang),
[NVIDIA Dynamo](/integrations/dynamo), and [Custom OCI workloads](/features/custom-oci).

After submission, human output prints the exact commands to follow durable progress. A successful
wait prints the command for the first inference request.

Separate the name applications call from the deployment that currently serves it:

`endpoint plan` makes the first plan active and stages later plans as candidates. Inspect and

```bash
infercrane endpoints

infercrane endpoint guard coder-production --evaluate
infercrane endpoint promote coder-production PLAN_ID
```

`--bindings` is ordered and accepts optional bounded weights, for example

Authenticated external APIs add provider-neutral policy flags to `endpoint bind`:

```bash

```

bindings and their release history are deliberately unchanged.

```bash

infercrane environment promote coder-staging --to coder-production --yes
```

## Connect an existing workload

The simple path verifies the upstream model list through the control-plane API and starts in
observe-only mode:

```bash
infercrane connect https://vllm.internal/v1 --as coder-production --type vllm
```

Use `--model` when the endpoint exposes more than one physical model. Use `--manage-traffic` only
when the endpoint has been qualified and should immediately enter the InferCrane logical route.
For a server started with an API key, `--token-env VAR` sends the key held in `VAR` once; the control
plane stores it encrypted and uses it for discovery, health checks, and, with `--manage-traffic`,
the requests it routes to the server (this needs
`INFERCRANE_CREDENTIAL_ENCRYPTION_KEY` on the control plane). `connect` refuses a loopback URL when
the control plane runs elsewhere, because the control plane would probe its own machine; use the
agent for that server.
The advanced ownership-compatible command remains available:

```bash
infercrane adopt endpoint coder-production \
  --url https://vllm.internal/v1 \
  --model coder \
  --upstream-model Qwen/Qwen3-8B \
  --ownership observe-only
infercrane adopt promote coder-production --ownership traffic-managed
```

Use `traffic-managed` only when InferCrane should publish the healthy existing target. Neither mode
transfers provider lifecycle ownership. See [Adopt and diagnose](/features/adoption-diagnostics).

## Connect servers on this machine

`infercrane agent` observes model servers the control plane cannot reach (on a laptop, behind NAT,
or in a private network) through an outbound-only agent. See
[Run on this machine](/run-on-this-machine) and [InferCrane agent](/architecture/agent).

```bash
infercrane agent detect
infercrane agent run
infercrane agent run --server http://127.0.0.1:8000 --token-env VLLM_API_KEY --as qwen-local
infercrane agent run --gateway 127.0.0.1:4000
infercrane agent run --once --output json
infercrane agent create rack-12
infercrane agent list
infercrane agent revoke rack-12
```

| Flag | Default | Meaning |
|---|---|---|
| `--server` | ports 8000, 30000, 8080, 11434, 1234 on loopback | A server URL; repeatable |
| `--no-detect` | false | Observe only the `--server` URLs |
| `--token-env` | none | Variable holding the API key of the `--server` servers, sent to them only as a bearer token; needs `--server` |
| `--auth-header-env` | none | Variable holding the full `Authorization` header for the `--server` servers; needs `--server` |
| `--model` | the loaded or only model | Model to observe when a server lists several |
| `--as` | derived from the model | Endpoint name, when one server is observed |
| `--gateway` | off | Listen address of the local pass-through that records request shapes |
| `--gateway-server` | the only observed server | Server the gateway forwards to |
| `--name` | this host's name | Agent name when `agent run` creates a key with your sign-in |


`operation list` shows the newest 20 operations for your organization; `--limit` accepts 1 to 500.
When a page is full, it prints the `--before` command for the next older page.

Long operations belong to the control plane, not the terminal. `deploy`, `apply`, rollout, scale,
and deletion continue after the CLI disconnects. Pressing Ctrl-C stops only the local watcher. Run
`infercrane operation watch ID` later to resume from persisted progress; add `--wait-timeout 20m`

that requests cooperative server-side cancellation and provider cleanup.

accept inference traffic. `Convergence` answers whether desired capacity, a rollout, or deletion is
still progressing. A deployment can therefore be `serving · converging` while a provider allocates
another replica; this is not reported as an outage. JSON output exposes the same stable fields under
`lifecycle_status`, including ready and desired replica counts, provisioning and draining counts,
candidate state, and the blocking durable operation.

Deterministic explanations use only persisted state and measurements:

```bash
infercrane explain qwen-prod
```

## Benchmark

Run AIPerf and persist the exact reproduction metadata.

```bash
infercrane benchmark mistral-prod \
  --profile interactive \
  --ttft-slo-ms 250 \
  --tpot-slo-ms 25 \
  --revision active
```

`--profile` accepts `balanced`, `buffered`, `interactive`, `long-context`, `long-generation`,
`overload`, or `throughput`. Profiles are immutable workload shapes; explicit request,
concurrency, token, and streaming flags override their defaults. `--revision` accepts `active`,
`candidate`, or an explicit revision ID. Without a profile, defaults remain 100 requests,
concurrency 10, and seed 17. Declared TTFT, TPOT, or total-latency SLOs produce measured goodput.

Capture and search immutable recipes only after a matching benchmark exists:

```bash
infercrane recipe create mistral-prod --name mistral-balanced --version 1.0.0
infercrane recipes mistral --limit 20
```

Compare persisted measured configurations without provisioning new capacity:

```bash
infercrane lab 'mistralai/Mistral-7B-Instruct-v0.3@IMMUTABLE_COMMIT' \
  --objective interactive \
  --profile interactive \
  --max-ttft-p95-ms 200ms \
  --max-hourly-cost 3
```

The objective can be `interactive`, `latency`, `throughput`, or `cost-efficiency`. InferCrane recommends only across
an exact common workload digest; mixed shapes remain `UNRANKED`. See
[Recipes and Inference Lab](/features/recipes-lab) for the provenance and missing-evidence contract.

## Migrate from a closed API

`infercrane migrate` measures a closed API routed through an endpoint as the baseline and switches the
endpoint to an owned deployment in stages. See [Migrate from a closed API](/features/migration).

```bash
infercrane migrate capture support-bot --binding primary --window 24h
infercrane migrate price support-bot primary --authority list_price \
  --input-usd 0.40 --cached-input-usd 0.10 --output-usd 1.60 --valid-until 2026-12-31
infercrane migrate verdicts RUN_ID
infercrane migrate canary support-bot --verdict VERDICT_ID --percent 5
infercrane migrate primary support-bot --window 1h
infercrane migrate rollback support-bot
```

| Action | What it does |
|---|---|
| `capture ENDPOINT` | Captures a content-free trace of the endpoint's requests (`--binding` for one binding); prints the workload fingerprint |
| `price ENDPOINT BINDING` | Records the closed API's per-token rate card: `--authority list_price` or `contract`, USD per 1M tokens, `--valid-until` |
| `verdicts RUN` | Lists the signed quality verdicts of a migration run |
| `canary ENDPOINT` | Sends at most 5% (`--percent`) of the endpoint's traffic to the deployment a PASS `--verdict` judged |
| `primary ENDPOINT` | Serves from the owned deployment first with the closed API as fallback, if Release Guard passes on the canary's per-binding traffic (`--window`) |
| `rollback ENDPOINT` | Routes the endpoint to the closed API alone |

A step Release Guard does not pass changes nothing and exits with the decision and its reasons.

## Revisions and Release Guard

```bash
infercrane rollout inspect qwen-prod
infercrane rollout policy get qwen-prod
infercrane rollout policy set qwen-prod \
  --require-compatibility \
  --require-synthetic \
  --auto-rollback \
  --validation-max-requests 100 \
  --validation-max-concurrency 4

infercrane rollout create qwen-prod \
  --model Qwen/Qwen3-8B \
  --cloud runpod \
  --gpu H100 \
  --min 1 \
  --max 2 \
  --idempotency-key qwen-prod-rev-19

# Preserve a complete advanced serving topology without flattening it to flags.
infercrane rollout create llama-production \
  --file infercrane-dynamo-candidate.yaml \
  --idempotency-key llama-production-dynamo-r2

infercrane rollout provision qwen-prod REVISION_ID --wait
infercrane rollout validate qwen-prod --acknowledge-validation-cost --wait
# Roll out the candidate revision once Release Guard accepts it, or reject it.
infercrane rollout promote qwen-prod REVISION_ID --reason 'guard accepted'
infercrane rollout reject qwen-prod REVISION_ID --reason 'TTFT regression'
# Roll back to an earlier revision.
infercrane rollout rollback qwen-prod REVISION_ID --reason 'TTFT regression' --wait
```

Creating a candidate revision also accepts `--model-revision`, `--runtime`, `--runtime-version`, `--runtime-args`, `--routing`, and `--region`. `--file` preserves a complete validated DeploymentSpec, including advanced serving topology, and cannot be mixed with candidate override flags. Rolling out a revision with `rollout promote` remains policy-gated; no LLM decides the outcome. `rollout rollback` requires `--reason`.

`rollout validate` is explicit synthetic traffic, not shadowing. It runs the existing AIPerf adapter
against active and candidate revisions using the same workload and persisted hard bounds. The
acknowledgement is mandatory because both runs may incur provider cost.

```bash
infercrane slo delete qwen-prod
```

`recommended` identifies a qualified setup that satisfies the policy. `no_match` means the measured
setups violate it. `unknown` means required evidence is missing. See
[Inference decisions](/features/inference-decisions).

Advisory Autopilot turns that evidence into a reviewable plan without mutating production:

```bash
infercrane autopilot plan qwen-prod --objective minimize_cost
infercrane autopilot inspect PLAN_ID
infercrane autopilot approve PLAN_ID
```

Approval records human intent. It does not bypass Release Guard, evidence requirements, hard
budgets, or the single mutation-owner boundary.
