# Upgrade and compatibility

InferCrane v1 separates four compatibility surfaces: the control API, DeploymentSpec, integration
contracts, and PostgreSQL schema. A passing runtime or provider conformance test does not override
the policy for another surface.

For an application SDK, OpenAI-compatible protocol, or runtime behavior change, use the complete
[development → staging → production protocol rollout](/runbooks/protocol-rollout). It defines the
buffered, streaming, cancellation, error-schema, consumer-canary, fail-closed promotion, and
restoration gates; the control-plane binary procedure on this page is a separate compatibility
boundary.

## Before upgrading

1. Read the release notes and compatibility matrix.
2. Back up PostgreSQL and verify the dump with `pg_restore --list`.
3. Run `infercrane plan` for representative DeploymentSpecs with the new CLI.
4. Run local qualification against the exact candidate commit.
5. Verify provider credentials and inventory with `infercrane doctor` and `infercrane orphans`.
6. Upgrade the control plane before upgrading generated SDKs or automation clients.

```bash
scripts/backup-postgres.sh /secure/path/infercrane-before-v1.dump
make qualify-local
```

## Automate a provider or serving-plan change safely

A provider change is a candidate revision, not an in-place infrastructure edit. Automation should
stop before mutation unless the exact combination is present in release evidence:

```bash
infercrane integrations --output json
infercrane models inspect MODEL_CATALOG_NAME --output json
infercrane plan deployment-provider-change.yaml --output json
```

Follow the [exact-combination compatibility check](/compatibility#check-one-exact-serving-combination).
The dry run must name the provider adapter, runtime and version, compute mode, immutable model,
accelerator/topology, region, and replica bounds. Stop safely when any required capability is
`unsupported`, `unknown`, `planned`, or lacks the environment-specific qualification required by
policy. Do not reinterpret missing evidence as a warning in deployment automation.

Only after the dry run and qualification gate pass should automation submit the same reviewed spec:

```bash
infercrane apply deployment-provider-change.yaml \
  --idempotency-key provider-change-REVISION \
  --wait
infercrane rollout inspect DEPLOYMENT
```

`apply` stages an immutable candidate; it does not replace active traffic. Run Release Guard and
promote explicitly. If provisioning or validation fails, preserve the operation/evaluation evidence
and reject the candidate; the active provider remains routed. The current decision must be `ACCEPT`
for the same active/candidate pair before promotion. After a post-promotion regression, restore the
retained previous revision with `rollout rollback`; never delete the deployment as release recovery.

## PostgreSQL migration contract

Migrations are embedded, ordered, forward-only, and transactionally applied under a PostgreSQL
advisory lock. The migration ledger stores a SHA-256 checksum for every migration. Startup fails if:

- a previously applied migration was edited;
- the ledger has a gap;
- the database contains a migration unknown to the running binary; or
- a migration cannot commit atomically.

The first v1 startup backfills checksums for a pre-v1 ledger after matching every known migration
name. This is a trust-on-first-v1-upgrade bootstrap: a legacy ledger did not retain enough
information to prove the bytes originally executed. Back up and inspect that database before the
first v1 startup. Every subsequent startup verifies the persisted checksum. Automated qualification
upgrades every historical migration prefix to the current schema.

Do not delete ledger rows, edit released SQL files, or start an older binary after a newer migration
has run. Restore the pre-upgrade backup if application rollback requires schema rollback.

## DeploymentSpec

The current file contract is:

```yaml
apiVersion: infercrane.dev/v1
kind: Deployment
```

Pre-v1 files without these two fields are read as v1 for compatibility. New files should include
them. Unknown fields, versions, and kinds fail closed. Additive optional v1 fields are compatible;
removing or changing a v1 field requires a future versioned conversion path.

## Control API and SDKs

`/api/v1` is the stable v1 namespace. Within v1:

- new optional response fields are additive;
- clients must ignore response fields they do not understand;
- existing field meaning and error codes do not change silently;
- removal requires deprecation in release notes for at least two minor releases;
- generated SDK major versions track the API major version.

CLI human output is not a parsing contract. Automation must use `--output json`, the generated SDKs,
or Terraform.

## Provider and runtime contracts

Provider Contract `infercrane.provider/v1` and Runtime Contract `infercrane.runtime/v1` are versioned
separately from the product. Registration exposes an adapter to composition; only the capability and
qualification inventory establishes evidence for an exact runtime/provider/mode combination.

```bash
infercrane integrations --output json
```

## Move a deployment from vLLM 0.22.1 to 0.34.0

The control plane now pins vLLM 0.34.0 as the current release. Upgrading the control plane changes
no running deployment:

- A revision that records `runtime_version: 0.22.1` keeps the 0.22.1 image when it scales, replaces
  a lost replica, or rolls back. The accelerator catalog (`GET /api/v1/catalog/accelerators`) lists
  those images with `status: legacy`.
- A new revision that names no version gets 0.34.0, and new setups are planned on 0.34.0.
- A built-in vLLM revision that names a release with no pinned image (anything other than 0.34.0 or
  0.22.1) is refused with `runtime vllm X is not pinned`. Before this release it ran the pinned
  0.22.1 image while recording X. Before upgrading, list such revisions and move them first.
- RunPod serverless and Dynamo deployments run the image the operator configured (the serverless
  template, `INFERCRANE_DYNAMO_VLLM_IMAGE_DIGEST`), not a pinned image. Move them by changing that
  image and its recorded version.

Move each 0.22.1 deployment with a candidate revision on 0.34.0, measured against the running one,
the same way as any other runtime change:

```bash
infercrane plan deployment-vllm-034.yaml --output json
infercrane apply deployment-vllm-034.yaml --idempotency-key vllm-034-REVISION --wait
infercrane rollout inspect DEPLOYMENT
```

A deployment whose checkpoint vLLM 0.34.0 no longer loads stays on 0.22.1 until its model moves to
another format. vLLM 0.34.0 moved GGUF and bitsandbytes to out-of-tree plugins (`vllm-gguf-plugin`,
`vllm-bnb-plugin`) that the pinned image is not known to carry, and removed `fp_quant` and
`cpu_awq`. The model check reads quantization methods from the 0.34.0 registry snapshot, so it
reports such a checkpoint's quantization as unknown ("not a vLLM 0.34.0 quantization method"), never
as a pass.

With [Stay optimized](/features/optimization#stay-optimized) on, the endpoint's next check fires an
engine-release trigger ("vllm 0.34.0 is the new pinned engine release; this endpoint runs 0.22.1")
and proposes that run. Re-measure before promoting: 0.34.0 changes defaults under every setup.
Upgrading the control plane fires this trigger on every 0.22.1 endpoint with Stay optimized on at
once. A proposed run starts by itself only where the endpoint allows automatic runs, and only within
its monthly cap; otherwise it waits for a person.

| Default | vLLM 0.22.1 | vLLM 0.34.0 |
|---|---|---|
| Batch budget (`--max-num-batched-tokens` / `--max-num-seqs`) | 2048 / 256 below 70 GiB and on A100; 8192 / 1024 from 70 GiB | 2048 / 256 below 70 GiB and on A100; 8192 / 1024 from 70 GiB; 16384 / 1024 from 160 GiB (B200, B300, MI300X and newer) |
| KV cache block | 16 tokens | 64 tokens, unless the attention backend prefers another |
| KV cache sizing | `gpu_memory_utilization` 0.92 | Extensible KV cache on CUDA and ROCm, sized from memory free after CUDA-graph capture; `gpu_memory_utilization` defaults to 1.0 (0.92 with `--no-enable-extensible-kv-cache`) |
| Async scheduling | On, except with CPU n-gram, draft-model, suffix, Medusa, or MLP speculation | On, also with those; off with ROCm DeepEP high-throughput and dual-batch overlap |
| CUDA graphs | Batches up to `min(2 × max_num_seqs, 512)` | The same, with a ceiling of 1024 on B200 and B300, where decode graphs cover every batch up to `max_num_seqs` |
| LoRA | Ranks 1, 8, 16, 32, 64, 128, 256, 320, 512 | Unchanged |

The vLLM release notes report 6–18% higher per-token decode latency at concurrency 128 on some H200
models from the new KV cache sizing; `--no-enable-extensible-kv-cache` or an explicit
`--gpu-memory-utilization` restores the old sizing. A server that shares its GPU with another process
needs an explicit `--gpu-memory-utilization`, because the default now takes the memory vLLM finds
free. A 0.22.1 setup that sets `--max-cudagraph-capture-size` keeps working on 0.34.0 with a
deprecation warning, and on B200 and B300 it turns off the wider decode graphs.

Where the runtime image must already be on the machine (`INFERCRANE_KUBERNETES_IMAGE_CACHE_POLICY`
or `INFERCRANE_AWS_IMAGE_CACHE_POLICY` set to `required`: Kubernetes then uses
`imagePullPolicy: Never`, and EC2 refuses an image it has not pre-warmed), pre-pull the vLLM 0.34.0
image digests before the first 0.34.0 revision starts, and keep the 0.22.1 images while any revision
records 0.22.1. With `prefer`, a missing image is pulled at start and the first replica starts more
slowly.

Operators who run SkyPilot on RunPod also need a 0.34.0 build of `ghcr.io/infercrane/vllm-runpod`,
published with the `Runtime image` workflow (`vllm_version: 0.34.0`, `vllm_base_image:
vllm/vllm-openai@sha256:20fdb089454afbb324efa4110a2c025ff7b27cc1a086e07aa580b18df8ad1ce1`). Until it
is published and pinned, that path boots the `v0.34.0` tag.

## Move a deployment from SGLang 0.5.12 to 0.5.23

The control plane now pins SGLang 0.5.23. An SGLang revision stores its image, so every existing
revision keeps the 0.5.12 image on every later operation; the accelerator catalog lists the 0.5.12
images with `status: legacy`. A new revision that names no version gets 0.5.23, and one that names
an unpinned release (anything other than 0.5.23 or 0.5.12) is refused. Move each deployment with a
candidate revision on 0.5.23, measured against the running one; Stay optimized's engine-release
trigger proposes that run.

What changes for a setup moving to 0.5.23, from its v0.5.23 source:

- `--cuda-graph-max-bs` no longer exists; use `--cuda-graph-max-bs-decode` (and `-prefill`). A
  0.5.12 setup that sets it does not start on 0.5.23.
- `--disable-cuda-graph` and `--enable-dp-attention` still work with a deprecation warning; their
  replacements are `--cuda-graph-backend-decode=disabled` and `--cuda-graph-backend-prefill=disabled`,
  and `--attn-dp-size`.
- `--hicache-ratio` has no fixed default any more: unset, it is 2.0 in the default `cache` host
  memory mode.
- New revisions start with `--enable-metrics`, so InferCrane can read SGLang's engine metrics; the
  0.5.12 revisions keep the command they stored, without it.

The defaults the optimizer reads (KV cache dtype, quantization, schedule policy, speculation, batch
limits sized from GPU memory) are the same in both releases. Where the runtime image must already be
on the machine (`required` image cache policy), pre-pull the 0.5.23 digests first.

## Engine arguments, keys, and pod ingress

These engine checks apply from this release. Review each before upgrading the control plane and
the agent.

- **Engine arguments.** Extra vLLM and SGLang arguments must be in the reviewed set listed in
  [engine arguments](/deployment-spec#engine-arguments). A stored revision with an argument outside
  it is refused at its next rollout, scale, or replacement. Running replicas keep serving. List the
  `runtime.args` of active revisions first, and move any that fail with a candidate revision.
  `--trust-remote-code` and `--enable-custom-logit-processor` are refused on every runtime.
- **Engine keys.** Every SGLang server now requires the worker key, like vLLM. A running SGLang
  replica gets the key when it is next provisioned. Until then it serves without one, so roll out
  or replace each SGLang deployment after the upgrade. Health and metrics paths stay open.
- **Engine pod ingress on Kubernetes.** With the `deployment` workload API, the control plane does
  not start until `INFERCRANE_KUBERNETES_ENGINE_INGRESS` is set. Apply the updated
  `deploy/kubernetes/base/provider-rbac.yaml` first, then set the value
  ([who can reach engine pods](/integrations/kubernetes#who-can-reach-engine-pods)). Existing
  replicas get their policy when they are next provisioned.
- **Agent candidate runs on Kubernetes.** `infercrane agent run --executor kubernetes` does not
  start without `--engine-ingress` or `INFERCRANE_KUBERNETES_ENGINE_INGRESS`. Upgrade the Helm
  chart with the agent: it sets the flag to the agent's own pods and adds NetworkPolicy permissions
  to the agent's Role. Candidates started after the upgrade get the policy and, for SGLang, the
  key.

## Current release support boundary

<Warning>
The current release-candidate line does not yet publish a supported adjacent-release compatibility pair. A
mixed-version rolling upgrade is therefore **not supported**. Use the single-version maintenance
procedure below. Do not infer rolling compatibility solely from live protocol numbers.
</Warning>

## Safe release-candidate upgrade

Because no adjacent pair is currently qualified, a mixed-version rollout is **not a supported
release-candidate workflow. Use this maintenance procedure instead:

<Steps>
  <Step title="Converge or record active operations">
    ```bash
    infercrane system instances --output json
    infercrane deployments --output json
    infercrane orphans --output json
    ```

    Let ordinary operations finish when possible. For every operation that must cross the
    maintenance window, retain its ID and current status; do not cancel or recreate it merely to
    upgrade.
  </Step>

  <Step title="Back up and stop the old application replicas">
    ```bash
    scripts/backup-postgres.sh /secure/path/infercrane-before-upgrade.dump
    pg_restore --list /secure/path/infercrane-before-upgrade.dump >/dev/null
    ```

    Keep PostgreSQL and provider resources intact. Stop all old InferCrane application replicas so
    old and new binaries never mutate the database concurrently.
  </Step>

  <Step title="Start exactly one new-version replica">
    Start the candidate image against the preserved database. Its startup migration lock and ledger
    validation must complete before `/readyz` becomes healthy. If startup rejects the ledger or a
    migration fails, stop and follow the release-specific restore procedure; do not edit migration
    rows.
  </Step>

  <Step title="Verify recovery before adding replicas">
    ```bash
    infercrane system instances --output json
    infercrane deployments --output json
    infercrane orphans --output json
    infercrane operation watch OPERATION_ID --wait-timeout 15m
    ```

    Confirm the membership list contains only the intended version, incomplete operations resume
    under fresh leases, and external inventory has not duplicated. Add further same-version replicas
    only after these checks pass.
  </Step>
</Steps>

This procedure preserves durable operations but includes a control-plane maintenance window. A true
rolling upgrade becomes available only when release notes publish an exact old/new pair, overlapping
protocol intervals, and compatible schema behavior.

## Roll back without erasing evidence

If the new binary or migration fails, do not start the old binary against the migrated database and
do not delete provider resources. While the failed-version API can still serve read-only requests,
export its post-upgrade state as a separate evidence set:

```bash
mkdir -p /secure/path/infercrane-upgrade-evidence
infercrane system instances --output json \
  > /secure/path/infercrane-upgrade-evidence/instances.json
infercrane deployments --output json \
  > /secure/path/infercrane-upgrade-evidence/deployments.json
infercrane inbox --output json \
  > /secure/path/infercrane-upgrade-evidence/inbox.json
infercrane orphans --output json \
  > /secure/path/infercrane-upgrade-evidence/orphans.json
curl -fsS "$INFERCRANE_URL/api/v1/audit-events?limit=500" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY" \
  > /secure/path/infercrane-upgrade-evidence/audit-events.json
```

Then stop every InferCrane application replica and preserve the failed database:

```bash
scripts/backup-postgres.sh \
  /secure/path/infercrane-upgrade-evidence/failed-upgrade.dump
```

If the failed API cannot serve those reads, retain its database snapshot and collect what remains
available directly under the incident procedure; never fabricate the missing interval. Provision a
separate empty rollback database, point `INFERCRANE_DATABASE_URL` at it, set
`INFERCRANE_RESTORE_TARGET_DATABASE` to its exact database name, and restore the verified pre-upgrade
dump using [Backup and restore](/runbooks/backup-restore#recover-the-active-control-plane-after-a-failed-migration).

The restored database is authoritative only through the backup timestamp. Post-backup exports and
the failed-upgrade database remain immutable external audit evidence; the current release cannot
reattach those rows automatically to the restored ledger. Before enabling reconciliation, compare
the restored active revision and provider identities with the retained exports and read-only
provider inventory. Any provider mutation after the backup is a manual reconciliation boundary.

## Future rolling-upgrade contract

Every live replica registers its binary version and control protocol interval. Startup
fails before serving when that interval cannot overlap a live member. Inspect the actual window:

```bash
infercrane system instances --output json
```

For an adjacent-version rollout, first confirm the release notes declare overlapping protocol
intervals. Add one new replica, verify `/readyz` and the membership list, then remove old replicas one
at a time. An expired operation lease is reclaimed by another worker; the old fence token cannot
checkpoint or complete work. This is not permission to mix arbitrary schema versions: take a verified
backup first and follow the migration compatibility statement for both releases.

Rotate server or client certificates by temporarily trusting both CA generations, rolling clients,
then servers, and finally removing the old CA. InferCrane reads certificate files at process startup,
so each trust change requires a graceful rolling restart.

## Support window

Release candidates receive best-effort migration fixes and may still change with release notes.
For stable releases, security fixes target the latest minor and the immediately preceding minor;
provider/runtime compatibility remains scoped to the published matrix and immutable evidence.
