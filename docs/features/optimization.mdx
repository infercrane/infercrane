# Evidence-gated optimization

InferCrane separates proposing a configuration from proving it. The optimizer starts with reviewed
model metadata and locally or really qualified provider/runtime compatibility. When the exact
optional estimator toolchain is available, it uses AIConfigurator to reduce the candidate space.
Otherwise it creates conservative reviewed catalog candidates. Neither path contacts a control
plane or provisions paid capacity.

Check the optional estimator once:

```bash
infercrane optimize doctor
```

Install its exact compatible tuple in an isolated Python 3.11–3.13 environment:

```bash
python3.12 -m venv .infercrane/tools/aiconfigurator-0.11.0
.infercrane/tools/aiconfigurator-0.11.0/bin/python -m pip install \
  aiconfigurator==0.11.0 plotext==5.3.2

infercrane optimize doctor \
  --aiconfigurator-python .infercrane/tools/aiconfigurator-0.11.0/bin/python
```

The `plotext` pin is required: AIConfigurator `0.11.0` is not compatible with `plotext 6.0.0` even
though its published dependency range permits it. `optimize doctor` validates the complete tuple,
not just the top-level package.

```bash
infercrane optimize propose mistral-7b-instruct \
  --provider aws \
  --region eu-central-1 \
  --gpu L40S \
  --objective interactive \
  --profile interactive \
  --target-concurrency 8 \
  --workload-fingerprint sha256:CONTENT_FREE_REPLAY_DIGEST \
  --max-ttft-p95-ms 200 \
  --max-tpot-p95-ms 25 \
  --max-error-rate 0.01 \
  --min-goodput 4 \
  --max-hourly-cost 3 \
  --write-dir .infercrane/candidates/mistral-interactive
```

The default `--source auto` tries the pinned AIConfigurator adapter and visibly falls back to the
reviewed catalog when the optional tool is unavailable. Use `--source aiconfigurator` to require the
estimator or `--source catalog` for deterministic reviewed starting profiles only.

The result is a bounded candidate set. Each spec pins:

- the exact model revision;
- runtime engine and version;
- provider adapter, region, and accelerator;
- reviewed runtime arguments;
- compute mode, scale bounds, and routing strategy.

### Start from a public workload prior

When customer traffic is not available yet, choose one of InferCrane's immutable content-free
public priors. The default interactive lane is available directly to the optimizer:

```bash
infercrane optimize propose Qwen/Qwen3-8B \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --profile public-interactive
```

Automation clients can discover the same versioned inputs with `GET /api/v1/workload-profiles`.
Each result includes a ready-to-submit `benchmark_request`, its exact optimizer binding, source
provenance, and the evidence digest. Available lanes cover interactive, long-prefill, and
decode-heavy shapes.

The public trace chooses token-shape experiments only. It does not supply a customer arrival rate,
quality target, or production SLO, so InferCrane marks it `promotion_eligible: false`. Every
candidate requires a representative customer replay before qualification or promotion. Use the
remote Modal profiler in the [public trace PoC](/testing/chutes-public-workload-poc) only to
reproduce or update the embedded artifact; normal product use does not download or rescan the
dataset.

### Start with any pinned open-weight model

A model does not need to be in the reviewed catalog to enter the proof loop. Supply its repository,
immutable commit, intended GPU count, and one or more executable runtimes:

```bash
infercrane optimize propose acme/novel-open-model \
  --model-revision 0123456789abcdef0123456789abcdef01234567 \
  --provider runpod-pods \
  --gpu H100 --gpu-count 2 \
  --runtimes vllm,sglang \
  --objective throughput
```

By default, an uncataloged model gets only an empty-argument vLLM or SGLang baseline. It does
not infer architecture support, memory fit, tokenizer behavior, licensing, quantization, speculative
decoding, or kernel compatibility. Those gaps are listed as required evidence. The optional
AIConfigurator adapter may reduce this generic candidate space, but its output remains modeled and
unqualified. A mutable branch such as `main` is rejected; the revision must be a 40–64 character
hexadecimal commit.

### Search runtime recipes for a pinned model

Add `--search recipes` to generate bounded experiments on a pinned runtime image. InferCrane reads
the model's pinned `config.json` to detect preconditions, so the search does not depend on the model
name:

```bash
infercrane optimize propose acme/novel-open-model \
  --model-revision 0123456789abcdef0123456789abcdef01234567 \
  --provider runpod-pods --gpu H200 \
  --objective throughput \
  --search recipes --allow-model-metadata-network
```

Pass `--model-config config.json` instead to stay offline. Without either, speculative arms are
skipped and the proposal says why. API clients send `search`, `model_features`, and
`model_config_digest` on `POST /api/v1/optimization/proposals`.

Each proposal starts with an untuned control on the same image, so every arm has a like-for-like
comparison even under a small `--max-candidates`. Arms then isolate one mechanism or combine two:

| Mechanism | Generated when |
|---|---|
| Speculative decoding (NEXTN) | The pinned config declares a native prediction head |
| Bounded CUDA graph capture | Always, on a supported accelerator |
| Chunked prefill | The workload's input tokens reach the arm's chunk size |
| FP8 KV cache | Always; requires semantic quality evidence |

The first search space covers SGLang 0.5.20 on H100, H200, and B200 through RunPod Pods. Anywhere
else the proposal keeps its existing candidates and explains why no experiments were generated.

<Warning>
  Arm order is exploration priority, not predicted performance. Each arm's flags ran on this image
  with another model, which proves only that the flags exist. Every arm is `proposed-unmeasured`
  until a campaign measures it against the control; a wrong or missing config feature costs at most
  one failed experiment inside the approved spend limit.
</Warning>

The command refuses to overwrite a non-empty candidate directory. Use `--output json` to archive the
input digest, source, compatibility evidence, required evidence, and limitations with the specs.

<Warning>
  A proposal is not a benchmark result or recommendation. AIConfigurator rows are marked `modeled`
  and `proposed-modeled-unqualified`; catalog rows are marked `unmeasured` and
  `proposed-unmeasured`. InferCrane never presents an estimate as measured or qualified evidence.
</Warning>

## The simple and advanced paths

The common path needs an objective, not a collection of runtime flags:

```bash
infercrane optimize propose Qwen/Qwen3-8B \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive \
  --max-ttft-p95-ms 200 \
  --max-error-rate 0.01 \
  --min-goodput 4 \
  --max-hourly-cost 3
```

Advanced users can bind the search to an observed content-free Replay digest, which campaigns then
replay as their load, choose runtimes,
control the workload profile and concurrency, require the estimator, and inspect the complete JSON
provenance. Provider credentials are not passed to the estimator. Model metadata network access is
off by default and requires `--allow-model-metadata-network`.

## Create a durable campaign

The authenticated console exposes the same boundaries under **Optimize**:

1. choose a reviewed model, objective, infrastructure target, and optional SLO;
2. review the candidate boundary without allocating provider resources;
3. create an immutable campaign;
4. grant a hard spend cap with a maximum 24-hour expiry;
5. follow durable execution from Activity, even after closing the browser;
6. inspect modeled and measured evidence separately;
7. explicitly publish a qualified new endpoint or promote a Release Guard-approved evolution.

Cancellation is durable too: it persists the decision and links to the cleanup operation. The
console never treats a proposed endpoint name as published until activation completes.

A campaign keeps the warnings its proposal recorded, such as skipped speculative-decoding arms or
the reminder that every recipe arm is unmeasured. Campaign responses, including
`GET /api/v1/optimization/campaigns/{id}`, return them as `warnings` so the campaign page shows the
same boundary as the review step. An empty list means the proposal recorded none; the field is absent
only when the stored proposal cannot be read. `infercrane optimize inspect`, `results`, `approve`,
`activate`, and `cancel` print a **Proposal warnings** block after the campaign header when there
is at least one warning, and `--output json` keeps the field exactly as returned. Warnings explain
what was skipped or left unproven. They are not performance evidence.

Use `propose` for a completely offline preview. Use `create` to persist the same immutable proposal
without provisioning anything:

```bash
infercrane optimize create llama-3.1-8b-instruct \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --max-candidates 3

infercrane optimize inspect CAMPAIGN_ID
infercrane optimize approve CAMPAIGN_ID --max-cost-usd 20 --expires-in 1h
infercrane operation watch OPERATION_ID
infercrane optimize results CAMPAIGN_ID
infercrane optimize activate CAMPAIGN_ID --candidate CANDIDATE_ID
infercrane operation watch ACTIVATION_OPERATION_ID
```

To follow a campaign live, run `infercrane optimize watch CAMPAIGN_ID`. It shows, in plain words,
where each setup is (starting a server, measuring against your current setup, checking answer
quality), what was measured (throughput, p95 time to first token, p95 latency, and cost per million
tokens when the price is sourced), how each setup compared with the current one including the
measurement noise floor, and the decision with the exact `activate` command when a setup qualifies.
It only reads the control API; `--once` prints one plain snapshot for scripts and logs.

That default creates a `new_endpoint` campaign. To optimize a candidate revision for an endpoint
that already serves production, bind the campaign to its stable deployment identity:

```bash
infercrane optimize create llama-3.1-8b-instruct \
  --provider aws --region eu-central-1 --gpu L40S \
  --objective interactive --max-candidates 3 \
  --target-deployment llama-production
```

InferCrane keeps these proof paths distinct. A new endpoint has no production baseline, so a winning
candidate may become `qualified` after measured performance, sourced cost, and signed semantic
quality evidence. It then waits for explicit human activation. An `evolve_endpoint` campaign must
create a candidate revision against the named deployment, compare it with active production through
Release Guard, and wait for explicit human promotion. InferCrane never invents a baseline for a new
endpoint and never lets an evolution bypass Release Guard.

Activation is itself a durable, idempotent operation. A new-endpoint campaign may activate only a
`qualified` candidate. It atomically publishes the endpoint name from the immutable proposal and
binds it to the selected isolated candidate deployment; an existing alias is never silently rebound.
The activation operation waits until the request-path route generation is published. An evolution
campaign may promote only a `guard_passed` candidate and delegates the traffic mutation to the
normal guarded rollout workflow. Approval expiry is checked before mutation, while a retry after a
completed activation remains a successful no-op.

Approval first verifies every candidate against a fresh sourced price for its exact cloud, region,
GPU, and maximum replica count. It then records a bounded authority window and queues one durable
execution operation. The worker composes the existing deployment/rollout lifecycle, measures each
exact candidate revision directly with AIPerf against the campaign control, adopts revision-bound
signed quality evidence, ranks persisted results, evaluates Release Guard for evolution campaigns, and
cleans rejected candidates. It never promotes automatically.

The execution capability is fail-closed. The control plane must find AIPerf and must have an exact
price snapshot valid for the entire approval window. Configure price evidence before approving:

```bash
export INFERCRANE_OPTIMIZATION_PRICES_JSON='[
  {
    "cloud":"aws",
    "region":"eu-central-1",
    "gpu":"L40S",
    "replicas":2,
    "hourly_usd":3.72,
    "currency":"USD",
    "source":"aws-price-list/2026-08-24",
    "observed_at":"2026-08-24T18:00:00Z",
    "valid_until":"2026-08-25T18:00:00Z"
  }
]'
```

The rate is the total hourly cost of that exact maximum-replica tuple. A missing tuple, expired
source window, absent AIPerf binary, or approval below the worst-case execution cost is rejected
before provider mutation. Operators must refresh price evidence rather than treating this static
example as current pricing.

A row like the one above is advisory: it can rank plans, but it cannot authorize spend, because a
hand-entered price is not a provider quote. Execution needs a fresh quote from a reviewed provider
price collector, or, for capacity you own or contract, an explicit rate card on a `kubernetes` row:

```bash
export INFERCRANE_OPTIMIZATION_PRICES_JSON='[
  {
    "cloud":"kubernetes",
    "gpu":"H100",
    "replicas":1,
    "hourly_usd":2.40,
    "currency":"USD",
    "source":"operator-rate-card/2026-11",
    "authority":"account_contract",
    "cost_scope":"instance_total",
    "observed_at":"2026-11-12T00:00:00Z",
    "valid_until":"2026-12-12T00:00:00Z"
  }
]'
```

`authority: account_contract` declares that you guarantee this complete hourly rate until
`valid_until`; it must cover the whole approval window. It is accepted only for `cloud: kubernetes`
with `cost_scope: instance_total`. `provider_api` and `measured_invoice` authority come only from
reviewed collectors and are rejected in this variable.

Automation clients can request the same non-mutating candidate set with
`POST /api/v1/optimization/proposals`. This endpoint performs no provider mutation and makes no
performance claim. Pass the returned immutable proposal to
`POST /api/v1/optimization/campaigns` when you are ready to persist the review boundary. Paid
execution still requires the separate approval endpoint.

The restart-safe execution path is locally qualified for lost child-operation responses,
cancellation, expired authority, evidence identity, cleanup, and the human promotion boundary.
Canceling a campaign queues durable cleanup even when its execution operation already finished.
Closing the CLI does not stop the control-plane operation; reattach with `infercrane operation
watch`. A qualified candidate keeps that parent operation in a bounded waiting state. If explicit
activation or promotion does not happen before authority expires, InferCrane marks the candidate
failed and cleans its resources rather than allowing an unbounded GPU bill.

Execution uses a measured-evidence barrier: all viable candidates reach AIPerf measurement and
revision-bound quality validation before ranking begins. Candidates are provisioned and measured
one at a time, control first. A candidate that reaches the barrier waits there while the next one
is provisioned, so a deployment that converges between execution attempts is recorded on the next
attempt. A winner stays in the ranking after it becomes `qualified` (or `guarding` for an
evolution), so ranking the candidates after it reproduces the same evaluation. Inference Lab then
compares only the exact same workload shape and the exact deployed model artifact
(`repository@revision`), even when the campaign was created from a catalog name. Candidates that serve different artifacts cannot share
one ranking and fail closed. Proposal order cannot choose the winner. Missing sourced cost, mismatched
workloads, or incomplete metrics produce `inconclusive`; explicit SLO or cost violations produce
`rejected`. For evolution campaigns, the selected candidate still has to pass
active-versus-candidate Release Guard and wait for human promotion. The persisted campaign links
benchmark, quality, Lab, and, where a real baseline exists, Release Guard evidence separately.

### How a campaign measures candidates

A single benchmark run misjudges the changes optimization cares about most. Prefix caching has no
effect without shared prefixes, a small gain can be run-to-run noise, and a candidate measured an hour
after another can win on drift alone. Campaigns therefore measure every candidate the same way.

**Load.** A campaign bound to a customer Replay digest (`workload_source: customer_observed`) replays
that trace. InferCrane verifies the stored trace against its digest, then renders each generation
request's input and output token counts as an AIPerf `mooncake_trace`. Requests that share system
messages share a leading 512-token prompt block, and a later session turn at least as long as the
previous one reuses that prompt's whole blocks, so prefix and session structure survive. One pass over
the trace, capped at its first 2,000 generation requests in arrival order, is one run. If the bound
trace is missing, malformed, or does not match its digest, every candidate fails with
`optimization_replay_unavailable` or `optimization_replay_invalid` before any provider mutation,
instead of silently measuring synthetic load. Campaigns without a bound trace send their versioned
synthetic profile.

The rendering records what it preserved and what it did not in the workload's `replay` identity.
Prompt content is synthetic because Replay never stores it, so MoE expert routing and speculative
acceptance on customer content remain unknown. Arrival timing is not replayed: load is closed-loop at
the profile concurrency. Replay records which requests share system messages but not how long those
messages are, so one shared block is assumed. Tool pauses, parent-session links, and reuse of earlier
assistant output are not modeled.

**Runs.** Each server receives warmup requests (twice the concurrency, between 16 and 256) before
measurement, and each arm runs three independent AIPerf invocations. Every invocation gets its own
seed and, for a replay, its own prompt-block namespace, drawn from a random base for each
measurement. A server is therefore not answered from prefix-cache entries that an earlier run
created, including when the control is measured again inside another candidate's measurement or a
measurement is retried. The base is kept as `measured.invocation_base`. The candidate's stored metrics
are the mean of its three runs, with Student-t 95% intervals in `confidence_95`.

**Control.** The control is the proposal's starting point: the untuned control arm when the proposal
includes one, otherwise the highest-ranked compatible candidate. It is measured first. While its deployment is
serving, every other candidate is measured interleaved with it, as control, candidate, control,
candidate, control, candidate, control. The control and candidate share a time window, not a GPU, so
differences between their nodes are not removed. Control runs that fail, or whose output throughput
differs by more than 5% between adjacent runs, make that comparison invalid; the candidate's own
measurement is kept, and its result against the control is unknown. A failure to look the control up
is retried rather than recorded as a measurement without one.

**Noise floor.** For each metric the noise floor is the larger of the control-to-control spread and
the candidate's 95% interval half-width, both relative to their means. A candidate whose change is
inside it shows no measurable difference. The workload's `measured.comparison` records the control
mean, spread, candidate mean, delta, floor, and decision for throughput, latency, and goodput.

**Ranking.** Inference Lab still orders the exact-workload candidates that meet the constraints. The
campaign selects the best of them that measurably beats the control on the objective metric. If none
does, the control is kept. A candidate inside the noise floor, or never shown to beat the control, is
superseded with `measured_no_measurable_difference`. If the control itself does not meet the
constraints, Lab's choice stands and no gain over the control is claimed. Cost efficiency compares output
throughput per sourced hourly cost. A candidate that could not be measured beside a serving control is
compared through both arms' 95% intervals, which is weaker evidence because the arms ran at
different times; overlapping intervals are no measurable difference. The persisted Lab evaluation
records each candidate's control decision, its basis, and the final selection.

**Runtime metrics.** When a candidate's runtime contract declares a `/metrics` path, AIPerf scrapes it
during each run, and InferCrane keeps a bounded summary of cache use, prefix-cache hits, preemption,
queueing, and speculative acceptance. Runtimes without a declared path record no runtime metrics, and
GPU telemetry is `not_collected`.

This method sends nine AIPerf invocations per non-control candidate instead of one, so measurement
takes several times longer. The approval window must cover it. Campaign ranking does not use the
[multi-lane Pareto evaluator](#multi-lane-optimization-evidence): that evaluator needs TTFT and ITL
limits and several concurrency lanes, and a campaign measures one lane and may declare no SLO.

## Generate a custom kernel

A custom kernel is a last resort, never a default. Monitoring can suggest which phase to profile
(`profile_phase` on the optimization readiness response), but only an exact target-GPU profile and
the Amdahl gate can open the kernel path, and existing implementations are tried first.

Start a run from a complete Accelerator Lab request, which carries its own spend cap and 24-hour
expiry:

```bash
infercrane optimize kernel-run --file request.json
```

When no approved source exists and the request allows generation, the worker runs
`infercrane-kernel-adapter`:

1. Optional literature search finds recent public research for the measured operator.
2. A language model with no tools returns one source file for a human-reviewed operator contract.
3. A static screen rejects obvious non-kernels before any GPU time is spent.
4. The draft runs in a no-network container against a hidden test suite and the runtime's own kernel.
5. `kernelresearch` keeps it only if every stage passes and it is materially faster.
6. An implausibly large speedup must repeat on fresh inputs before it can be kept.

The hidden suite checks shape sweeps, value distributions that defeat hardcoded bypasses, dirty
memory, determinism, and bitwise batch invariance. A retained kernel still has to pass the Brezel
source build, target-GPU qualification, full serving replay, and explicit human promotion. A search
that keeps nothing is recorded as `kernel_research_no_winner`, with every attempt preserved.

The adapter profiles and qualifies on one GPU host with Docker and AIPerf:

- **Profile** captures a torch trace of the requested phase, then maps GPU kernels to reviewed
  operator families. Kernels it cannot classify stay in the denominator and never become hotspots.
- **Qualify** re-runs the hidden suite on the built bytes, then replays your workload as control,
  candidate, control on the same GPU. More than 5% control drift invalidates the run. Deterministic
  prompts must match the control byte for byte.

Serving containers run offline on an internal Docker network, with a read-only model cache and no
credentials. Only the model download step has internet access. A candidate arm must prove the
generated kernel was called, because otherwise the result would measure the unmodified runtime.

Each operator pack names the exact runtime versions its serving integration was reviewed against,
and the adapter refuses any other version before it spends on generation or GPU time. The
residual-RMSNorm pack supports vLLM 0.22.1 only. It plugs into vLLM IR, which vLLM has deprecated,
and vLLM 0.34.0 removes the setting it uses, so a vLLM 0.34 or later pin needs a new
CustomOp-based integration first.

Set `max_candidates` to at least 2. The planner ranks by device time, and the largest hotspot is
usually GEMM, which has no reviewed pack yet and is reported as a failed generation.

| Adapter setting | Purpose |
|---|---|
| `INFERCRANE_KERNEL_MODEL_URL`, `INFERCRANE_KERNEL_MODEL`, `INFERCRANE_KERNEL_MODEL_TOKEN_FILE` | Any OpenAI-compatible endpoint, including one inside the customer boundary |
| `INFERCRANE_KERNEL_MODEL_INPUT_USD_PER_M`, `INFERCRANE_KERNEL_MODEL_OUTPUT_USD_PER_M`, `INFERCRANE_KERNEL_GPU_HOURLY_USD` | Prices used to enforce the spend ceiling |
| `INFERCRANE_KERNEL_PACK_DIR`, `INFERCRANE_KERNEL_EVALUATOR`, `INFERCRANE_KERNEL_EVAL_IMAGE`, `INFERCRANE_KERNEL_EVALUATOR_TIMEOUT` | Reviewed operator packs and the isolated launcher |
| `INFERCRANE_KERNEL_CPU_SCREEN`, `INFERCRANE_KERNEL_CPU_SCREEN_IMAGE` | Optional CPU correctness screen that rejects wrong drafts before GPU evaluation |
| `INFERCRANE_KERNEL_LITERATURE` | `off` by default, `arxiv`, or an absolute path to a curated reference file |
| `INFERCRANE_KERNEL_RUNTIMES_FILE`, `INFERCRANE_KERNEL_MODEL_CACHE`, `INFERCRANE_KERNEL_WORK_DIR`, `INFERCRANE_KERNEL_AIPERF` | Reviewed runtime launch data and host paths for profiling and qualification |
| `INFERCRANE_KERNEL_REPLAY_DIR`, `INFERCRANE_KERNEL_REPLAY_DATASET_TYPE` | Local files named by content digest for the workload replay and quality suite |
| `INFERCRANE_KERNEL_HF_TOKEN_FILE` | Optional Hub token, used only by the model download step |
| `INFERCRANE_ACCELERATOR_WORKER_URL`, `INFERCRANE_ACCELERATOR_WORKER_TOKEN_FILE` | Artifact store for retained source |

Research abstracts are shown to the model as untrusted reference data and recorded as provenance.
They are never performance evidence. The first reviewed pack covers residual-add + RMSNorm in
Triton; other operators fail closed until a pack exists.

## Plan an optimized artifact

Builders run outside InferCrane. The common path produces a strict immutable plan:

```bash
infercrane artifact optimize plan BASE_ARTIFACT_ID \
  --preset fp8 \
  --tool-version 0.12.0 \
  --builder-image-digest sha256:BUILDER_DIGEST \
  --calibration-digest sha256:CONTENT_FREE_DATASET_DIGEST \
  --license-spdx Apache-2.0
```

Available plan presets cover FP8, AWQ, GPTQ, NVIDIA-specific NVFP4, EAGLE-3, MTP, and DFlash. There
is no TensorRT engine preset: TensorRT-LLM removed its engine backend and `trtllm-build`, and its
PyTorch backend loads checkpoints such as the FP8 and NVFP4 outputs directly. An engine built by an
earlier TensorRT-LLM release can still be recorded with `--plan-file`. A preset is not a
compatibility or speed claim. Every plan requires an exact
tool version, digest-pinned builder, hardware constraints, immutable output attestation, exact
candidate binding, and passing semantic quality evidence before qualification. Advanced users can
provide the complete JSON plan with `--plan-file`.

## Propose, prove, release

Use the generated files through the existing lifecycle:

```bash
# Review without mutation.
infercrane plan .infercrane/candidates/mistral-interactive/01-*.yaml

# Deploy one explicitly selected candidate.
infercrane deploy .infercrane/candidates/mistral-interactive/01-*.yaml \
  --idempotency-key mistral-interactive-candidate-1 \
  --wait

# Measure the same workload shape.
infercrane benchmark DEPLOYMENT --profile interactive

# Compare only persisted, comparable measurements.
infercrane lab 'mistralai/Mistral-7B-Instruct-v0.3@IMMUTABLE_COMMIT' \
  --objective interactive \
  --profile interactive \
  --max-ttft-p95-ms 200ms \
  --max-tpot-p95-ms 25ms \
  --max-error-rate 0.01 \
  --min-goodput 4 \
  --max-hourly-cost 3

# Apply normal candidate and Release Guard policy before promotion.
infercrane rollout inspect DEPLOYMENT
```

When model precision or model artifacts differ, attach signed semantic evaluation evidence before
promotion. When cost is part of the objective, attach sourced, dated cost evidence. Only an exact
model, runtime, accelerator, provider, and canonical workload result supports a measured recipe.

## Seed candidates from NVIDIA Model Optimizer

InferCrane can discover reviewed NVIDIA Model Optimizer checkpoints as provenance-bound candidate
seeds. Each seed pins the publisher repository, immutable revision, artifact identity, algorithm,
precision, and source URL before it enters the search space. The console shows that provenance and
the remaining qualification gates.

These checkpoints are **unmeasured candidates**, not InferCrane performance claims. InferCrane does
not claim that it transformed the publisher artifact or that the artifact is faster on a target
GPU. Exact runtime and accelerator compatibility, correctness, semantic quality, workload
performance, and cost evidence remain mandatory before Release Guard can accept a candidate. A
publisher checkpoint that fails any gate is retained as negative evidence rather than promoted.

## What the first planner knows

The first source composes:

- [reviewed model recipes](/features/model-catalog);
- the executable [integration compatibility inventory](/compatibility);
- reviewed vLLM configuration profiles for balanced, interactive, and throughput workloads;
- exact runtime versions and provider adapters.

Accelerator matching uses concrete hardware identity. Generic Kubernetes resource names such as
`nvidia.com/gpu` are capacity resources, not GPU models, and cannot qualify a mechanism. Explicit
aliases such as `NVIDIA-L40S` normalize to the exact hardware family. Dynamo candidates compile to
one InferCrane-owned parent graph with outer autoscaling fixed at one; Dynamo owns its internal
workers. This prevents two controllers from scaling the same serving graph.

It does not infer that a model fits an accelerator. It does not automatically enable quantization,
speculative decoding, LMCache, disaggregated serving, FlashInfer, or TensorRT-LLM. Those mechanisms
are version- and workload-specific and require their own compatibility and qualification evidence.
Use `--include-simulated` only for development exploration; simulated candidates are excluded by
default.

## Upstream composition boundaries

InferCrane will reuse upstream execution and optimization work behind replaceable adapters:

| Upstream | InferCrane boundary | Current status |
|---|---|---|
| vLLM | Runtime execution, continuous batching, attention, prefix caching, and qualified engine flags | Active runtime; reviewed starting profiles are locally qualified |
| SGLang | Alternative runtime and prefix-aware execution | The pinned 0.5.12 runtime passed real AWS L40S lifecycle checks with Qwen3-8B and five-request AIPerf samples; that is not performance qualification. Qwen3-0.6B on SGLang 0.5.10.post1 on H100 is separate negative compatibility evidence. SGLang 0.5.20 candidates for any pinned model stay unmeasured until a campaign measures them |
| AIConfigurator | GPU-free modeled candidate reduction | Active optional adapter pinned to `0.11.0` plus `plotext 5.3.2`; Linux x86_64 real-package contract verified |
| AISimulate | GPU-free simulation and recommendation source | Not integrated; adoption requires a stable package, schema, support, parity, and rollback contract |
| LLM Compressor / ModelOpt | Produce immutable quantized artifacts | Replaceable external-builder plans and provenance are local-qualified; transformation and GPU compatibility remain external qualification |
| vLLM Speculators | Model-specific EAGLE, MTP, DFlash, and related speculative candidates | Replaceable artifact plans and exact verifier provenance are local-qualified; acceptance rate and output correctness require real measurement |
| LMCache | KV reuse and offload for qualified repeated-prefix workloads | Registered cache composition and exact capability boundary; executable lifecycle remains fail-closed |
| Dynamo / NIXL | KV-aware routing and prefill/decode serving graph | Experimental Kubernetes adapter; real GPU/NIXL evidence required |
| TensorRT-LLM | Narrow optimized runtime for supported model/GPU tuples | Upstream removed the engine backend; engine provenance remains only for engines built by an earlier release. Runtime execution remains unsupported until an exact tuple is qualified |
| llm-d / AIBrix | Kubernetes routing, scheduling, and heterogeneous fleet patterns | Registered single-owner composition boundaries; no executable lifecycle support claim |

The durable rule is: **the optimizer proposes; InferCrane proves**. Candidate sources, builders, and
execution systems remain replaceable. Modeled results cannot satisfy a measured gate, provider
mutation requires bounded approval, optimized artifacts retain immutable provenance, and activation
or promotion remains an explicit action.

## Multi-lane optimization evidence

External optimization workers can emit the content-free
`infercrane.dev/optimization-evidence/v1` contract defined in
`schemas/optimization-evidence-v1.schema.json`.
It keeps three benchmark evidence levels distinct:

- `screening` is inexpensive candidate-search evidence (at least 12 requests per lane);
- `qualification` requires at least 100 requests, two independent runs, and 300 seconds per lane;
- `public` requires at least 300 requests, three independent runs, and 600 seconds per lane, and is
  reserved for independently repeated baseline-versus-final receipts.

These schema floors prevent evidence relabeling; a workload policy may require larger samples. They
do not retroactively promote the existing 12-request Qwen measurements, which remain screening
evidence.

A lane may also record `input_tokens`, `output_tokens`, and a typed `economics` projection. These
fields are validated context from the producer: they never affect qualification or scoring, and
`economics` is not sourced cost evidence. Unknown fields are still rejected.

Qwen3.8-27B-FP8 has a provisional H200 catalog profile copied from the paired Modal screening recipe.
Proposing it returns a `proposed-unmeasured` candidate; each target still needs its own evidence.

Every campaign pins one model, hardware tuple, and workload digest. Every candidate adds an
immutable serving-recipe digest and every required concurrency lane. Each
lane records aggregate output throughput, request throughput, SLO goodput in requests/second, and
SLO-qualified output tokens/second as separate metrics. InferCrane applies error, prompt-integrity,
quality, sample-size, TTFT, ITL, and SLO-attainment gates to every lane before calculating a score.
An ineligible candidate has no score, even when another lane has the highest raw throughput.

Evaluate a secret-free document locally without provisioning infrastructure:

```bash
infercrane optimize evidence evaluate \
  --file optimization-evidence.json \
  --output json
```

The result pins the evaluator algorithm, input digest, policy/version, rejection reasons, Pareto
set, and selected candidate. The supported policies cover qualified output throughput, SLO request
goodput, qualified throughput per dollar, minimum COGS under the SLO, and latency-sensitive serving.

FastPath provisional handoffs have a separate inspection boundary:

```bash
infercrane optimize evidence inspect-fastpath \
  --file artifacts/handoff/MODEL/manifest.json
```

Inspection validates immutable model/tokenizer revisions, tokenizer and chat-template hashes,
runtime commit, digest-pinned image, CUDA and hardware identity, launch revision, evidence level,
quality declaration, and every workload lane. The result remains `external_unverified` inside
InferCrane until the control plane binds it to its own immutable revision and passing signed quality
evidence. A community source remains recorded even after InferCrane independently reproduces its
recipe; community measurements never become qualification evidence.

## Benchmarks and competitor comparisons

AIConfigurator estimates help decide what to test; they are not publishable performance claims.
Use the [competitive benchmark methodology](/testing/competitive-benchmark-methodology) to compare
InferCrane-managed serving with Baseten, Fireworks, or another provider on the same model artifact,
precision, request dataset, protocol, concurrency, region class, warm/cold definition, and output
token accounting. If an external provider does not expose the same artifact or configuration, label
the result as a product comparison rather than an engine comparison.
