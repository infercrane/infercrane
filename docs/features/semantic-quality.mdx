# Healthy infrastructure is not enough

A candidate may be ready, fast, and error-free while producing worse answers. InferCrane accepts
aggregate evidence from a customer-owned evaluation suite, verifies its signature and revision
identity, and lets Release Guard enforce explicit score thresholds. Optimization runs also produce
their own evidence with a [built-in answer check](#built-in-answer-check), so a run reaches a
decision without you signing anything.

InferCrane does not store prompts or generated outputs in this evidence format and does not choose an
LLM judge for you.

## Built-in answer check

When an optimization campaign measures a candidate and finds no evidence you attached for its exact
revision, the worker checks the candidate's answers itself. It sends the same prompts to the
candidate and to a reference, the campaign control or, for an evolve-endpoint campaign, the target's
active revision, and scores how closely each candidate answer matches the reference answer.
[How a campaign checks answers](/features/optimization#how-a-campaign-checks-answers) describes the
steps.

| Property | Built-in answer check |
|---|---|
| Prompts | `infercrane-default` version 1: 24 short prompts with short answers (arithmetic, facts, extraction, code, translation, summaries), pinned by SHA-256 digest in the product. Print it with `infercrane evaluation set default`. |
| Requests | One prompt at a time, `temperature 0`, `top_p 1`, seed 17, at most 64 output tokens unless the eval set sets `max_tokens`. Each request also sends `chat_template_kwargs: {"enable_thinking": false}`, so hybrid reasoning models such as Qwen3 and GLM answer directly; chat templates without that switch ignore it. A case from your eval set also sends its conversation, `tools`, and `tool_choice`. Sent directly to one ready replica of each exact revision. |
| Score per prompt | Token-level F1 of the candidate's answer against the reference's answer, ignoring case, punctuation, and reasoning: `<think>` blocks, and any text before a `</think>` that the chat template opened in the prompt. A case that declares tools is scored on its tool calls; see [Tool calls](#tool-calls). |
| Answers with no text | If the reference gives no answer text and makes no tool call to any prompt within the token limit, for example because a reasoning model was cut off mid-reasoning or its server returned only reasoning, the check stops without a score. The candidate ends `inconclusive` with `quality_reference_unanswered`. Use an eval set with a larger `max_tokens`. |
| Score | The mean over prompts. The reference's own row records 1. |
| Verdict | `PASS` for a drop up to 5%, `WATCH` above 5% and up to 10%, `BLOCK` above 10%, using the same classifier as Release Guard. A candidate that breaks a tool call the reference made correctly is `BLOCK` whatever its score. `BLOCK` records `passed: false`. |
| Evidence | Evaluator `infercrane-builtin` version 3, suite version `VERSION@sha256:DIGEST`, a paired score per prompt, the tool-call score in `distribution.tool_calls` when the eval set has tool cases, a precision change's [divergence](#divergence-of-a-precision-change) in `distribution.divergence`, and an artifact digest that commits to a hash of every answer and call. Signed with the control plane's key. Evidence from version 2 is not compared with version 3. |
| Provenance | `source: infercrane` and the reference's revision ID. Only the worker writes these rows; the attach API always records `source: customer` and refuses the evaluator name `infercrane-builtin`. |

Answers are compared in memory and discarded. Prompts of the built-in suite live in the product;
nothing about your traffic is sent.

Evidence you attach for the candidate's exact revision always wins over the built-in check. A
campaign created with `--quality-check customer_evidence` skips the built-in check and waits for your
evidence. The run page and `infercrane optimize inspect` then show the exact `evaluation ingest`
command for each waiting candidate.

The answer check measures agreement with your current setup on general prompts. It is not a task
accuracy benchmark. Use an eval set of your own prompts, or your own evaluator, for that.

### Use your own test set

An eval set replaces the built-in prompts with your own cases. Schema v1 has the same format as the
built-in suite: single prompts.

```json eval-set.json
{
  "schema": "infercrane.dev/quality-eval-set/v1",
  "name": "support-answers",
  "version": "3",
  "max_tokens": 128,
  "prompts": [
    {"id": "refund-window", "prompt": "How many days do customers have to request a refund? Answer in one sentence."},
    {"id": "reset-password", "system": "You are a support agent.", "prompt": "How do I reset my password?"}
  ]
}
```

Schema v2 accepts everything v1 does. A case may also hold a conversation in `messages` instead of
`prompt`, and declare OpenAI function `tools` with an optional `tool_choice`:

```json eval-set.json
{
  "schema": "infercrane.dev/quality-eval-set/v2",
  "name": "support-agent",
  "version": "1",
  "max_tokens": 128,
  "prompts": [
    {"id": "refund-window", "prompt": "How many days do customers have to request a refund?"},
    {
      "id": "order-status",
      "messages": [
        {"role": "system", "content": "Use the tools to look up orders."},
        {"role": "user", "content": "Where is my order A-10442?"}
      ],
      "tools": [{
        "type": "function",
        "function": {
          "name": "get_order",
          "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "string", "pattern": "^A-[0-9]{5}$"}},
            "required": ["order_id"],
            "additionalProperties": false
          }
        }
      }],
      "tool_choice": "auto"
    }
  ]
}
```

`examples/evaluation/eval-set-tools.json` has a fuller example, with a conversation that carries an
earlier call and its result.

Up to 200 cases and 512 KiB (a [task set](#task-sets) up to 1,000 cases and 1 MiB). Case IDs are 1 to 64 letters, digits, dots, dashes, or underscores and
must be unique. A case sets either `prompt` (with an optional `system`) or `messages`. A conversation
holds 1 to 64 turns with roles `system`, `user`, `assistant`, and `tool`, and ends with a user or tool
turn. An assistant turn may carry earlier `tool_calls` to declared functions, and each tool turn
answers one of them by `tool_call_id`. Each case declares 1 to 64 functions; a function's
`parameters` must be a JSON Schema (draft-07 or 2020-12) without remote `$ref`, and `tool_choice` is
`auto`, `none`, `required`, or a declared function. Unknown fields are rejected.

Expected answers are accepted only in a **graded** set, which names its `grading` (`exact_match`,
`token_f1`, or `answer_line` for a [task set](#task-sets)) and gives every prompt 1 to 8 `expected` answers; an ungraded set with expected answers is
refused, because the ordinary check scores agreement with the reference's answers, not stored answers.
A graded set scores answer text, so its cases may hold conversations but not tools. A graded set is
what a [migration Proof](/features/migration) scores both the closed API and each setup against
(evaluator `infercrane-graded`), compared with a paired bootstrap into a signed PASS, BLOCK, or
UNKNOWN verdict. The evaluator names `infercrane-builtin`, `infercrane-graded`, and `infercrane-task`
are reserved: your own evidence cannot claim them.

#### Task sets

A word-overlap check cannot tell a real loss from noise once answers are long: two servers of the
same setup under load wrote different texts for most prompts. A **task set** scores whether answers
are right instead. Set `grading` to `answer_line` and give every prompt one `expected` answer: a number,
or a letter from `A` to `D`. Each answer is read from its last `Answer:` line: the first number after
it, or the first of `A` to `D` that stands alone after it. A text without that line counts its last
number for a number item and is wrong for a letter item; an empty answer is wrong.

When the run's eval set is a task set, the check asks the reference and the candidate every item and
scores both against the gold answers (evaluator `infercrane-task`). The two are compared item by item:
the mean of the per-item differences, with a 95% interval of 1.96 standard errors.

| Interval of the difference | Verdict | Setup |
|---|---|---|
| Above zero | better | passes |
| Inside ±3 points | no measurable difference | passes |
| Below zero | worse | blocked |
| Reaches past ±3 points without excluding zero | not settled | blocked: the items cannot show it is safe |

A setup that changes answers by design is read by a stricter rule. That is a setup that serves
other weights or numeric precision (another checkpoint, `--quantization`, `--kv-cache-dtype`,
`--dtype`), or one a technique made whose manifest declares `changes_answers`. Its answers count
as held only when the lower end of the 95% interval lies above −1 point:

| Interval of the difference | Verdict | Setup |
|---|---|---|
| Below zero | worse | blocked |
| Above zero | better | passes |
| Lower end above −1 point | answers held within 1 point | passes |
| Anything else | answers not shown to hold within 1 point | not promoted, whatever its speed |

A setup whose answers were not shown to hold ends inconclusive (`quality_answers_not_shown_held`),
never "no measurable difference", and the report says what it gained and why that is not enough,
for example "faster by 62% (output throughput), but its answers were not shown to hold within 1
point on one server each". Its evidence records the rule (`task_rule`), the verdict
(`task_verdict`), and how many servers of each setup answered (`task_servers`). One pair of
servers answering 1,000 items gives an interval about ±1.5 points wide, so a loss near a point
usually cannot be shown either way on one pair.

A setup that changes answers and gains in its first window is measured again on fresh servers
(Optimization, "A gain is measured again on fresh servers"). Before its first server is retired for that, the first servers
answer the task set too, and the check after the fresh window pools both pairs: each item's score
on a side is the share of that side's servers that got it right, and the interval is read over
items as before. Two pairs halve the servers' disagreement on the same items, so the interval
narrows, and `task_servers` records 2. The 1-point bar does not move: a lower end of −1.03 points
is not held, pooled or not. Pairs pool only when every reference server ran one revision and every
candidate server another, on the same task set; otherwise the verdict rests on the fresh pair and
the candidate's evidence says why (`task_pool_refused`). If the first servers could not answer,
the checkpoint records why and the verdict rests on the fresh pair alone. A run that evolves a live
endpoint keeps its control's server, so that one server answers once per pair. A setup without a
gain is not measured again, and its answers stay on one pair: it is not promoted on speed anyway.
A run on an endpoint an InferCrane agent serves pools the same way: the agent answers the task set
in its first window and again in the window on a new server, and the control plane judges both
pairs by this rule ([the agent page](/architecture/agent#optimization-runs-on-an-agent%E2%80%99s-endpoint)).

A task set may hold up to 1,000 items, 1 MiB, and an answer limit of 2,048 tokens, because answers
with working need about 1,000 tokens. The check asks each server 32 items at a time, the
reference's first and then the candidate's, so batching treats both alike, and each answer keeps
its item's place. Whether two identical setups score within the measured noise at 32 at once has
not been tested in the product yet. The evidence records the concurrency in its distribution
(`items_at_once`). A 1,000-item set takes about 12 minutes of each server on an L4. A check on a
task set may run 45 minutes; other checks 30. The reference's row records its own share right, and the
candidate's row its share right and the verdict. `tools/task-set/from_fast_track.py` turns the
fast-track map's 1,000-item task set (GSM8K and MMLU items, both MIT) into one.

Setups the optimizer plans carry a risk class. Lower numeric precision, other kernels, and
speculation can change what the model writes, so their `required_evidence` asks for a task score
against the starting setup. Every other change schedules the same computation and keeps the short
check. The evaluator name `infercrane-task` is reserved like the other two.

#### Tool calls

A case that declares `tools` is a tool case. When the reference calls functions, the candidate scores
1 on that case only if it calls the same functions with arguments that are JSON and equal the
reference's as canonical JSON (key order and spacing do not count, nor does the order of parallel
calls); otherwise 0.

A candidate **breaks** a tool call when the reference's calls name declared functions and their
arguments validate against those functions' `parameters`, and the candidate's do not: it calls a
different or undeclared function, drops or adds a call, answers in text instead, or sends arguments
that are not JSON or do not fit the schema. One broken call blocks the candidate, whatever its mean
score: its evidence records `passed: false`, so Release Guard blocks it too. A valid call with other
arguments, such as another city, is not broken; it scores 0 and counts in the mean like any other
different answer.

When the reference's own call does not validate, the case measures agreement only, and the evidence
counts it in `reference_invalid`. When neither side calls a function, the text answers are compared as
in any other case.

The tool-call score is reported apart from the mean, in the evidence's `distribution.tool_calls` and
in the candidate's `quality.tool_calls`:

| Field | Meaning |
|---|---|
| `cases` | Cases that declare tools. |
| `score` | Mean over those cases. Their scores also count in the overall mean. |
| `broken` | Cases where the candidate broke a call the reference made correctly. |
| `reference_invalid` | Cases where the reference's own call did not validate. |
| `candidate` | Cases by how the candidate's calls failed against the reference's, below. |
| `reference` | Cases by how the reference's own calls failed. Missing, extra, and unexpected calls are relative to the reference, so they stay 0 here. |

Each failure kind counts cases, never call content, and one case can count under several kinds:

| Kind | The calls in that case |
|---|---|
| `missing_call` | The reference called a function this side did not call, including an answer in text instead of a call. |
| `malformed_arguments` | Arguments that are not JSON. |
| `wrong_function` | An undeclared function, or another function in place of the reference's. |
| `schema_invalid` | Arguments that do not validate against the declared `parameters`. |
| `extra_calls` | More calls than the reference made. |
| `unexpected_call` | A call where the reference answered without one. It scores 0 but is not a broken call. |

Calls are compared in memory and never executed. A tool case needs a server that accepts `tools`: vLLM
must run with `--enable-auto-tool-choice` and a `--tool-call-parser` for the model. A server that
refuses a request with tools fails the check with an error that says so; it is never scored.

```bash
infercrane evaluation set upload eval-set.json
infercrane optimize create MODEL --provider PROVIDER --gpu GPU --eval-set sha256:DIGEST
```

The digest is the SHA-256 of the file's exact bytes. The campaign stores it in its reviewed proposal,
so the eval set cannot change under a running campaign. A campaign that names an eval set that is
not uploaded waits for it, and the run page shows the upload command. `evaluation set inspect` shows
an uploaded eval set without its prompts, and `evaluation set delete` removes it. Uploaded eval sets
belong to your organization and are deleted with it.

Runs that [Stay optimized](/features/optimization#stay-optimized) proposes for an endpoint use the
eval set its policy names in `quality_eval_set`, or the built-in prompts when it names none:

```bash
infercrane evaluation set stay-optimized chat sha256:DIGEST
infercrane evaluation set stay-optimized chat default
```

The command checks that the eval set is uploaded and changes only that field of the endpoint's saved
policy. A run already proposed keeps the eval set it was proposed with.

### Divergence of a precision change

Word agreement cannot separate a lossy precision change from noise: two servers of one setup can
already differ in long answers under load. So for a setup that changes numeric precision, the
built-in check also measures how far its next-token distribution moved. A setup changes precision
when it serves another checkpoint than the campaign's control, or another value of
`--quantization`, `--kv-cache-dtype`, or `--dtype`.

It reads long answers, because a precision change shows in what the model writes. With a
[task set](#task-sets) it reads the task set's own items, whose worked answers are long. Otherwise
it reads `infercrane-divergence`, 32 built-in open prompts that each ask for about 150 words. It
does not read the built-in answer-check prompts, which ask for a number or a word. Each reference
answer is capped at 256 tokens, so a reading holds up to 8,192 answer positions.

For up to 32 of those prompts without tools, the reference first answers greedily. Both servers then read
that prompt and answer as one forced sequence: a chat request whose last message is the answer,
with `continue_final_message`, and `prompt_logprobs` set to 16. A second request counts the
prompt's tokens. At every position, the KL divergence of the setup from the reference is taken over
the reference's 16 most likely tokens and one bucket for the rest of the vocabulary. A token the
setup did not return shares its unreturned mass. Coarser buckets can only lower a divergence, so the
value reads low rather than high. Both servers read identical inputs, so the value does not depend on
where two answers first part.

Token IDs name the same text only within one tokenizer, so both servers must read with the same
tokenizer and chat template. A setup serving the control's model at the same revision does. For a
setup serving another repository, such as a published FP8 checkpoint, the proposal records each
model's tokenizer digest in `input.model_tokenizers`. The control plane reads it from Hugging Face
when it makes the proposal: the sha256 of the files a server reads text with (`tokenizer.json`,
`tokenizer_config.json`, the chat template, the vocabulary, merges, and special and added tokens),
each named by its content hash. The divergence is read only when both digests are recorded and
equal; otherwise it is unknown, and the answers alone decide.

The result is recorded in the evidence's `distribution.divergence`, and in the candidate's
`quality.divergence`:

| Field | Meaning |
|---|---|
| `method` | `forced-decoding-kl-top-k-v1`. |
| `top_k` | Tokens compared per position: 16. |
| `prompts` | Prompts both servers read alike. A prompt whose token counts differ between the servers is left out. |
| `prefill_tokens`, `prefill_mean_kl` | The prompt's positions and their mean KL per token. |
| `generation_tokens`, `generation_mean_kl`, `generation_max_kl` | The answer's positions (the sample size), their mean KL per token, and the largest single position. |
| `prompt_set`, `prompt_set_version`, `max_answer_tokens` | The prompts read (a task set's name, or `infercrane-divergence`), their `version@digest`, and the cap on each answer. |

It is evidence: it passes and blocks nothing. No threshold has been set from measurements yet. A
threshold needs many readings on long answers, set against the same setups' task scores. It does
not come from one reading. Readings on the answer-check prompts, from before the check read long
answers, carry no `prompt_set`; their few answer positions are a small sample. It is
absent when not measured: for a setup that changes no precision, for a closed API, when a server
does not return prompt log probabilities, when the two servers are not known to read with the same
tokenizer, or when no prompt could be read alike. The reference's own
evidence never carries one. Prompts, answers, and log probabilities are read in memory and never
stored.

The same measurement runs without a control plane, between any two OpenAI-compatible servers that
return prompt log probabilities:

```bash
infercrane evaluation divergence --reference http://127.0.0.1:8000 --candidate http://127.0.0.1:8001 --model MODEL
infercrane evaluation divergence --reference URL --candidate URL --model MODEL --eval-set eval-set.json --output json
```

It reads the built-in long-answer prompts (`infercrane-divergence`) unless `--eval-set` names a
file, which is read as given, each answer capped at 256 tokens. `--api-key-env` names a variable
holding a bearer key both servers accept. Two servers of the same setup give the divergence that
nondeterminism alone causes, which is the floor any precision change is read against.

### Signing key

Built-in evidence is signed with the passport signing key from
`INFERCRANE_PASSPORT_SIGNING_KEY_FILE` when the control plane has one. Without it, each control-plane
process generates a key when it starts. Every row stays verifiable either way, because the envelope
carries its public key, but the key ID then changes on restart. Configure the passport key for a
stable key ID.

## Create an evaluator key

```bash
infercrane evaluation keygen --file ./quality-evidence.key
```

Keep the private Ed25519 key outside the control plane. The operator authorized to attach evidence is
the trust boundary.

## Ingest a result from any evaluator

<Warning>
An artifact digest proves which private result bundle was evaluated, not that the evaluator was
well-designed. Before generating or attaching evidence, approve the representative dataset, privacy
boundary, evaluator and version, calibration procedure, sampling method, and required human review
for high-risk changes. The commands below persist signed release evidence and `--attach` mutates the
candidate record; they do not upload prompt/output bodies or authorize promotion.
</Warning>

Have Ragas, DeepEval, a custom CI evaluator, or another customer-controlled system emit the strict
content-free evaluator result contract at `schemas/evaluator-result-v2.schema.json`:

```json evaluator-result.json
{
  "schema": "infercrane.dev/evaluator-result/v2",
  "suite": "support-answers",
  "suite_version": "git:8a91d7c",
  "evaluator": "customer-eval-ci",
  "evaluator_version": "1.4.0",
  "score": 0.93,
  "passed": true,
  "sample_count": 3,
  "distribution": {
    "schema": "infercrane.dev/quality-distribution/v1",
    "kind": "paired_scores",
    "pairing_digest": "sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "scores": [0.94, 0.91, 0.89]
  },
  "artifact_digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "evaluated_at": "2026-08-13T20:00:00Z"
}
```

The abbreviated score array above is illustrative; in a valid file `scores` contains exactly
`sample_count` finite values from 0 through 1 in the evaluator's canonical pair order. Active and
candidate files must use the same pairing digest. The digest commits the private sample identities
without storing those identities, prompts, or responses in InferCrane.

Bind that aggregate result to the exact immutable candidate revision, sign it, and explicitly attach
it through the control-plane API:

```bash
infercrane evaluation ingest qwen-prod REVISION_ID \
  --result ./evaluator-result.json \
  --key ./quality-evidence.key \
  --file ./candidate-quality.json \
  --attach

infercrane evaluation verify ./candidate-quality.json
```

Unknown fields are rejected, so prompt and generated-output bodies cannot accidentally enter the
evidence envelope. If API attachment fails, the signed local file remains available for a safe
`evaluation attach` retry.

## Sign aggregate evidence directly

```bash
infercrane evaluation sign qwen-prod REVISION_ID \
  --suite support-answers \
  --suite-version git:8a91d7c \
  --evaluator ragas \
  --evaluator-version 0.3.9 \
  --score 0.91 \
  --passed=true \
  --samples 250 \
  --artifact-digest sha256:RESULT_ARTIFACT_SHA256 \
  --key ./quality-evidence.key \
  --file ./candidate-quality.json

infercrane evaluation verify ./candidate-quality.json
infercrane evaluation attach qwen-prod --file ./candidate-quality.json
```

The signed payload records deployment, immutable revision, suite and evaluator versions, normalized
score, pass/fail result, sample count, result-artifact digest, and evaluation time. Attaching the same
evidence twice is idempotent.

## Fail closed in Release Guard

```bash
infercrane rollout policy set qwen-prod \
  --require-quality \
  --minimum-quality-score 0.90 \
  --max-quality-regression 3 \
  --quality-comparison bootstrap \
  --quality-bootstrap-alpha 0.05 \
  --quality-bootstrap-min-samples 3 \
  --quality-bootstrap-seed 20260827

infercrane rollout evaluate qwen-prod
infercrane rollout inspect qwen-prod
```

Active and candidate evidence must use the same suite version and evaluator version to be comparable.
Missing or incomparable required evidence leaves the decision waiting. A failed suite, score below
the minimum, or regression beyond policy rejects the candidate. The evaluator cannot activate a
revision; promotion remains a separate, authorized control-plane decision.

Release Guard checks every eval the candidate has evidence for, not only the newest one, including
the built-in answer check. For an evolve-endpoint campaign the built-in check records the active
revision as its reference, so the two rows are comparable. An eval is
one suite scored by one evaluator. For each eval, InferCrane takes the candidate's newest evidence
and compares it with the active revision's newest evidence from the same suite version and
evaluator version.

`threshold` remains the default comparison mode. In `bootstrap` mode InferCrane performs 10,000
deterministic paired resamples. A confidence interval wholly below the allowed regression passes;
one wholly beyond it rejects; an overlapping interval or too few pairs waits. The persisted decision
records the seed, alpha, active/candidate counts, observed regression, and interval so a retry is
reproducible.

The three-score example demonstrates the contract, not a recommended production sample size.
Choose and review a representative minimum for the evaluator and risk class; insufficient pairs
must remain waiting.

## PASS, WATCH, and BLOCK per eval

A small drop is not always a reason to stop a rollout, but it should not pass silently either. Add a
watch band below the regression limit, and every eval gets one of four verdicts:

| Verdict | When | Release Guard |
|---|---|---|
| `PASS` | The drop is at or below the watch threshold, or at or below the regression limit when no watch band is set. | No change. |
| `WATCH` | The drop is above the watch threshold and at or below the regression limit. | Stays `ACCEPT`, adds a `quality_watch` reason, and records a follow-up. |
| `BLOCK` | The suite failed, the score is below the minimum, or the drop is above the regression limit. | `REJECT`, as before. |
| `UNKNOWN` | No comparable evidence from the active revision, or bootstrap evidence is unpaired, inconclusive, or short of samples. | `WAIT`. Missing evidence never passes. |

The drop is relative to the active revision's score: `(active - candidate) / active × 100`. In
`bootstrap` mode, the interval decides `BLOCK` and `UNKNOWN` as described above. Once the interval
clears the limit, the observed paired drop decides between `WATCH` and `PASS`.

The model verdict is the most severe eval verdict, in the order `BLOCK`, `UNKNOWN`, `WATCH`,
`PASS`. A candidate with no evidence at all is `UNKNOWN`.

### Set the watch band

`quality_watch_regression_percent` sits beside `max_quality_regression_percent` in the persisted
policy. It needs a regression limit and cannot exceed it. The example below keeps the 3% limit from
the policy above and opens a watch band from 1% to 3%:

```bash
curl -fsS "$INFERCRANE_URL/api/v1/deployments/qwen-prod/release-guard/policy" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY" |
  jq '.quality_watch_regression_percent = 1' |
  curl -fsS -X PUT "$INFERCRANE_URL/api/v1/deployments/qwen-prod/release-guard/policy" \
    -H "Authorization: Bearer $INFERCRANE_API_KEY" \
    -H "Content-Type: application/json" \
    --data-binary @-
```

`infercrane rollout policy set` has no flag for the watch band yet. It keeps the stored value when
you change other settings. Lowering `--max-quality-regression` below the watch threshold is
rejected. Remove the band first by setting the field to `null`.

### Read the verdicts

`GET /api/v1/deployments/{name}/quality-evidence` returns the evidence list and a `verdicts`
object for the current candidate. It applies the persisted policy to the stored evidence and records
nothing:

```json
    "max_regression_percent": 3,
    "reference": { "revision_id": "ACTIVE_REVISION_ID", "model": "ACTIVE_MODEL" },
    "candidate": { "revision_id": "CANDIDATE_REVISION_ID", "model": "CANDIDATE_MODEL" },
    "evals": [
      {
        "suite": "support-answers",
        "suite_version": "git:8a91d7c",
        "evaluator": "customer-eval-ci",
        "evaluator_version": "1.4.0",
        "verdict": "WATCH",
        "code": "quality_watch",
        "reference_score": 0.93,
        "candidate_score": 0.915,
        "delta": -0.015,
        "regression_percent": 1.61,
        "limit": 1,
        "follow_up": "Re-run support-answers@git:8a91d7c with customer-eval-ci@1.4.0 on this revision after promotion and review the drop before promoting a candidate built on it"
      }
    ]
  }
}
```

The example is abbreviated: real responses also carry `data`, `content_recorded`, evidence IDs, and
a message per eval, and numbers are not rounded. `delta` is the candidate score minus the active
score, so a drop is negative. `model` is the resolved immutable model identity, or the model the
revision requested when no identity was resolved, and empty when neither is recorded.

Without a `compared` state there is no verdict. The other states are `no_candidate`, `not_gated`
(the policy does not gate on quality, or Release Guard is disabled), and `unavailable` (no running
deployment or policy).

The stored Release Guard evaluation stays the decision of record. Each evaluation persists the same
report under `metrics.quality`. Its reasons name the eval (`suite@suite_version`) for every `BLOCK`
or `UNKNOWN` eval, and for every `WATCH` eval when the decision is `ACCEPT`.

### Follow up on WATCH

When the decision is `ACCEPT` and at least one eval is `WATCH`, the evaluation starts its reasons
with one `quality_watch` reason per watched eval. `infercrane rollout inspect` prints each one with
its follow-up. Release Guard also writes a `release_guard.quality_watch` audit event with outcome
`follow_up_required`. That event lists the watched evals, their scores and drops, and the
follow-up, so it stays visible after promotion. Listing audit events needs tenant-admin access:

```bash
curl -fsS "$INFERCRANE_URL/api/v1/audit-events?limit=100" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY" |
  jq '.data[] | select(.action == "release_guard.quality_watch")'
```

A `WATCH` does not lower any other gate. If another check rejects or waits, that decision stands and
no follow-up is recorded.
