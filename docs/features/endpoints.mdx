# Stable endpoints and serving plans

An endpoint is the model name an application sends to InferCrane. It is deliberately separate from
a deployment, provider, and runtime:

```text
application model="coder-production"
              ↓
           endpoint
              ↓
      active serving plan
              ↓
        backend binding
              ↓
 concrete deployment or imported target
```

This lets an operator stage a different serving implementation without changing application code.
Existing v1 deployment aliases are migrated automatically to a `production` environment, a logical
model, a lifecycle-managed binding, and a one-binding active plan of the same name. Each new
deployment gets the same set. Its logical model has an empty description.

That endpoint belongs to the deployment, as does an endpoint a deploy publishes under its
`endpoint_name`. When the deployment is deleted, or its first deploy is cancelled, InferCrane deletes
these endpoints too, unless you bound another backend to one of them. Endpoints you create yourself
are never deleted with a deployment. A deleted endpoint's name can be used again, and a deployment
deployed again under the same name reuses that name's logical model.

## Create an endpoint

```bash
infercrane logical-model create coder \
  --description "Stable coding model"

infercrane endpoint create coder-production \
  --model coder \
  --environment production

infercrane endpoint bind coder-production \
  --name primary \
  --deployment qwen-prod \
  --ownership lifecycle-managed

infercrane endpoint plan coder-production \
  --policy manual \
  --bindings primary
```

The first plan becomes active. Later plans are staged as candidates and receive no application
traffic until promoted:

```bash
infercrane endpoint plan coder-production \
  --policy primary-fallback \
  --bindings candidate,primary

infercrane endpoint inspect coder-production
infercrane endpoint guard coder-production --evaluate
infercrane endpoint promote coder-production PLAN_ID
```

Plan creation returns `route_refresh: converged` when the in-memory route was published before the
response. `pending` means durable state is committed and ordinary reconciliation will publish it.

## Endpoint states

The reconciler records each endpoint's `observed_state`:

| State | Meaning |
|---|---|
| `pending` | Durable state is committed and reconciliation has not published a route yet. |
| `serving` | A route is published for the active serving plan. |
| `observing` | Every binding in the active plan is `observe-only`. InferCrane records health and evidence but publishes no route by design, so this is not a failure. |
| `degraded` | At least one routable binding in the active plan could not be published, or a `manual` plan does not resolve to exactly one route. |
| `suspended` | The endpoint is intentionally not serving. |
| `deleted` | The endpoint was deleted. |

A plan that mixes `observe-only` bindings with routable ones reads `serving` or `degraded` from the
routable bindings alone.

## Routing policies

| Policy | Behavior |
|---|---|
| `manual` | Exactly one selected binding. |
| `primary-fallback` | First available binding in declared priority order. A buffered request the first binding cannot answer moves to the next one (see below). InferCrane does not replay an accepted stream. |
| `weighted` | Deterministic smooth weighted round-robin among currently available bindings. |

### Weighted plans interleave

A weighted plan interleaves its bindings, so a short window of requests already sees the
configured share. With weights `9000:1000`, every run of ten requests sends one to the second
binding; `9500:500` sends one in every twenty. Any weights work, so a canary can use the share it
needs. The order restarts only when the available bindings or their weights change: a binding
that becomes unhealthy, recovers, or gets a new weight. The reconciler republishing the same plan
does not restart it. Each gateway process keeps its own order in memory.

### When the primary fails mid-request

On a `primary-fallback` plan, the reconciler drops a binding that turned unhealthy at its next
routing pass. Until then, the gateway itself moves a request on when all of these hold:

- the request is buffered, not streamed;
- the binding gave no response byte: the connection failed, or it answered `502`, `503` or `504`;
- the caller is still waiting and the endpoint's `request_timeout_ms` has not passed;
- the failed binding is not a paid external binding (one with an external budget policy). Those
  are never retried, because the supplier may already have charged for the attempt.

The request goes to the next published binding in priority order that it has not tried, with that
binding's model name and credentials. It tries at most two more bindings, and each gets one
attempt. The endpoint's admission `retry_budget` is spent only on the first binding, and the router
behind a deployment has already retried its own workers, so retries are not stacked. A paid
external fallback still reserves its budget before anything is sent; if it cannot, it is skipped
and the caller gets the first binding's error.

Request telemetry keeps one record per request, attributed to the binding that answered, with
`fallback_reason` saying why the request left the earlier binding: `upstream_connection_failed`,
`upstream_502`, `upstream_503` or `upstream_504`. `retry_count` counts retries on the same
binding only. The failed attempt is not recorded on the binding it left, so Release Guard and
release monitoring do not count it as that revision's error. Endpoint monitoring's `fallbacks`
count shows how often that happens, per binding on the binding that answered.

Serving plans are immutable and SHA-256 identified. Promotion changes only future route
acquisitions. A buffered or streaming request remains pinned to the route generation it acquired
until the request finishes.

Promotion fails closed unless the latest persisted endpoint Release Guard evaluation is `PASS` for
the current active/candidate pair. `REJECT` and `INCONCLUSIVE` can be inspected but cannot be
promoted. Candidate traffic is never duplicated silently; Release Guard evaluates trustworthy telemetry
from the primary deployment-backed binding and reports insufficient evidence as `INCONCLUSIVE`.
It does not reuse those primary metrics for a weighted or otherwise unmeasured routing topology.
An append-only managed fallback is eligible only when it preserves the active routing prefix and
has immutable consent plus hard-budget policy; the persisted evaluation records that topology
classification explicitly.

A **migration plan** routes between a closed API's external binding and an owned deployment binding
and records `migration_verdict_id`: the signed verdict that the deployment's active revision answers
a graded suite as well as that closed API. It is the only way a weighted plan may span two different
models, and it cannot be promoted to another environment. `POST /api/v1/endpoints/{name}/migration`
with `step` `canary`, `primary`, or `rollback` creates the step's plan, evaluates Release Guard, and
activates it on `PASS`. See [Migrate from a closed API](/features/migration).

## Ownership boundaries

Bindings record `observe-only`, `traffic-managed`, or `lifecycle-managed` ownership. InferCrane supports
fully compiled lifecycle-managed deployment bindings. Incremental import/adopt workflows and
customer-managed external bindings; creating a record does not imply that
InferCrane owns an external workload's lifecycle.

The inference hot path reads an immutable in-memory endpoint snapshot. It never queries PostgreSQL.
Request telemetry records the logical model, environment, endpoint, serving plan, binding,
deployment, revision, replica where known, provider, and runtime without storing prompt or output
content by default.

## Add an authenticated managed API

An OpenRouter or generic OpenAI-compatible API can be staged behind the same endpoint. Provider
credentials remain reference-only, external data transmission requires explicit consent, and hard
request/cost reservations fail closed before any bytes are sent:

```bash
export MANAGED_MODEL_API_KEY='...'
infercrane provider connect managed-coder \
  --adapter openai-compatible-external \
  --url https://models.example.com/v1 \
  --model provider/coder-model \
  --from-env MANAGED_MODEL_API_KEY

infercrane endpoint bind coder-production \
  --name managed-fallback \
  --connection managed-coder \
  --request-limit 1000 \
  --cost-limit-usd 25.00 \
  --max-request-cost-usd 0.10 \
  --acknowledge-external-data \
  --enable-external

infercrane endpoint plan coder-production \
  --policy primary-fallback \
  --bindings primary,managed-fallback
```

The new plan is a candidate. It receives no application traffic until Release Guard passes and an
operator explicitly promotes it. Adding a fallback never changes the application request:

```python
client.responses.create(model="coder-production", input="Explain this incident.")
```

The web console exposes the same staging workflow on the endpoint page. It never receives the
provider credential; it sends only the selected secret-reference ID to the control API.
