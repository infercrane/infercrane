# Choose a model without accepting a black box

InferCrane's Verified Models catalog is a small, reviewed set of deployment starting points. It is
not a hosted-model marketplace and it does not imply that one model runs on every GPU, runtime, or
provider.

```bash
infercrane models
infercrane models embeddings
infercrane models inspect mistral-7b-instruct
```

Each entry exposes:

- the Hugging Face repository and immutable commit;
- publisher, task, protocol, capabilities, and modalities;
- license URL and gated-access requirement;
- reviewed runtime configuration and serving profiles;
- review date and an explicit evidence boundary.

Create a project from one reviewed entry:

```bash
infercrane workload init ./support-model \
  --recipe mistral-7b-instruct \
  --profile vllm-interactive

cd ./support-model
infercrane workload validate
infercrane workload plan
infercrane workload deploy --wait
```

The browser console exposes the same control-plane catalog under **Models**. A model detail page
shows the immutable identity and qualification scope before the deployment form is populated.

## Pick an operating objective, then measure it

Generation recipes may expose three reviewed vLLM candidate profiles:

| Serving profile | Intended trade-off | Immutable runtime arguments |
| --- | --- | --- |
| `vllm-balanced` | General production starting point with repeated-prefix reuse | `--enable-prefix-caching` |
| `vllm-interactive` | Favor decode responsiveness | Prefix caching and `--max-num-batched-tokens 2048` |
| `vllm-throughput` | Favor aggregate token throughput | Prefix caching and `--max-num-batched-tokens 16384` |

These are configuration-verified candidates, not performance claims. The selected profile is written
into `infercrane.yaml`, including the runtime version, immutable workload image and executable argv
when required, accelerator type and count, provider hint, replica bounds, and cache-aware routing.
Review or edit that ordinary DeploymentSpec before `plan`; editing a reviewed tuple creates an
explicitly unreviewed configuration that must earn its own evidence.

The candidates follow upstream [vLLM optimization guidance](https://docs.vllm.ai/en/latest/configuration/optimization/),
which explicitly describes latency/throughput trade-offs for chunked prefill and requires workload-
specific measurement. Benchmark the exact model, GPU, runtime version, and traffic shape before
promotion; a value that helps one workload can hurt another or increase memory pressure.

## Evidence levels

| Level | What it proves | What it does not prove |
| --- | --- | --- |
| Configuration verified | Repository identity, immutable revision, license metadata, protocol, runtime image/argv, and accelerator topology were reviewed | GPU fit, provider capacity, latency, throughput, or price |
| Measured recipe | One exact artifact, runtime, provider, GPU type/count, region, workload, and AIPerf run | Portability to a different serving plan |
| Community recipe | Contributor-supplied configuration with visible provenance | InferCrane qualification unless separately recorded |
| Explicit model | The operator selected a repository and serving plan | Compatibility or production readiness |

The current built-in catalog contains only **configuration-verified** entries. Measured results stay
tenant-scoped in benchmark history and immutable model recipes; InferCrane does not silently promote
them into universal claims.

## General profiles for fast-moving runtimes

Serving profiles are not limited to InferCrane's built-in vLLM image. A profile can carry a custom
OCI image pinned by digest, a runtime version label, complete executable argv and probes, an exact
GPU count, compatible GPU types, and a provider hint. The same revision contract flows through
planning, provider compilation, pricing, capacity evidence, benchmarking, recommendations, and
signed inference passports. Lifecycle code contains no model-specific branch.

`glm-5.3-flash` and `qwen3.8-flash-next` are experimental catalog entries exercising this general
path. Each reviewed profile pins the model commit, a dedicated upstream vLLM image, exact GPU
topology, and complete executable argv. Both remain **configuration-verified**, not real-GPU or
production-qualified.

The primary GLM profile requests one native RunPod Pod with eight H200 GPUs and tensor parallelism,
matching the current upstream H200 recipe. A separate four-B200 Blackwell profile follows upstream's
TP4 Blackwell guidance but remains an exact-tuple qualification candidate. The `runpod-pods` adapter
launches the pinned upstream image directly, without an SSH-derived wrapper.
The reviewed command first materializes the complete commit-pinned Hugging Face snapshot at a local
container path, then replaces the bootstrap process with vLLM. This provider-neutral argv pattern
works around a day-zero runtime ordering issue where multimodal processor metadata is opened before
the runtime's ordinary Hub resolver runs; it is reusable by other custom OCI profiles that require a
filesystem model path. It deliberately uses a bounded 131K context starting point rather than
converting the model card's declared 1M
maximum into an unmeasured production promise. See the [official model card](https://huggingface.co/zai-org/GLM-5.3-Flash)
and [upstream vLLM recipe](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash).

```bash
infercrane models inspect glm-5.3-flash
infercrane workload init ./glm-flash \
  --recipe glm-5.3-flash \
  --profile custom-oci-hopper-tp8
infercrane workload validate ./glm-flash
infercrane workload plan ./glm-flash
```

Those commands are local and non-mutating through `plan`. Deployment still requires current RunPod
capacity, enough configured storage, paid-resource acknowledgement, and fresh qualification
evidence for the exact generated tuple. The FP8 snapshot is about 306 GiB before runtime overhead.
Use an appropriately sized identity-bound network volume or container disk; storage and topology
remain plan inputs, not inferred defaults.

The Qwen profile uses the separate FP8 checkpoint and the official eight-H200 TEP8 topology. Plain
TP8 is incompatible with that checkpoint's quantization blocks, so the reviewed argv enables expert
parallelism and the Triton MoE backend. InferCrane bounds the starting context at 131K; native 262K
and one-million-token YaRN remain separate qualification targets. This is the experimental
`Qwen3.8-Flash-Next` open-weight preview, not the forthcoming production `Qwen3.8-Flash` QwenCloud
service. See the [official model card](https://huggingface.co/Qwen/Qwen3.8-Flash-Next-FP8) and
[upstream vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-Flash-Next).

<Warning>
  Qwen3.8-Flash-Next uses the Qwen Community License 1.0, not an OSI open-source license. Its terms
  require a separate Qwen license for specified commercial Model-as-a-Service and AI work-assistant
  uses. Review the [exact pinned license](https://huggingface.co/Qwen/Qwen3.8-Flash-Next-FP8/blob/bcd9f01ddc9cff2316eb84281bebcd5b058bddce/LICENSE)
  before deployment.
</Warning>

```bash
infercrane models inspect qwen3.8-flash-next
infercrane workload init ./qwen-flash-next \
  --recipe qwen3.8-flash-next \
  --profile custom-oci-hopper-tep8
infercrane workload validate ./qwen-flash-next
infercrane workload plan ./qwen-flash-next
```

Those commands are also local and non-mutating through `plan`. Real deployment requires current
RunPod capacity for an exact eight-H200 Pod and fresh protocol, memory, performance, and cleanup
evidence. The catalog also exposes `custom-oci-blackwell-tp2` and
`custom-oci-blackwell-tep4` as explicitly unqualified two- and four-B200 candidates for environments
where the H200 node shape is unavailable; selecting either does not create a support claim.

## Current market watch

The public model story is intentionally broader than InferCrane's small regression fixtures. As of
2026-08-23, three different signals point to the families teams are evaluating now:

- [Artificial Analysis](https://artificialanalysis.ai/leaderboards/models) ranks Kimi K3, Qwen3.8
  A95B, and DeepSeek V4 Pro among the leading open-weight models by its Intelligence Index;
- [OpenRouter's usage ranking](https://openrouter.ai/rankings/) shows substantial current token
  traffic for Kimi, DeepSeek, and MiniMax families;
- official model cards and releases show active ecosystems around
  [GLM-5.3](https://z.ai/blog/glm-5.3),
  [gpt-oss](https://huggingface.co/collections/openai/gpt-oss),
  [Gemma 4](https://huggingface.co/collections/google/gemma-4), and Meta Llama.

| Market path | Current families to evaluate | InferCrane entry path |
| --- | --- | --- |
| Frontier open-weight reasoning | Kimi K3, Qwen3.8 A95B, DeepSeek V4 Pro | Connect a provider API or qualify an explicit multi-node artifact plan |
| Coding and long-horizon agents | GLM-5.3, Kimi K3, Qwen3.8, DeepSeek V4 | Keep one endpoint; compare task, latency, and cost evidence before changing bindings |
| High-volume API alternatives | Kimi, DeepSeek, MiniMax | Govern the external binding with budgets, request evidence, and fallback policy |
| Deployable ecosystem anchors | gpt-oss, Gemma, Llama, Qwen compact variants | Start from an exact artifact, then qualify runtime, topology, and protocol |
| Retrieval | BGE, Qwen Embedding, Jina embedding families | Qualify the embeddings protocol and workload-specific throughput |

Popularity is a discovery signal, not a market-share percentage or compatibility proof. OpenRouter
ranks token volume rather than users or spend, and model-hub downloads can include automation. The
leaderboard date and exact model revision must remain visible whenever InferCrane publishes a
comparison.

Frontier families also expose the central reason InferCrane exists: Kimi K3, Qwen3.8 A95B, DeepSeek
V4, and GLM-5.3 do not share one license, topology, runtime requirement, provider surface, or cost
profile. The application can retain one stable model identity while each backend binding keeps its
own qualification evidence.

## Reviewed deployment collections

The built-in catalog follows application tasks rather than chasing a weekly popularity ranking.
Selection considers current ecosystem adoption, an official upstream model card, license clarity,
and compatibility with InferCrane's qualified runtime line. Older compact models are useful here
because they make frequent single-GPU lifecycle qualification affordable; they do not define the
marketing story.

| Collection | Reviewed starting points | Typical application |
| --- | --- | --- |
| General chat | Mistral 7B Instruct, Qwen3 8B, Llama 3.1 8B Instruct | Support, assistants, generation |
| Reasoning | Qwen3 8B, DeepSeek R1 Distill Qwen 7B | Analysis and multi-step tasks |
| Coding | Qwen2.5 Coder 7B Instruct | Completion, explanation, transformation, repair |
| Vision and documents | Gemma 3 4B IT, Qwen2.5 VL 7B Instruct | Screenshots, forms, diagrams, visual question answering |
| Embeddings and RAG | BGE-M3 | Multilingual search and private retrieval |
| Extraction and summarization | Granite 3.3 8B Instruct | Controlled enterprise text pipelines |

This is not a claim that every entry is best for its category. Evaluate quality on the application's
own data, then benchmark the exact serving plan before promotion.

Catalog review uses the upstream [Hugging Face model metadata](https://huggingface.co/models), the
[vLLM supported-model matrix](https://docs.vllm.ai/en/latest/models/supported_models.html), and each
publisher's model card and license. Task-oriented discovery is informed by model-library patterns
used by [Replicate](https://replicate.com/collections) and
[Baseten](https://www.baseten.co/library/), but InferCrane entries remain provider-neutral and do not
copy their performance or availability claims.

<Note>
Popular models that require a newer runtime, a multi-node topology, unpublished weights, or custom
license handling remain available through an external binding or explicit-model path. Catalog
starting points provide defaults; they are not an allowlist and they do not imply measured
performance or provider availability.
</Note>

<Warning>
`gpu_hint` supplies the default accelerator. Profiles with `compatible_gpus` reject a different GPU
during scaffolding because their runtime argv is hardware-specific. You can edit the generated YAML
to experiment, but that is a new unreviewed configuration. Run `plan`, confirm memory/topology
requirements, and qualify the exact provider/runtime combination before production.
</Warning>

## Any Hugging Face model remains available

The catalog is convenience, not an allowlist. Any open Hugging Face model can be checked
automatically and deployed from the dashboard or the CLI (see
[Check any model automatically](#check-any-model-automatically)), or scaffolded by hand:

```bash
infercrane workload init ./my-model --model organization/repository
infercrane workload plan ./my-model
```

Mutable references are resolved into `ModelArtifact` identity during the durable deployment
lifecycle. A catalog entry simply starts with a reviewed commit and clearer license/protocol
metadata.

### Search Hugging Face

To find a repository that is not in the catalog, search the public Hugging Face models API through
the control plane:

```bash
curl -sS "$INFERCRANE_CONTROL_URL/api/v1/catalog/hugging-face/search?query=phi&limit=20" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY"
```

The control plane asks Hugging Face for public `text-generation` and `feature-extraction` models
whose repository name matches `query`, merges the two lists, and returns the most downloaded first.
`query` takes 2 to 100 characters. `limit` takes 1 to 50 and defaults to 20.

Each result reports `repository`, `pipeline_tag`, `license`, `gated` and `gated_mode`, `downloads`,
`last_modified`, and `library_name` exactly as Hugging Face returned them. A value Hugging Face did
not report is `null`, never a guess. `license` comes from the repository's `license:` tag.
`downloads` is Hugging Face's count for the last 30 days. It shows popularity, not quality,
compatibility, or performance.

Every result has `reviewed: false` and `source_kind: "hugging-face-search"`. A search result is a
repository you can try with `--model organization/repository` or the dashboard's New endpoint
screen. It does not join the catalog and does not become an optimization candidate.

The search is bounded:

- Each search waits at most 4 seconds for Hugging Face.
- Successful answers are kept in memory for 10 minutes, up to 256 queries per control-plane
  process. Failures are not kept.
- At most 8 searches reach Hugging Face at the same time.
- The control plane sends no Hugging Face token, so private repositories are never listed. Gated
  repositories are listed with `gated: true`; deploying one still needs a token that has accepted
  its terms.

When Hugging Face cannot answer, the route returns `hugging_face_search_unavailable`: HTTP 504 when
it timed out and HTTP 502 for any other failure, with the reason in `error.message`. A control plane
without outbound HTTPS access to `huggingface.co` always returns that error; the catalog routes keep
working.

### Check any model automatically

A model outside the reviewed catalog is **not reviewed: checked automatically**. The control plane
reads what Hugging Face publishes for one exact commit and answers four questions:

| Check | What is read | Result |
| --- | --- | --- |
| Architecture | `config.json` `architectures`, compared with a committed snapshot of the vLLM 0.22.1 and SGLang 0.5.12 model registries | `supported` (with the runtime), `unsupported` (with the reason), or `unknown` |
| Size | Hugging Face's safetensors summary: parameters by tensor type, and stored bytes | Read, or unknown when the repository has no safetensors |
| GPU fit | Weights plus KV cache for the target load, against GPUs this control plane has a current price for | The fewest GPUs, then the smallest GPU, that hold it, with tensor parallelism across them; or `does_not_fit`, or unknown |
| License and access | The model card's license, and Hugging Face's `gated` and `private` flags | Shown as declared; a gated or private model needs a Hugging Face token |

The GPU fit sizes one replica for `concurrency` requests (default 8) at `context_tokens` tokens each
(default 8192, capped at the model's declared context length). It assumes vLLM's default 90% memory
use, 2 GiB per GPU for activations and buffers, a 16-bit KV cache in every layer (an upper bound for
sliding-window models), and 32-bit weights served at 16 bits. Multi-head latent attention models
cache their compressed latent instead. The fit lists every priced GPU type that holds the model.

```bash
infercrane models check microsoft/phi-4
infercrane models check microsoft/phi-4 --concurrency 16 --context-tokens 16384
infercrane models check microsoft/phi-4 --spec phi-4.yaml
infercrane deploy phi-4.yaml --wait
```

`--spec` writes the proposed setup as a DeploymentSpec: the pinned commit, the runtime's own
defaults with `--max-model-len` set to the checked context, and `--tensor-parallel-size` when the
fit needs more than one GPU. In the dashboard, a Hugging Face search result shows the same check
inline, and opening it shows the proposed setup with a **Not reviewed: checked automatically**
badge and every check that ran. An unsupported model shows why, with the nearest reviewed models.

```bash
curl -sS "$INFERCRANE_CONTROL_URL/api/v1/catalog/hugging-face/check?repository=microsoft/phi-4&concurrency=8" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY"
```

The response holds `check` (schema `infercrane.model-check/v1`), `reviewed_model` (the reviewed
catalog name when the repository has one; prefer that setup), and `performance_claims: false`.
`check.verdict` is `supported` only when the architecture is registered, the model fits a priced
layout, and it could be read; `unsupported` when one of those is known to fail; and `unknown` when
something could not be read. `check.checks` lists what was checked, one line each. A value Hugging
Face did not publish is `null`.

The check never claims throughput, latency, answer quality, capacity, or price. Measure those with
an [optimization run](/features/optimization).

**Gated and private models.** Save a Hugging Face token as a workspace credential named `model-…`
under Settings › Connections (or `infercrane secret`), from an account that accepted the model's
terms. Pass its ID as `model_secret_reference_id` (`--secret` in the CLI). The token is resolved
only to read the model, is never returned, and its reads are cached per workspace and credential,
so one workspace's token never answers another's request. The token pins and reads the model; the
GPU provider still downloads weights with its own configured Hugging Face credential.

**Turning it on.** The control plane reads Hugging Face for checks only when the operator sets
`INFERCRANE_HUGGING_FACE_METADATA_ENABLED=true`. It is off by default; planning then says that
models outside the reviewed catalog cannot be checked, and the check route returns
`metadata_access_disabled` (HTTP 501). The reads never happen on the inference request path and never
touch PostgreSQL.

**Limits.** Each check waits at most 8 seconds for Hugging Face, sends at most 8 requests at once, and
follows redirects only on the same host. Results are cached in memory by commit, up to 512 per
control-plane process; a branch name is re-pinned after 10 minutes. Errors are typed:
`model_not_found` (HTTP 404; Hugging Face answers the same way for a private repository read without a
token), `revision_not_found` (404), `hugging_face_token_rejected` (422), and
`hugging_face_unavailable` (504 on timeout, 502 otherwise).

**Where the runtime registries come from.** `internal/modelcheck/runtime_model_registries.json`
records the architectures each pinned runtime release registers, read from its source at the
release commit, plus vLLM's quantization methods. `scripts/snapshot-runtime-model-registries.py`
rebuilds it; a test fails when the pinned runtime versions change without a new snapshot.

## API

Authenticated consoles and automation can use:

```bash
curl -sS "$INFERCRANE_CONTROL_URL/api/v1/catalog/models?query=chat" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY"

curl -sS "$INFERCRANE_CONTROL_URL/api/v1/catalog/models/qwen3-8b" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY"
```

The response includes `performance_claims: false`. Trustworthy performance comes from
[AIPerf benchmarking](/features/benchmarking), [Inference Lab](/features/recipes-lab), and the exact
evidence attached to a revision.

InferCrane does not mirror a third-party discovery catalog. The Hugging Face search above passes
each query through and keeps answers in memory only for a few minutes. Customer-visible models are
reviewed InferCrane products, while private deployment workflows resolve each artifact to an
immutable repository revision before any capacity can be created.
