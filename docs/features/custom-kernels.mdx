title: Custom kernels
description: How an optimization run tries a custom GPU kernel last, only when the trace shows one operator the engine runs poorly, and what a kernel has to prove.
---

A custom kernel is the last thing an optimization run tries, never the first. It is part of the run:
the run plans it next to the setting and precision changes, runs it in its own lane after your one
approval, and records its verdict with the run's other setups. Nobody starts a kernel run on its own.

<Warning>
The kernel lane is off by default and needs an Accelerator Lab worker on a GPU host you control. A
qualified kernel is recorded but not yet served: serving one needs a runtime image with the kernel
built in, which InferCrane does not build yet. See [What it does not do yet](#what-it-does-not-do-yet).
</Warning>

## When a run plans a kernel

The run plans a custom-kernel setup only when every condition holds. Each one reads measured evidence;
a value nobody measured is unknown, and unknown never plans a kernel.

| Condition | Read from |
|---|---|
| One operator class holds at least 30% of kernel time | the endpoint's newest [GPU trace](/features/gpu-profiling#operator-efficiency): attention, mixture-of-experts expert matrix multiplies, expert routing, or normalization |
| The engine's own kernel for it runs below 50% of what the GPU allows for its shapes | the trace's operator efficiency, which needs recorded shapes for at least half of that operator's time |
| No setting change in the same plan already changes that operator's kernels | FP8 weights change expert matrix multiplies, an FP8 KV cache changes attention, AMD AITER changes all four |
| The lab has a reviewed kernel pack for that operator on the GPU's vendor and the starting setup's exact engine version | the reviewed packs below |
| The run replays your recorded traffic | the run's traffic; a public sample or test profile plans no kernel |
| This control plane runs kernel lanes | `INFERCRANE_OPTIMIZATION_KERNEL_LANE` |

The plan says why in one sentence, for example "Normalization took 41% of kernel time and ran at 32%
of what this GPU allows for its shapes". When a condition fails, the plan lists the kernel as skipped
and names the condition. The rule is `gpu_trace.kernel_dominant_operator` in
[rules from a GPU trace](/features/optimization#rules-from-a-gpu-trace).

Reviewed packs today:

| Operator | Kernel | Vendor | Engine | Serving scope |
|---|---|---|---|---|
| Normalization | fused residual-add + RMSNorm, Triton | NVIDIA | vLLM 0.22.1 | vLLM's `fused_add_rms_norm` |
| Mixture-of-experts experts | fused routed experts: gate and up, SiLU, down, weighted sum, Triton | NVIDIA | vLLM 0.22.1 | BF16 expert weights with SiLU and no expert map, bias, or LoRA, under `--moe-backend triton`, which the candidate sets; other calls keep vLLM's kernel |

Because the mixture-of-experts candidate sets `--moe-backend triton`, it is measured against whatever
backend the starting setup uses. On an H100, vLLM 0.22.1 picks FlashInfer CUTLASS for BF16 experts by
default, so a kernel has to beat that, not only vLLM's Triton experts.

Neither pack has qualified a kernel. The mixture-of-experts pack's own reference kernel has been measured
end to end on an H100 and would not qualify (see [Evidence so far](#evidence-so-far)). It comes first because published
measurements put routed experts at 35–46% of decode kernel time for DeepSeek-V3 on one node (H200 and
MI300X) and the engine's own Triton experts at 10–20% of HBM bandwidth at batch 1 on an H200. In wide
expert-parallel decode at large batches, communication and attention dominate instead, so a kernel is
not planned there. Matrix multiplies and attention have no pack.

## What the kernel lane does

After you approve the run, the setting changes race as usual and report when they are ready. They
never wait for the kernel. In parallel, the kernel lane:

1. **Builds.** Publishes your recorded traffic and the answer-check prompts to the lab worker, then has
   the lab profile the starting setup on the target GPU, write or adapt a kernel for the operator from
   the reviewed pack, and build it in an isolated Brezel sandbox.
2. **Checks correctness.** Against the engine's own kernel on a hidden suite: shape sweeps, edge-case
   and unusual shapes, value distributions that defeat shortcuts, determinism, and a memory and race
   sanitizer.
3. **Measures.** A microbenchmark against the engine's own kernel, both replayed from a CUDA graph the
   way the engine replays decode steps, so launch overhead counts for neither. A kernel that cannot be
   captured in a graph fails here. Then your traffic is replayed as control, candidate, control on the
   same GPU, with the answer check. The kernel must be at least ×1.01 faster on its own and reach a 2%
   end-to-end gain.

In the run, the kernel setup reads as provisioning while it builds and checks, and measuring while it
is measured. Each kernel is pinned to the exact engine version and image it was measured with. A
change of engine means qualifying it again or turning it off.

## What a verdict means

| Verdict | Meaning |
|---|---|
| Qualified on the lab GPU | Every gate passed. The setup records the kernel speedup, the measured end-to-end change on your replayed traffic, and the lab's cost. It ends `inconclusive` with `kernel_qualified_not_servable`, because it cannot be served yet, and is never offered for roll-out. |
| Not qualified | It ran and failed a gate: correctness, shapes, sanitizer, kernel speed, the end-to-end target, memory, or quality. The lab's reasons are kept. |
| Failed | The lab stopped before a verdict, or the approval ended before the lane started. |

Only a qualified kernel's measured end-to-end change is a result. The share and efficiency that
planned it are why it was tried, never a predicted gain.

## Cost

A run has one approved spend cap, split evenly across its setups. A kernel setup provisions no
servers, so its share is the lab's hard limit. The plan sizes it for 2 GPU-hours on your lab host. The
lab adds the recorded cost of each stage at the prices your worker is configured with
(`INFERCRANE_KERNEL_GPU_HOURLY_USD` and the language model's token prices), and stops as soon as the
total passes the share. A stage already running finishes, so the total can pass the share by up to one
stage. The lab host and the language model are yours, inside your own cloud account.

## Turn it on

The kernel lane needs a complete [Accelerator Lab](/features/optimization#generate-a-custom-kernel)
configuration on the control plane, and:

```bash
INFERCRANE_OPTIMIZATION_KERNEL_LANE=true
```

On the GPU host, point the kernel adapter's replay directory at the worker's artifact directory, so
the files a run publishes are the files the qualifier reads:

```bash
infercrane-accelerator-worker --artifact-dir /srv/infercrane/artifacts ...
INFERCRANE_KERNEL_REPLAY_DIR=/srv/infercrane/artifacts
```

The control plane refuses `INFERCRANE_OPTIMIZATION_KERNEL_LANE` without the Accelerator Lab, and a run
planned with a kernel cannot be created or approved on a control plane that has the lane off.

## What it does not do yet

- **Serve a qualified kernel.** It needs the kernel and its reviewed integration built into a runtime
  image pinned to the engine version, then measured against the run's chosen setup as a follow-up change
  through the answer check and [Release Guard](/features/release-guard), and rolled out only on your
  approval. Until then a qualified kernel is evidence, not a change.
- **Measure decode in CUDA graphs.** Kernels replayed from a CUDA graph have no host operator, so their
  efficiency is unknown. Profile eager steps with `record_shapes` on.
- **Plan for vLLM's paged attention.** Its shapes do not carry context lengths, so its efficiency is
  unknown.

## Evidence so far

The two reviewed packs on an NVIDIA H100, inside the pinned vLLM 0.22.1 image (Triton 3.6.0, with
`compute-sanitizer` added as a test tool):

- **The hidden suite catches wrong kernels.** The pack's own correct kernel passed all six stages on both
  the visible and the hidden verification shapes, with the memory sanitizer reporting no errors. A
  kernel that ignores the router weights and one that swaps gate and up both failed at the first stage.
- **Timed call by call, the microbenchmark favored the kernel.** At four tokens on Qwen3-30B-A3B's
  expert shape (128 experts, hidden 2048, intermediate 768, top-8, BF16), the first evaluator timed
  vLLM's `fused_experts` at 234 µs and the pack's reference kernel at 171–172 µs, ×1.36.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/moe-experts-pack-h100-2026-11-20T043718Z.json).
- **End to end, the same kernel was correct but slower.** Qwen3-30B-A3B-Instruct-2507 in BF16 on one
  H100, 512 tokens in and 128 out, three runs per arm at 1, 4, and 16 concurrent requests, with the
  default setup measured before and after (drift under 0.5%):

  | Arm | Output tokens/s at 1 / 4 / 16 | Change against the default setup | Answer check |
  |---|---|---|---|
  | Default setup (FlashInfer CUTLASS experts) | 187 / 502 / 1,331 | — | reference |
  | vLLM's Triton experts | 195 / 478 / 1,136 | +4.4% / −4.6% / −14.6% | 24 of 24 identical |
  | Pack kernel for every call | 105 / 370 / 826 | −43.8% / −26.2% / −37.9% | 24 of 24 identical |
  | Pack kernel up to 64 tokens, vLLM's Triton above | 110 / 395 / 849 | −41.3% / −21.2% / −36.2% | 24 of 24 identical |

  The kernel's marker confirmed it ran in both kernel arms. Sending prefill to vLLM's Triton experts
  brought time to first token at one request back from 90 ms to 29 ms, but each decode step still took
  8.9 ms against 5.2 ms. The lane would mark this kernel not qualified.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/moe-experts-e2e-h100-2026-11-20T115713Z.json).
- **Replayed from CUDA graphs, the microbenchmark agrees with serving.** vLLM replays decode steps from
  CUDA graphs, so it pays no launch overhead per call; the first evaluator counted it. With 48 expert
  layers, 234 µs each would be 11.2 ms per token, more than the 8.1 ms a whole decode step took on
  vLLM's Triton experts at four requests. The evaluator now replays both kernels from a CUDA graph.
  Timed that way, vLLM's `fused_experts` took 129 µs, about 68% of what the H100's memory bandwidth
  allows, and the pack's kernel 169–171 µs, about 51%: ×0.75–0.76, below the ×1.01 the lane requires. At
  this shape on an H100, vLLM's Triton experts are not the weak kernel the published batch-1 H200
  figures describe, and the plan's 50% condition would not plan a kernel.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/moe-experts-pack-graph-h100-2026-11-20T120436Z.json).
- **The normalization pack, checked the same way.** Its reference kernel passed every stage on both
  suites with the memory sanitizer clean, and its two wrong kernels failed (numerical stability and
  determinism). Replayed from CUDA graphs at 128 rows of 1,024, it took 6.5–6.8 µs against vLLM's
  `fused_add_rms_norm` at 6.5–6.6 µs, ×0.96–0.99: not faster.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/residual-rmsnorm-pack-graph-h100-2026-11-20T120409Z.json).

A kernel speedup counts only when it is timed the way the engine runs it, and only the end-to-end change
is a result.

Two kernel screens of Qwen3.8 on an NVIDIA H200 (compute capability 9.0, SGLang source, Triton 3.7.1):

- **State commit, authored in Triton.** Every candidate passed all six correctness stages, with
  outputs bit-identical to the existing kernel (maximum absolute difference 0). The fastest was ×1.0066
  on the kernel, about 0.7%. The operator held 5.5% of the profiled time, so the projected end-to-end
  change was about 0.04%, below the 3% this screen required. It was not put forward for an endpoint.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen38-state-scatter-kernel-h200-2026-09-23T185014Z.json).
- **Gated DeltaNet, tuning the existing kernel.** No variant beat the existing configuration, and four
  of the eight failed parity. The existing kernel was kept.
  [Evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen38-gdn-kernel-h200-2026-09-23T181527Z.json).

An earlier handwritten CUDA residual-add + RMSNorm kernel for Qwen3-0.6B on an H100 was correct on every
shape but slower than both the Triton candidate and vLLM's own kernel, and was rejected
([evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen3-0.6b-cuda-h100-2026-09-20.json)).
The mixture-of-experts reference kernel above is the only custom kernel measured end to end so far, on
synthetic traffic rather than a recorded replay.
