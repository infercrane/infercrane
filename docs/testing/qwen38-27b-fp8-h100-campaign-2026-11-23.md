# Qwen3.8-27B-FP8 on H100: a speculation setting confirmed on fresh servers

On 23 November 2026 InferCrane's campaign judge measured the speculation option that the model's
publisher documents for `Qwen/Qwen3.8-27B-FP8` (multi-token prediction, three draft tokens)
against the publisher's plain vLLM command, on real-text chat traffic at 32 requests at once, with
one NVIDIA H100 per setup. In its first window the speculation setup served 32.1% more output tokens
per second than the current setup. Measured again on two fresh H100s, it served 33.1% more. A copy
of the current setup, measured the same way against it, came out 0.1% slower, and the judge rejected
it as no measurable difference.

This page is the receipt. The run's rules were committed before it started (commit `e55df535`) and
are in this repository unchanged. The harness commit that ran it (`tools/poc-modal` at `e55df535`)
and the control plane image (built from `43dbdbf5`) are not commits on main, so this page records
what ran; it is not a reproduction script in this release.

- [Packed evidence](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen38-27b-fp8-h100-campaign-2026-11-23.json): setups, servers, every
  measured turn, the judge's comparisons in both windows, the speculation counters, the answer
  check, the planner's record and the product's campaign report. No request rows, prompts or
  answer texts.

Local paths are anonymised as `<evidence>`. The JSON file names what was removed for publication
and the sha256 of each file it was made from.

### The setups

Each setup ran on its own server with `VLLM_USE_RUST_FRONTEND=1`, the model read from local weights
and served under its Hugging Face name.

**The current setup** (the publisher's vLLM command):

```text
--tensor-parallel-size 1 --enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3 --mm-encoder-tp-mode data --max-num-seqs 512
```

**The speculation setup** (the same plus the speculation option the recipe page documents):

```text
--tensor-parallel-size 1 --enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3 --mm-encoder-tp-mode data --max-num-seqs 512 --speculative-config {"method":"mtp","num_speculative_tokens":3}
```

**The copy** (the current setup again, on its own server, with only a seed added; it must not
win):

```text
--tensor-parallel-size 1 --enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3 --mm-encoder-tp-mode data --max-num-seqs 512 --seed 1
```

The rules measure the planner's first proposal beside the documented option and the copy. The
planner's first proposal was the documented option itself, so the campaign had three setups, not
four.

### The servers

| Server | Setup | What it served |
|---|---|---|
| S0 | current setup | The replay and the planner's diagnosis; removed before the campaign, not measured by the judge |
| S1 | current setup | Its own four turns, then its turns in the speculation setup's first window |
| S2 | speculation | The first window |
| S3 | speculation | Fresh server: the second window |
| S4 | current setup | Fresh server: its turns in the second window and in the copy's window |
| S5 | copy | The copy's window |

Each window compares two different H100s, one per setup, taking turns: the current setup, then
the setup, then the current setup again, and so on. The judge allows 0.75% for the difference
between two machines.

## Results

Output tokens per second for the whole server, the mean of the window's turns, as the judge
compared them. The change and its noise floor are the judge's.

| Window | Servers | Current setup | Setup | Change | Noise floor | Judge |
|---|---|---:|---:|---:|---:|---|
| Speculation, first window | S1 against S2 | 792 | 1,047 | +32.1% | 3.4% | improved |
| Speculation, fresh servers | S4 against S3 | 792 | 1,054 | +33.1% | 2.7% | improved |
| Copy of the current setup | S4 against S5 | 792 | 791 | −0.1% | 2.0% | no measurable difference |

The judge's change is computed from paired log ratios (each of the setup's turns against the
current setup's turns on either side of it), so it differs a little from the ratio of the two
means: 1,047 over 792 is +32.2%.

Every turn, output tokens per second (current setup, then the setup, taking turns; 100 requests a
turn):

| Window | Turns |
|---|---|
| Current setup alone (S1) | 787, 791, 787, 790 |
| Speculation, first window (S1, **S2**) | 788, **1,060**, 795, **1,048**, 795, **1,030**, 789, **1,048**, 793 |
| Speculation, fresh servers (S4, **S3**) | 793, **1,038**, 793, **1,063**, 788, **1,059**, 794, **1,058**, 792 |
| Copy (S4, **S5**) | 791, **793**, 795, **793**, 790, **793**, 792, **786**, 792 |

A turn took about 80 seconds with the current setup and 61 to 63 seconds with speculation.

**Speculation was used.** The engine's own counters, read by the product: 141,354 of 253,749
drafted tokens accepted in the first window (55.7%) and 140,983 of 254,796 on the fresh servers
(55.3%). The current setup and the copy drafted nothing.

**No request failed:** 31 measured turns of 100 requests and 7 warm-ups of 64, 3,548 requests, plus
the 100 replayed requests. Every measured setup's evidence names the corpus above.

**By the rules' pass bar the speculation setup is confirmed:** improved in the first window and
again on fresh servers, a gain above 5%, the answer check passed, the copy did not win, and
accepted tokens were recorded. InferCrane's decision was to propose rolling it out. Nothing was
activated: the run stops at the proposal.

### Latency, as changes only

Latency was measured from the laptop through the tunnel. It is comparable between setups and is
not what a user next to the server sees, so the rules publish no absolute latency from these
campaigns. The judge's changes and decisions:

| Metric, p95 | First window | Fresh servers | Copy |
|---|---|---|---|
| Request latency | −14.5%, improved (noise floor 2.3%) | −17.9%, improved (3.6%) | +0.1%, no measurable difference (7.4%) |
| Time to first token | +15.7%, no measurable difference (43.0%) | **+31.4%, regressed** (12.2%) | +22.7%, no measurable difference (33.4%) |
| Time per output token | −19.8%, no measurable difference (33.7%) | −15.1%, improved (13.0%) | −0.1%, no measurable difference (22.7%) |

**The winner was slower to its first token.** On the fresh servers the judge called p95 time to
first token regressed, by 31.4%. The campaign's objective was output tokens per second, and for
that objective the judge's guards are failed requests and answer length, not time to first token,
so the regression did not hold the winner back. The product's campaign report at the time showed
only the first window's change for this metric (+17.7%, no measurable difference) and raised no
warning. The cause of the regression was not measured. The report now warns when the chosen setup
got slower to its first token in either window ([optimization](/features/optimization)).

### Answers

The product's built-in answer check asked each setup and the current setup the same 24 short
prompts (at most 64 tokens each, greedy decoding with a fixed seed, reasoning off) and scored
each answer by word overlap with the current setup's answer: token F1 after lowercasing and
dropping punctuation. That measures which words appear and how often, not their order or the
exact text. The check passes at a mean of 95% and blocks under 90%. The speculation setup and the
copy each scored 1.0: every one of the 24 short answers had the same words as the current setup's.

How many of the 24 were word for word identical is not known: the product stores the scores, not
the answers. This is a guard against a setup that breaks answers, not a quality score, and no
quality claim is made.

### The planner

The planner was asked after the replayed traffic had ended. It read 0 requests running per server,
called the server lightly loaded ("Only 0 requests ran at once per server (threshold 4)") and put
the speculation option first, at priority 90, for that reason. Under the rules, the question of
whether the planner proposes this setup for a loaded server is not answered by this campaign.

## What this does and doesn't show

It shows that InferCrane's judge, on real H100s, confirmed a 32% to 33% gain in output tokens per
second for the publisher's documented speculation option over the publisher's plain command, on
this traffic at 32 requests at once, and did not crown a copy of the current setup.

It does not show:

- A result on one machine. Each setup had its own H100. How much two H100s differ here is bounded
  only by the copy (−0.1% on one pair of servers) and the judge's 0.75% allowance.
- A gain on another GPU, engine version, model, traffic shape or load.
- Anything beyond what the publisher documents: the confirmed setup is the publisher's own
  documented option.
- That the planner proposes this setup under load.
- Answer quality, or exact text.
- Absolute latency, or a better time to first token: it got worse on the fresh servers.

The tokens per second here count reasoning tokens and are not comparable with the
[H200 re-run's](/testing/qwen38-27b-fp8-h200-rerun-2026-11-23) cells, which switch reasoning off
and measure next to the server. Only the changes inside this campaign are its result.

**Read with care.** The laptop's one-minute load was 4.5 at the start and 4.3 at the end on 8 CPUs,
above the 4 the run wanted; the copy's −0.1% and the current setup's turns (787 to 795) say the
measurement stayed steady. The fresh speculation server (S3) sat farther from the laptop than the
others: median round trip 67 ms against 23 to 24 ms. It was refused three times for its host's
NVIDIA driver before it landed on the pinned one, and the copy's server was refused on two starts
before a third one did.

The product's campaign report is in the packed evidence. It is unsigned: no signing key was set in
the test cluster.

## Command

The run, from `<worktree>` at commit `e55df535`, as the launch record gives it, with the
spend-limit flag left out:

```bash
python3 tools/poc-modal/poc_modal.py run --traffic real-text --shape interactive --requests 100 --planner-setups 1 --engine vllm-0.34.0
```

The command replays the traffic through the current setup, records its shape, asks the planner,
and runs the campaign through the control plane: every setup, both windows, the answer checks and
the ranking.
