# Optimizer golden suite

The golden suite is a fixed evaluation of InferCrane's optimizer. Each task replays recorded
evidence, names the customer's current setup as the baseline, and states the decision a careful
reviewer would make from the raw numbers. A change to qualification, scoring, or the baseline rule
that turns a known loss into a promotion fails the suite.

The suite replays files. It starts no servers and allocates no GPUs, so it costs nothing to run.

## Run it

```bash title="Run the golden suite"
make test-optimizer-golden
```

The target runs the race-enabled Go tests and then prints both reports, the evaluator's decisions
and the [planner's choices](#planning-tasks):

```bash
infercrane optimize evidence golden \
  --file internal/optimizationevidence/testdata/golden/manifest.json
infercrane optimize evidence golden \
  --file internal/optimizationevidence/testdata/golden/planning.json
```

Add `--output json` for the full report, including each task's evaluator reason. The command exits
non-zero on any wrong decision or false win. `TestOptimizerGoldenSuite` runs the same tasks as part of
`go test`, so `make dev-check` fails on the same regressions.

## What the metrics mean

Every task ends in one of three decisions:

- `promote`: a candidate replaces the baseline.
- `keep_baseline`: the current setup stays.
- `reject_all`: nothing qualified, including the baseline, so no setup can be recommended.

| Metric | Definition |
| --- | --- |
| Win rate | Correct promotions divided by tasks that expect a promotion. A promotion is correct only when it names the expected candidate. |
| False win | The evaluator promoted a candidate in a task that expects `keep_baseline` or `reject_all`, or promoted a candidate in the task's `must_not_win` list. One false win fails the suite. |
| Missed win | A task expects a promotion and the evaluator kept the baseline or rejected everything. It is a wrong decision, so it also fails the suite. |
| Median gain over the baseline | The median relative improvement of the promoted candidate over the baseline, on the objective the evidence declares. Positive means better: more throughput, or lower cost or latency. |
| Measured GPU-hours per answer | GPU time inside the measured windows of every lane of every candidate in a task's evidence (`gpu_seconds_per_successful_request` × `successful_requests`), averaged over tasks. |

A gain is known only when the baseline qualified. When the baseline fails its own SLO, the promoted
candidate has no comparable baseline score, so the gain is reported as unknown and left out of the
median instead of being estimated.

Measured GPU-hours leave out provisioning, model loading, and warmup, so they are a lower bound on
what an answer cost. Two tasks that share an evidence file each count it in full. The laptop task
counts the laptop's GPU time. A lane with no successful requests or no recorded GPU seconds makes its
task's GPU time unknown; the report counts those tasks and leaves them out of the average.

## The baseline rule

The evaluator accepts two optional fields in `selection_policy`:

```json title="Declare the current setup"
{
  "selection_policy": {
    "id": "serverless-primary-slo-output-throughput",
    "version": 2,
    "objective": "maximum_slo_qualified_output_throughput",
    "lane_aggregation": "arithmetic_mean",
    "evidence_level": "screening",
    "qualification_before_scoring": true,
    "cost_tie_breaker": true,
    "baseline_candidate_id": "sglang-control",
    "minimum_relative_gain": 0.08
  }
}
```

Evidence without `baseline_candidate_id` is evaluated exactly as before: the best qualified score is
selected, and the input digest does not change. With a baseline, qualification still runs first, and
then:

1. If the baseline qualified, the best other qualified candidate is promoted only when its relative
   gain on the objective is larger than the noise floor. Otherwise the baseline is kept.
2. If the baseline failed qualification, the best qualified candidate replaces it, with an unknown
   gain.
3. If nothing qualified, the decision is `reject_all` and `winner_id` is empty.
4. If the baseline scored zero, the relative gain is undefined and the baseline is kept.

The default noise floor is 5%. The unchanged `sglang-0520-nextn-k4-bounded-graphs` recipe spanned
4.9% in lane-mean cost across six H200 screening receipts, so a smaller lead cannot be told apart from
re-measurement noise. `minimum_relative_gain` can raise the floor, for example when a campaign measured
larger drift between its control runs. It cannot lower it: lowering the floor is a code change that
must keep this suite passing. Treat 5% as a minimum; one speculative-decoding recipe varied by 30%
between two receipts, both of which failed quality gates.

The result adds a `baseline_decision` object with the outcome, the kept or promoted `candidate_id`,
the best `challenger_id`, its `relative_gain`, the `noise_floor`, a reason, and the rule's
`algorithm_version` (`baseline-noise-floor-v1`). Each candidate also reports `baseline` and
`relative_gain_over_baseline`. `winner_id` is the candidate to serve: the promoted candidate, the kept
baseline, or nothing.

## Add a task

<Steps>
  <Step title="Start from recorded evidence">
    Use an `infercrane.dev/optimization-evidence/v1` file from a real run. Recorded receipts live in
    `docs/testing/evidence/`. Put new laptop or fixture evidence in
    `internal/optimizationevidence/testdata/golden/`. Never edit measured values or build evidence to
    fit a case; boundary cases such as a gain of exactly 5% belong in unit tests.
  </Step>
  <Step title="Decide before you run the evaluator">
    Check every candidate's quality gates and every lane against the SLO. Then compute the objective
    for each lane and its mean, and compare the best challenger with the baseline against the noise
    floor. Write the decision and the numbers behind it down first, so the evaluator's output cannot
    shape the expectation.
  </Step>
  <Step title="Add the task to the manifest">
    Each task needs `id`, `evidence` (relative to the manifest), `baseline_candidate_id`,
    `expected_decision`, `categories`, and `why`. A `promote` task also needs `expected_candidate_id`
    and may list `must_not_win` candidates, such as one that breaks the SLO. Categories are
    `clear_win`, `inside_noise`, `slo_gate`, `quality_gate`, `baseline_fails_slo`,
    `laptop_rehearsal`, and `recorded_h100`. The test fails if any category except
    `baseline_fails_slo` loses its last task.
  </Step>
  <Step title="Run the suite">
    Run `make test-optimizer-golden`. If the evaluator disagrees with a new task, do not change the
    expectation to match. Find out which one is wrong. A pull request that changes an existing
    expectation must explain the new reasoning in that task's `why`.
  </Step>
</Steps>

To record a new laptop task, run the rehearsal on a quiet machine:

```bash
python3.12 tools/laptop-rehearsal/rehearse.py --requests 24 --output-dir /tmp/rehearsal
```

Keep a run only when the drift between its two control runs is below 10%. The checked-in run drifted
1.7%. An earlier attempt on a busy machine drifted 30% and was discarded.

## Planning tasks

The evaluator decides which measured setup wins. The planner decides which setups get measured at
all. `planning.json` (schema `infercrane.dev/optimizer-planning-golden/v1`) fixes the planner's
choices: each task is a proposal request with a recorded
[endpoint diagnosis](/features/optimization#choose-setups-from-the-endpoint-diagnosis) and the
order a reviewer would measure setups in. The same command detects the schema and runs the planner
instead of the evaluator. `TestPlanningGoldenSuitePasses` runs it under `go test`.

A task fails when any of these differ from the expectation:

| Field | Checks |
| --- | --- |
| `expected_order` | Every diagnosed setup by rank: `control`, then techniques such as `fp8-kv-cache`. The [setups that test the plan](/features/optimization#setups-that-test-the-plan) (roles `reference` and `copy`) are not part of the order, but `must_not_use_args` still applies to them. They count against `max_candidates`, so each task's limit leaves room for two of them. |
| `expected_state` | The plan state: `applied`, `not_ready`, `reliability_blocked`, `no_actionable_findings`, or `no_starting_setup`. |
| `must_not_propose` | Techniques no setup may apply. |
| `must_not_use_args` | Flag fragments no setup other than the control may carry, such as a method that lost on recorded hardware. |
| `expected_skipped` | Chosen techniques the plan must record as skipped, with a reason. |
| `expected_needed_evidence` | Exactly the evidence the plan asks for: `fresh_traffic`, `engine_metrics`, or `fewer_errors`. |

the rule table before you run the planner, and record the reason in `why`. Categories are
`kv_pressure`, `queueing`, `host_bound`, `prefill`, `prefix_reuse`, `decode_low_concurrency`,
`decode_high_concurrency`, `gpu_profile`, `gpu_trace`, `not_ready`, `reliability`,
`recorded_gpu_run`, `publisher_checkpoint`, `pinned_image_setups`, and `accelerator_kernels`, and
the test fails if any of them loses its last task. A change to a rule, priority, or flag value must
bump the rule set version (now `diagnosis-technique-rules-v12`) and explain each changed expectation
in its task's `why`.

## Planner gym

Planning tasks check the order a reviewer wrote down. The planner gym checks whether the planner's
first choice wins on cells that were measured. It needs no GPU and runs in seconds:

```bash title="Score the planner on measured cells"
make planner-gym
```

The cases are one file per measured campaign set, under `internal/optimizer/testdata/planner-gym/`,
written by `tools/planner-gym/build_cases.py` from the runs' own records. The file names every
record it read with its sha256. Each case is one cell (one kind of traffic at one load) and one
current setup. The gym:

1. builds the endpoint diagnosis for that cell and setup;
2. asks the planner, as a customer would;
3. takes the first proposed setup the GPU can run. A setup whose arguments the engine refuses, such
   as more requests at once than its cache holds, is skipped, as a campaign skips it. With nothing
   left, the current setup stays;
4. compares that setup with the best setup measured in the cell.

There are two kinds of case, scored apart:

| Kind | Planner input |
| --- | --- |
| Map window | Rebuilt from the readings inside the measured window: requests running and waiting, cache use, the engine's cache layout, prompt and answer lengths, first-token and request times. It goes through the product's own readiness assessment. A reading the run did not record is left out, so no rule fires on it. |
| Product reading | The diagnosis the product recorded when it was asked about the same cell, or before a campaign. Values the agent did not relay at the time are added from the same setup's measured servers, and the case names each one. |

Every case is scored in two columns: all output tokens per second, and output tokens per second of
requests whose first token came within the limit the file states. The gym asks the planner with
that limit set for the second column.

- A **hit** is a first proposal whose measured range reaches the best setup's: inside the spread
  between servers counts as a hit.
- **Given up** is the share of the best setup's output the customer would not get. It assumes the
  judge keeps the better of the proposal and the current setup.
- **Unknown** means the first proposal makes a setup no run measured in that cell. It is counted
  apart and never as a hit or a miss.

Each case also says whether the planner's rules were written from that cell. The gym reports cells
the rules were built from apart from the rest: a rule that scores well on its own cells shows
nothing about other traffic. `TestPlannerGym` fails when a table's hits fall below its floor. A
change that lifts a score raises the floor in the same commit; a floor is never lowered to let a
change pass. `INFERCRANE_PLANNER_GYM_OUT=FILE` also writes the table as Markdown.

Two more uses of the same code:

- **Score another run.** `build_cases.py --screen SCREEN.json` turns a screen (every setup in turn
  on one machine, `tools/fast-track-map`) into a cases file; `INFERCRANE_PLANNER_GYM_CASES=FILE make
  planner-gym` scores the planner on it, asked from the screen's current setup. The floors hold for
  the committed file only. A screen has one machine, so its spread is what the current setup's
  two runs (first and last) differ by: the best setup is ahead of another only by more than that,
  as `screen.py` decides its finalists. Without two runs of the current setup that difference is
  unknown and only the best setup itself is a hit.
- **Predict before measuring.** `build_cases.py --server SERVER.json` turns one measured server of
  the current setup into a cases file, and

  ```bash
  INFERCRANE_PLANNER_PREDICT_CASES=cases.json INFERCRANE_PLANNER_PREDICT_OUT=predictions.json \
    go test -count=1 -run '^TestPlannerPredict$' ./internal/optimizer
  ```

  writes, per cell and per goal (all output, and useful output), the diagnosis, every proposal with
  its arguments, what was skipped and why, and the cache room. Written and kept before the other
  setups are measured, it is what a later run scores: with `INFERCRANE_PLANNER_GYM_CASES` set to
  the screen's cases file, `INFERCRANE_PLANNER_GYM_PREDICTIONS=predictions.json` adds a table per
  goal that scores the file as written, by the same judge, without asking the planner again.

A small model's cases file carries `model_memory` (served weight bytes, KV cache bytes per token)
when `build_cases.py` knows the model, as the product's model check would read it, and the gym adds
it to each diagnosis. A screen whose cells a rule set was written from, after the screen was seen,
marks them `rules_built_from`.

What the gym cannot show: how the planner does on another model, engine or GPU than the file's,
and whether a setup it proposes outside the measured ones would win. Those stay unknown until a
run measures them.

## Limits

- The tasks replay screening evidence, mostly from one model and one workload family on H200.
- The win rate rests on three expected promotions. Add tasks before reading much into it.
- The suite checks decisions on recorded evidence. It does not check that a new campaign measures
  correctly; the campaign's own control runs and noise-floor checks do that.
- Planning tasks check which setups are measured and in what order, not whether they win. Only the
  two RTX 4090 tasks rest on a measured outcome; the rest encode the rule table.
