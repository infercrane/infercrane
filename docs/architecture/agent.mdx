# InferCrane agent

The InferCrane agent is one process that runs beside a customer's model server: on a laptop, a
workstation, an on-prem rack, any Kubernetes cluster, or any cloud. It only dials out, over HTTPS,
so the control plane can observe a server it cannot reach: a server behind NAT, on loopback, or in
a private network. It can also serve that server's traffic itself, as the data plane inside the
customer's cloud, and run candidate setups in the customer's cluster. Prompts and completions then
never reach InferCrane. This page is the authoritative design. The quickstart is
[Run on this machine](/run-on-this-machine); the [list of every field that leaves your
cloud](#what-leaves-your-cloud) is below.

The agent is part of the open-source core (Apache-2.0). It ships in the `infercrane` CLI binary as
`infercrane agent`, and any control plane, hosted or self-hosted, accepts agents.

```text
customer machine                                    InferCrane control plane
┌────────────────────────────────────────┐          ┌──────────────────────────────┐
│ app ──► local gateway (optional) ──┐   │          │ /api/v1/agent/sync           │
│                                    ▼   │  HTTPS   │   agent key only             │
│ vLLM · SGLang · llama.cpp ◄── infercrane agent ───►│   same parser as a scrape    │
│ Ollama · LM Studio   (probe, /metrics)  │ outbound │   target_measurements        │
│ nvidia-smi · sysctl · sysfs             │   only   │   request_records (shapes)   │
└────────────────────────────────────────┘          └──────────────────────────────┘
       nothing listens for the control plane            never dials the agent's servers
```

## What the agent does

| Capability | State |
|---|---|
| Find vLLM, SGLang, llama.cpp, Ollama, and LM Studio on ports 8000, 30000, 8080, 11434, 1234, or any `--server URL` | Implemented |
| Read engine and version (`/version`, `/server_info`, `/props`, Ollama `/api/version`), models (`/v1/models`), the loaded model (Ollama `/api/ps`, LM Studio `/api/v0/models`), and health | Implemented |
| Send an API key to the servers named with `--server` (`--token-env`, `--auth-header-env`); never to InferCrane, and never to a server found on a default port | Implemented |
| Register each healthy server as an observe-only endpoint | Implemented |
| Relay engine metrics so Observe, readiness, and bottleneck diagnosis work | Implemented for vLLM, SGLang, llama.cpp |
| Record content-free request shapes through the optional local gateway | Implemented |
| Report NVIDIA GPUs (`nvidia-smi`, which reads NVML), Apple Silicon, and AMD GPUs with unknowns named | Implemented; Apple and AMD telemetry is not collected |
| Serve an agent-managed endpoint inside the customer's cloud with InferCrane API keys, routes, admission, and request quota ([data plane](#the-agent-as-the-data-plane)) | Implemented |
| Run a candidate setup in the customer's Kubernetes namespace, measure it against the current setup with AIPerf, and run the answer check there ([candidate runs](#candidate-runs)) | Implemented for Kubernetes |
| Install in Kubernetes with a Helm chart (`deploy/helm/infercrane-agent`) | Implemented |
| Run candidates by restarting an engine the agent launched on one machine (`--launch`) | Designed below; not implemented |

Ollama and LM Studio expose no engine metrics. Their queue, cache, and per-token internals stay
unknown, and the agent says so instead of estimating them.

## Trust model

### The control plane never dials an agent's servers

A server registered by an agent becomes a target with `agent_id` set. The control plane treats that
target as unreachable from itself:

- The reconciler's adopted-target probe skips it. Health comes only from the agent's reports.
- Endpoint compilation never publishes a route to it, whatever its ownership says.
- `deploy --targets` and the apply path cannot bind it.
- Promotion to `traffic-managed` is refused. Its traffic is served by the agent instead: the
  endpoint becomes `agent-managed` (see [the agent as the data plane](#the-agent-as-the-data-plane)),
  or stays observe-only with the optional local gateway recording request shapes.
- `infercrane connect` reuses a target by URL only when no agent owns it, so two machines that both
  serve `http://127.0.0.1:8000` stay two targets.

If its agent has not reported a server for three minutes, the server is marked unhealthy, because
nothing knows it is healthy. A revoked agent's servers are marked unhealthy at once.

A server is identified by its host and port. If the server at that address now serves a different
model, its health, metrics, and traffic are refused for the old endpoint, which is marked unhealthy
with the reason, instead of landing on the wrong endpoint. If an agent's endpoint is deleted, the
running agent registers the server again on its next pass.

### The agent key

An agent key is a principal of kind `agent`. It is minted in one of two ways and shown once:

- `infercrane agent run`, when the CLI is signed in (`infercrane login`) and no agent key is saved
  for this context. The CLI asks for a key with its own sign-in, saves it in the OS keychain (or a
  separate `0600` file), and never uses the CLI's own key in the agent loop.
- `POST /api/v1/agents` (or `infercrane agent create NAME`), for a machine where nobody signs in.
  Pass the key in `INFERCRANE_AGENT_KEY`.

Creating or revoking an agent requires the `deploy` action. Only the key's SHA-256 digest is
stored, as for every credential. Agent keys do not expire; revoke and replace them instead.

An agent key may:

- call the agent API (`/api/v1/agent/*`: sync, servers, data-plane, quota-leases, commands), and
  nothing else;
- register up to 32 servers as observe-only endpoints in its own workspace, each with its own
  logical model (it cannot attach to a model another endpoint uses);
- report health, hardware, filtered engine metrics, and request shapes for its own servers;
- pull the data plane of its own agent-managed endpoints, lease request quota, and take the
  candidate runs queued for it.

An agent key may not call any other control-plane route (HTTP 403), invoke inference on the
gateway (HTTP 403), read other agents' servers, deploy, promote, delete, queue work for itself, or
read workspace data. Relayed evidence for a server key that this agent did not register is
rejected, and a data-plane request shape must name the agent-managed binding of that server.
Making an endpoint agent-managed, queuing a candidate run, and changing residency need a person or
service key with the `deploy` action; an agent key cannot do any of them.

### What leaves the machine

The complete list, field by field, is [What leaves your cloud](#what-leaves-your-cloud). In short:
hardware inventory, server addresses and health, filtered engine metrics, content-free request
shapes, quota lease counts, and candidate-run numbers. Never prompts, completions, tool calls,
message content, request or response headers, API keys, eval prompts, answers, or engine logs.

The agent filters a scrape with the same family list the control plane's parser reads, so an
unrelated metric (and any label it carries) is dropped before the request is built. Request hashes
use HMAC-SHA256 with a random 256-bit secret created on the machine the first time the agent runs
and kept beside its saved key (`agent-credentials.json`, mode `0600`). The secret is independent of
the agent key and is never sent, so neither the control plane nor anything that sees the agent's
requests can derive it or test a guessed prompt against a hash. Hashes only tell whether two
requests shared a system prompt or a session, and they stay comparable when the agent key is
rotated.

Strings read from a local server (versions, details, model names) are stripped of control
characters and cut on a character boundary before they are sent; a model ID that is not clean text
is left out rather than altered.

## Protocol

The agent makes every call; the control plane answers. There is no inbound port, no tunnel, and
no long-lived connection that a proxy or load balancer has to keep open.

| Call | When | Body |
|---|---|---|
| `POST /api/v1/agent/sync` | At start, then every poll interval (default 15 s; the control plane may advise 5–60 s) | Protocol version, agent version, hardware, servers and health, metric relays, request shapes |
| `POST /api/v1/agent/servers` | When a new healthy server appears | Server key, endpoint name, model, engine, address |
| `GET /api/v1/agent/data-plane?generation=` | With `--serve`: at start and every poll interval | The generation the agent holds; the answer is the snapshot, or `unchanged` with a new validity window |
| `POST /api/v1/agent/quota-leases` | With `--serve`, when the workspace has a request quota and the agent's lease runs low | The current minute and a request count (at most 1,000) |
| `GET /api/v1/agent/commands?wait=25s` | With `--executor`: a long poll, held at most 25 s | Nothing |
| `POST /api/v1/agent/commands/{id}` | Progress every phase and every 2 minutes, then the result | State, phase, failure code, and the [candidate-run result](#what-leaves-your-cloud) |

- Bodies are gzip-compressed JSON, at most 8 MiB after decompression. Unknown fields are ignored
  so a newer agent can add fields within one protocol version (`infercrane.agent/v1`).
- The agent honours `HTTPS_PROXY` and the CLI's TLS settings
  (`INFERCRANE_CLIENT_TLS_CA_FILE`, client certificates). It sends its key only over HTTPS, except
  to a control plane on the same machine.
- The control plane validates each server report, metric relay, and request shape on its own and
  returns the ones it refused in `rejected`; one bad item never fails the sync or the heartbeat. If
  a whole sync is refused as invalid (HTTP 4xx), the agent drops that batch's evidence instead of
  resending it, so a bad item cannot block it forever. Other failures are retried with backoff up to
  five minutes. Undelivered request shapes stay in a bounded buffer (10,000; the oldest are dropped
  and counted). The agent keeps each sync under 6 MiB of scrapes, sending baselines and then whole
  relays in a later sync.
- A key minted a moment ago may not be in every replica's credential snapshot yet; the agent retries
  an unknown key for ten seconds at start, and treats it as fatal after that.
- Request shapes carry an agent-generated ID, so a retried sync records each request once. The
  control plane corrects the agent's clock skew from the sync's `sent_at`.

Polling was chosen over a stream because it works through every corporate proxy, needs no sticky
sessions across control-plane replicas, and survives restarts on either side. Each sync is
stateless on the control plane (see the next section), so any replica can answer it. The command
long poll holds one outbound request open for at most 25 seconds; a replica checks for new commands
every 2 seconds and answers at once when a command is queued through it.

### Relayed metrics are treated like scraped metrics

The control plane's own collector compares the current scrape of an engine with the oldest scrape
of the same engine process in the last five minutes. The agent keeps the same window locally and
sends both texts in one relay: the current scrape and that baseline. The control plane parses both
with `metrics.ParseEngine`, checks they come from one engine process, and derives measurements with
`metrics.EngineMeasurements`, exactly as for a scrape it made itself. Rows carry the same names,
units, sources (`vllm_metrics`, …), and 90-second validity, keyed by the target in
`target_measurements` instead of a deployment revision. Monitoring and readiness read
deployment-bound and target-bound rows through the endpoint's bindings, with no engine, runtime, or
provider branch. A scrape older than its validity window is rejected, not stored as current.

## Traffic

By default the agent sees no traffic: requests go straight from the application to the server.
The endpoint, the CLI, and the agent detail API all say so ("traffic not visible: requests go
straight to the server").

`--gateway 127.0.0.1:4000` starts a pass-through in front of one server. The application points at
the gateway instead of the server. Every request and response passes through unchanged, including
the application's own `Authorization` header; the agent never adds the server key it holds. For
`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, and `/v1/responses`, the gateway reads
the model name, the streaming flag, and token usage on the machine, and records only the shape listed
above. Give it a loopback address; any other address exposes the gateway, and the server behind it,
to the network.

## Upgrade and revocation

- **Upgrade.** Every sync reports the agent version. A control plane may set a minimum version and
  then answers older agents with HTTP 426; the agent stops and prints the install command. A newer
  recommended version is shown as advice only. The agent never updates itself: upgrades go through
  the package that installed it (release binary, Homebrew, container image), so what runs on a
  customer's machine is always a build the customer chose.
- **Revocation.** `DELETE /api/v1/agents/{id}`, `infercrane agent revoke NAME`, or the dashboard
  disables the agent's principal, marks the agent revoked, and marks its servers unhealthy. The
  agent routes re-check the agent's row on every request, so the next sync gets HTTP 401: the code
  is `agent_revoked`, or `agent_unauthenticated` once the credential snapshot has dropped the key
  (within about a second). The agent then stops, its local gateway included, and sends nothing more.
  A health report from a sync that raced the revocation is not applied. Revocation therefore takes effect within
  one poll. The endpoints remain, so their history stays readable.
- **Rotation.** Create a new agent key, restart the agent with it, then revoke the old agent.

## The agent as the data plane

An endpoint whose server only an agent reaches can be served by that agent, inside the customer's
cloud. The application calls the agent with an InferCrane API key; the agent authenticates the key,
applies the endpoint's admission policy and the workspace's request quota, routes to the server,
streams the answer back, and records a content-free request shape. Prompts and completions stay in
the customer's network. The hosted control plane sees none of them.

```text
customer cloud                                                    InferCrane control plane
┌──────────────────────────────────────────────────────┐          ┌────────────────────────────┐
│ app ── InferCrane API key ──► agent  --serve :8080   │          │ GET  /agent/data-plane      │
│                               │ authenticate (digests)│ outbound │   routes by server key      │
│                               │ admission, quota lease│  HTTPS   │   API key digests           │
│                               │ route ─► vLLM / SGLang│ ───────► │   admission, request quota  │
│                               ▼                       │   only   │ POST /agent/quota-leases    │
│                   content-free request shapes ────────┼────────► │ POST /agent/sync            │
└──────────────────────────────────────────────────────┘          └────────────────────────────┘
        prompts and completions stay here                    never routes to, dials, or proxies it
```

### Ownership and residency

| Ownership of an agent's server | Who serves its traffic | How it gets there |
|---|---|---|
| `observe-only` | The application, straight to the server (or through the optional pass-through `--gateway`) | `infercrane agent run` registers it |
| `agent-managed` | The agent's data plane (`--serve`), with InferCrane keys, admission, and quota | `PUT /api/v1/adoptions/endpoints/{name}/ownership` with `{"ownership_mode":"agent-managed"}`, by a key with `deploy` |
| `traffic-managed` | Refused for an agent's server: the control plane cannot reach it | |

Making an endpoint agent-managed also sets its **residency** to `customer-cloud`, in the same
transaction. Residency is a property of the endpoint (`GET /api/v1/endpoints/{name}` shows it,
`PUT /api/v1/endpoints/{name}/residency` sets `any` or `customer-cloud`):

- A `customer-cloud` endpoint accepts only bindings to servers an InferCrane agent owns. A
  database trigger refuses any other binding, whichever code path adds it: a hosted or
  InferCrane-operated deployment, an external fallback, or a Model API supplier. Setting
  `customer-cloud` on an endpoint that already has such a binding is refused (HTTP 409,
  `residency_conflict`) until the binding is removed.
- The hosted gateway answers a request for a `customer-cloud` endpoint with HTTP 403
  (`residency_error`) and never forwards it, not even to another supply such as a hosted Model API
  of the same name. The playground uses the same gateway path. Asynchronous inference refuses the
  endpoint before storing anything (HTTP 403, `residency_customer_cloud`).
- Returning to `any` is an explicit, audited change by a key with `deploy`. Returning the server to
  `observe-only` stops the agent serving it; the endpoint stays `customer-cloud`.

The endpoint's state reads `serving` while its agent reports a healthy agent-managed server, and
`degraded` when it does not. Hosted routes for it are never published.

### What the agent pulls

`GET /api/v1/agent/data-plane` returns a snapshot of exactly what this agent needs, and nothing
about other agents or other endpoints:

| Field | Content |
|---|---|
| `routes` | Each agent-managed endpoint of this agent's servers: endpoint, logical model, environment, and serving plan identities, the routing policy, and per binding the binding and target IDs, the agent's own **server key**, upstream model, engine, weight, and protocol capabilities |
| `credentials` | SHA-256 digests of the workspace's live, non-agent API keys that may call at least one of those endpoints, with role, scopes, endpoint restrictions, and expiry. Keys restricted to other endpoints, agent keys, disabled and expired keys are left out. No key itself is ever sent; digests are what the control plane stores |
| `admission` | The admission policy of each of those endpoints (concurrency, queue depth and timeout, request timeout, request and output limits, priorities, retry budget) |
| `request_quota` | The workspace's hard request rate, when it has one |
| `generation`, `valid_until` | A digest of the content, and how long the agent may serve on it (15 minutes) |

A route names a server by the agent's server key, never by address. The agent resolves the key to
an address it detected itself, and routes only to servers it registered and currently sees as
healthy; a key it does not know is never routed to, whatever the snapshot says. The agent
validates every snapshot before using it.

### How the agent serves

The agent runs the same gateway code as the hosted control plane (`internal/gateway`):
authentication against the digests, endpoint restrictions, admission, request quota, weighted or
primary-fallback routing, streaming, cancellation, and retries. The application's API key is not
forwarded to the model server; the agent sends the server's own key (`--token-env`), which never
leaves the machine.

- **Request quota.** The workspace limit is shared with every other agent and the hosted gateway
  through the same durable minute-window allocator. The agent leases at most 1,000 requests at a
  time (`POST /api/v1/agent/quota-leases`). If it cannot get a lease, requests get HTTP 429; they
  are never let through unmetered.
- **Staleness.** The agent refreshes the snapshot every poll interval. If it cannot refresh for 15
  minutes it stops serving (HTTP 503, `data_plane_stale`), because a revoked key could otherwise
  keep working. Revoking the agent stops it at its next poll.
- **Records.** Each request becomes a request shape with `source: data-plane` and the binding it
  was routed to; the control plane stores it as a request record with compute mode
  `agent-data-plane`. Monitoring, readiness, replay capture, and optimization read these records as
  they read the hosted gateway's.

## Candidate runs

The control plane can ask an agent to try a candidate setup in the agent's own cluster. A person or
service key with `deploy` queues the run; the agent takes it over its outbound long poll and runs
it; only numbers come back.

```bash
curl -X POST "$INFERCRANE_URL/api/v1/agents/kind-cluster/candidate-runs" \
  -H "Authorization: Bearer $INFERCRANE_API_KEY" -d @candidate.json
```

A candidate run names the endpoint whose server is the current setup, the candidate's model,
image (pinned by digest), argv and extra engine arguments, accelerator and count, the AIPerf load
(requests, concurrency, input and output tokens, streaming), the eval set for the answer check, and
a timeout. It can never carry a shell: an entry point that is a shell or an interpreter is refused,
and arguments with substitutions are refused.

The agent then, in its own namespace:

1. checks the image against its operator's allowlist (`--allow-image`, Helm
   `executor.allowedImages`) and the accelerator against `--allow-accelerator`, before applying
   anything;
2. starts the candidate with the same namespaced Kubernetes provider the control plane uses
   (`provision.Kubernetes`: one Deployment and one Service, server-side apply, no cluster-scoped
   permission) and waits for it to be ready;
3. measures the current setup, the candidate, and the current setup again with AIPerf, so the
   result carries a same-setup noise figure;
4. runs the answer check on both: the built-in public suite (`default`), or an eval set the
   operator keeps beside the agent (`local:NAME`, Helm `executor.evalSets`). Eval prompts and every
   answer stay in the cluster; only per-prompt agreement scores and digests are sent;
5. deletes the candidate, also when the run fails or is cancelled.

Runs on one agent go one at a time, so two candidates never compete for the same accelerators.
`GET /api/v1/agents/{id}/candidate-runs/{run}` shows the state, the current phase, and the result;
`DELETE` cancels it, and the agent removes the candidate on its next report. A run whose agent
stops reporting is handed out again (at most three times), and a run past its deadline expires.

Candidate runs are separate from optimization runs today: their results are stored with the run,
not ranked against other candidates or promoted. Feeding them into ranking, Release Guard, and
promotion is the next step.

### Taking turns on one machine (designed, not implemented)

On a single machine the agent will run candidates only for an engine it launched itself, never for
a process it merely observes:

```bash
infercrane agent run --launch -- vllm serve Qwen/Qwen3-8B --port 8000
```

It will drain the data plane (new requests wait, bounded), stop the engine, start it with the
candidate flags, measure it, and restore the original setup, in a window the customer approves.

## Kubernetes

The Helm chart in `deploy/helm/infercrane-agent` installs the agent as one Deployment:

```bash
kubectl -n models create secret generic infercrane-agent-key --from-literal=key=$AGENT_KEY
helm install agent deploy/helm/infercrane-agent -n models \
  --set controlPlane.url=https://control.example.com \
  --set 'agent.servers[0]=http://vllm.models.svc:8000' --set agent.endpointName=support-bot \
  --set executor.enabled=true --set 'executor.allowedImages[0]=vllm/vllm-openai'
```

| Object | Purpose |
|---|---|
| Deployment `<release>-infercrane-agent` | The agent: no inbound port for InferCrane, a read-only root filesystem, no privilege escalation, all capabilities dropped |
| Service `<release>-infercrane-agent` | The data plane for applications in the cluster (`http://<release>-infercrane-agent.<namespace>.svc:8080/v1`) |
| Secret `<release>-infercrane-agent-hash-key` | The request-hashing key, random, kept when the release is removed so hashes stay comparable |
| Role and RoleBinding (with `executor.enabled`) | Exactly the provider grant of `deploy/kubernetes/base/provider-rbac.yaml`: Deployments and Services, read-only PVCs, in one namespace. No Secrets, no Pods/exec, nothing cluster-scoped |
| Secret `<release>-infercrane-agent-worker`, ServiceAccount `infercrane-runtime` | The candidate pods' API key and identity (no API token mounted) |
| ConfigMaps | The control plane's private CA, and local eval sets, when set |

`scripts/test-agent-data-plane-kind.sh` installs the chart on a kind cluster and proves the data
path end to end (see [Proof](#proof)).

## What leaves your cloud

Every field the agent sends to the control plane, by call. Nothing else is sent: no prompt,
completion, tool call, message content, request or response header, caller request ID, API key,
local server key, hashing key, eval prompt, answer, engine log, or Kubernetes object.

| Call | Fields |
|---|---|
| `POST /agent/sync` (envelope) | protocol, agent version, OS, architecture, sent-at time; hardware state, and per accelerator kind: vendor, name, count, memory, driver, source, and the fields it could not read; limitations; the pass-through gateway's listen address and server key, when used |
| `POST /agent/sync` (servers) | per server: server key, engine, engine version, address as the agent reaches it, model names, loaded model, health and its detail, whether metrics and authentication are configured |
| `POST /agent/sync` (metrics) | per server: the current and a baseline engine scrape, filtered on the machine to the families InferCrane parses, with their ages |
| `POST /agent/sync` (request shapes) | per request: a random shape ID, server key, start time, operation (chat, completion, embeddings, responses, other), requested model name, response model name, status code, latency, time to first byte, queue time, retry count, streaming flag, input and output token counts, error type, and HMAC-SHA256 hashes (keyed with a secret that never leaves) of the system prompt, session ID, and parent session ID, tool pause time; with the data plane also the binding ID |
| `POST /agent/servers` | server key, endpoint name, model, engine, address |
| `GET /agent/data-plane` | the generation the agent holds |
| `POST /agent/quota-leases` | a minute and a request count |
| `GET /agent/commands` | nothing |
| `POST /agent/commands/{id}` | state, phase, failure code and a bounded failure detail written by the agent; for a finished candidate run: per measurement (current setup, candidate, current setup again) the tool and version, request, success, and failure counts, duration, request and output-token throughput, and p50/p95 time to first token, time per output token, and latency; the noise figure; the eval-set name, its digest, the prompt count, one agreement score per prompt, the mean, the verdict, and a digest committing to the answers; seconds until ready, the candidate image reference, and whether it was cleaned up |

## Proof

`internal/testtools/agentintegration` holds the hermetic proof: an application calls the agent's
data plane with an InferCrane key, a candidate run goes through the command channel, and a
recorder on the control plane's side asserts that no prompt, answer, eval prompt, key, caller
request ID, or session ID was sent. `scripts/test-agent-data-plane-kind.sh` repeats it on a kind
cluster with the Helm chart: the control plane, its PostgreSQL, and a TLS proxy that keeps a copy
of every byte the agent sends run in one namespace; the model server and the agent in another.
The test then checks the bytes on the wire, a dump of PostgreSQL, and the control plane's logs for
the prompt, the answers, the eval prompts, and the key. Its model servers are the development fake
engine (no GPU, no weights): the run proves the data path and the command channel, not engine
performance.

## Limits

- Health and metrics are as fresh as the last sync (15 s by default; scrapes every 30 s).
- One agent observes one model per server. A server that lists several models and has none loaded
  needs `--model`.
- Apple Silicon and AMD GPUs are reported as detected, with GPU telemetry unknown. Intel GPUs are not
  reported.
- The data plane forwards a local server's key only as a bearer token (`--token-env`); a server
  that needs another header scheme can be observed but not served.
- One agent serves one replica's worth of traffic; run more replicas of the Helm Deployment for
  more. Each replica leases quota on its own.
- Candidate runs need Kubernetes; the single-machine `--launch` mode is designed, not implemented.
  Their results are not yet ranked or promoted by optimization runs.
- AWS self-serve connections are the next slice of this plan: they reach private-network workers
  through this agent.
