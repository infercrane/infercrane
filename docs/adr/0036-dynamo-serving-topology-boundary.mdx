# ADR 0036: Dynamo serving topology boundary

Status: accepted. This supersedes only ADR 0019's deferral of Dynamo; the base Kubernetes and KServe decisions remain unchanged.

## Context

InferCrane owns stable endpoint identity, immutable revisions, durable operations, Release Guard,
traffic policy, and evidence. NVIDIA Dynamo can own a Kubernetes-native serving graph containing a
frontend, router, planner, and vLLM or SGLang worker pools. Treating both systems as replica routers
or autoscalers would create competing mutation owners and unsafe scale-down behavior.

The integration must preserve a simple model deployment path while exposing disaggregated serving,
KV-aware routing, and cache intent to teams that deliberately choose those trade-offs.

## Decision

- `serving` is an immutable, provider-neutral revision field. An empty field preserves the standard
  provider/runtime path.
- `backend: dynamo` requires `cloud: kubernetes`, `provider.adapter: kubernetes-dynamo`, and one
  outer InferCrane graph replica. Dynamo owns every internal worker count and child object.
- InferCrane applies one namespaced `nvidia.com/v1beta1 DynamoGraphDeployment` parent using strict
  server-side dry-run and server-side apply. It never force-steals fields.
- The request path is application → InferCrane stable endpoint → Dynamo frontend → Dynamo-selected
  worker. The control path is InferCrane reconciler → Kubernetes API → Dynamo operator.
- Aggregated and disaggregated topology are explicit. KV-aware routing is explicit. NIXL transfer is
  delegated to Dynamo/runtime configuration; InferCrane does not implement KV transport.
- KVBM, LMCache, and HiCache are alternatives. Only aggregated vLLM with explicit KVBM memory and
  storage bounds is locally executable in the first adapter. Other combinations fail before mutation.
- Dynamo Planner ownership is represented in the contract but fails closed until DGDSA/Planner
  lifecycle and metrics ownership are qualified.
- The adapter receives only Secret references and immutable image digests. It neither reads nor
  persists Secret values.

## Consequences

The default workflow stays small. Advanced teams can reproduce and audit a complete serving graph
through YAML/API without leaking CRD structure into the InferCrane core. A single parent identity
makes retries, adoption, inventory, and deletion deterministic.

Local tests prove contract validation, manifest generation, Kubernetes ownership, lost-response
adoption, and stale-status handling. They do not prove GPU compatibility, NIXL behavior, cache
performance, or that disaggregation improves a workload. Those claims require real-cluster evidence.

## Alternatives rejected

- **Put the adapter in the data path:** adds control-plane coupling and an avoidable request hop.
- **Let InferCrane and Dynamo both autoscale:** creates two writers with incompatible drain state.
- **Copy Dynamo scheduling or KV logic:** duplicates an upstream inference engine and prevents
  independent upgrades.
- **Enable every cache combination from CRD compatibility alone:** confuses schema acceptance with
  executable runtime qualification.
