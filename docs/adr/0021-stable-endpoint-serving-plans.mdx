# ADR 0021: Stable endpoints and immutable serving plans

- Status: accepted
- Date: 2026-08-11

## Context

The v1 request alias is the deployment name. This makes a concrete lifecycle resource double as the
application contract and prevents a release from comparing or switching between different providers,
runtimes, imported targets, or future regional realizations without changing that contract.

## Decision

Introduce tenant-scoped `LogicalModel`, `Environment`, `Endpoint`, `BackendBinding`, and immutable
`ServingPlan` resources. An endpoint owns active and candidate plan pointers. Plans contain only
binding identities, routing policy, bounded weights/order, and a canonical digest. Bindings refer to
concrete deployments or external targets; provider/runtime configuration remains below that boundary.

The reconciler compiles the active endpoint graph into immutable in-memory route snapshots. Gateway
requests acquire a snapshot generation and never query PostgreSQL. Candidate plans do not receive
application traffic unless explicitly promoted. Streaming requests stay pinned to the acquired
generation until completion. Promotion changes future acquisitions only.

Existing deployments are transactionally backfilled into a `production` environment with an endpoint
of the same name and a one-binding active plan. This preserves request aliases while making the new
identity explicit.

## Consequences

- Applications can retain one stable model name while serving implementations change.
- Release Guard and telemetry can compare serving plans, including plans backed by different concrete
  deployments.
- Endpoint reconciliation becomes responsible for validating references and publishing complete route
  generations atomically.
- A deployment may exist without application traffic; deletion must reject or detach live bindings.
- `production` is an explicit compatibility default for migrated v1 resources, not an inference about
  a user's wider environment taxonomy.

## Alternatives

- Extending `Deployment` with provider alternatives keeps identity and lifecycle coupled and was rejected.
- Making LiteLLM configuration the domain model makes a replaceable gateway dependency authoritative
  and was rejected.
- Resolving bindings from PostgreSQL per request violates the established data-path invariant and was
  rejected.

## Verification

Migration, tenant-isolation, immutable-plan, route-generation, long-stream promotion, telemetry,
Release Guard, API/CLI and Docker integration tests are required by
[the v1.1 milestone](/roadmap/v1.1.0).
