# ADR 0041: Open-core and hosted compute boundary

Status: accepted.

## Context

InferCrane's product direction includes both customer-owned capacity and a future
InferCrane-supplied compute option. Implementing supplier accounts, balances, payment processing,
abuse controls, warm pools, or proprietary tenancy inside the public control plane would couple a
portable infrastructure product to one commercial operation. Publishing a `compute: infercrane`
configuration before a real supplier path is qualified would also create a non-functional product
promise.

The Community product must remain useful on its own. A hosted service may operate it and accept
commercial responsibility, but the public lifecycle, evidence, and release semantics cannot depend
on private packages.

## Decision

- Keep the complete self-operated control plane, gateway, CLI, SDKs, provider/runtime contracts,
  monitoring, durable operations, and release-safety loop in the Apache-2.0 repository.
- Keep hosted tenancy, supplier credentials, customer balances, payments, abuse prevention, rate
  cards, warm-pool operation, support, and contractual enterprise automation outside the public
  control-plane process.
- Require hosted services to consume public InferCrane APIs or narrow versioned extension
  contracts. The public core must never import a proprietary package.
- Preserve one product model across customer cloud, existing inference, and future InferCrane
  Compute. Endpoint, deployment, revision, operation, and evidence identities do not change with the
  compute source.
- Do not add an InferCrane Compute enum, CLI flag, dashboard control, price, or availability claim
  until at least one supplier path has passed lifecycle, isolation, metering, hard-budget, cleanup,
  and incident-recovery qualification.
- Start any future private beta with one supplier, prepaid or hard-capped spend, explicit regional
  availability, no physical GPU ownership, and deny-by-default access.
- Keep BYOC and self-hosted operation first-class even after hosted compute exists.

## Consequences

Users can adopt the open-source product without trusting a future cloud business. InferCrane can
later offer a model-to-endpoint experience using supplied capacity without rewriting application
identities or release workflows. Commercial operation can evolve quickly, while a billing or
supplier dependency cannot compromise the portable core.

The repository intentionally does not contain a pretend managed-compute implementation. Building
the private service remains demand- and qualification-gated work.

## Verification

- Product documentation labels hosted control plane and InferCrane Compute as direction rather
  than current availability.
- Public capability and qualification matrices contain only implemented adapters and measured
  evidence.
- Core packages have no dependency on payment processors, hosted identity vendors, supplier master
  accounts, or private warm-pool services.
- Public site and console tests reject unsupported availability claims and fixture-only production
  paths.
