# Kubernetes

The Kubernetes provider maps one durable replica intent to either a `Deployment` plus `Service`, or
one standard KServe `InferenceService`. Kubernetes owns scheduling and Pods. InferCrane owns revision
lifecycle, rollout policy, routing membership, evidence, and deletion of its exact labeled resources.

<Warning>
One real-cluster tuple is qualified, on 27 Nov 2026: Amazon EKS 1.36 in `us-east-1`, one
`g5.xlarge` (NVIDIA A10G 24 GB, EKS AL2023 NVIDIA AMI, driver 580.178.04), the VPC CNI with
`enableNetworkPolicy`, NVIDIA's device plugin 0.20.2 with GPU feature discovery, the control plane in
the cluster, and vLLM 0.34.0
(`vllm/vllm-openai@sha256:20fdb089454afbb324efa4110a2c025ff7b27cc1a086e07aa580b18df8ad1ce1`)
serving `Qwen/Qwen3-8B` on the whole GPU and `Qwen/Qwen3-0.6B` on the GPU time-sliced four ways.
Install, deploy, the gateway, the agent with its executor, a migration with a 5% canary and
rollback, and uninstall passed there, with the deviations and limits the
[record](/testing/aws-real-evidence#eks-customer-install-on-one-a10g-27-nov-2026) lists. Every other
GPU (the L4 included), cloud, Kubernetes distribution, runtime, and model has hermetic and Kind
qualification only. Registration is not a real-cluster support claim.
</Warning>

## Choose the workload API

| Mode | InferCrane creates | Use when |
|---|---|---|
| `deployment` | one `apps/v1 Deployment` and one `v1 Service` | You want the narrowest dependency set |
| `kserve` | one standard `serving.kserve.io/v1beta1 InferenceService` | KServe Standard mode is already installed and operated by your platform team |
| Dynamo adapter | one `nvidia.com/v1beta1 DynamoGraphDeployment` | You deliberately need aggregated/disaggregated worker topology; see [Dynamo](/integrations/dynamo) |

InferCrane does not create child Pods directly. It does not install KServe, Gateway API, a GPU device
plugin, model storage, or a Kubernetes distribution.

## Bootstrap a namespace

Review the manifests before applying them:

```bash
kubectl apply -f deploy/kubernetes/base/namespace.yaml
kubectl apply -f deploy/kubernetes/base/service-accounts.yaml
kubectl apply -f deploy/kubernetes/base/provider-rbac.yaml
```

The included Role is namespace-scoped and contains no wildcard, Secret, Pod, cluster-wide, or RBAC
mutation permission. It manages one `NetworkPolicy` per engine replica (see
[who can reach engine pods](#who-can-reach-engine-pods)). It has read-only `get`/`list` access to PVC metadata for cache verification. If the control plane runs outside the cluster, bind the same Role to the user or
identity in its kubeconfig instead of the included service account subject.

Create the worker credential without putting it in Git or shell history. On Kubernetes its value is
the control plane's `INFERCRANE_API_KEY`, byte for byte, with no trailing newline: the engines
compare it exactly.

```bash
(umask 077 && mkdir -p "$HOME/.config/infercrane" && printf '%s' "$INFERCRANE_API_KEY" >"$HOME/.config/infercrane/worker-key")
kubectl --namespace infercrane-system create secret generic infercrane-worker \
  --from-file=api-key="$HOME/.config/infercrane/worker-key"
```

## Configure the control plane

```bash
export INFERCRANE_KUBERNETES_CONTEXT='production-cluster'
export INFERCRANE_KUBERNETES_NAMESPACE='infercrane-system'
export INFERCRANE_KUBERNETES_WORKLOAD_API='deployment'
export INFERCRANE_KUBERNETES_SERVICE_ACCOUNT='infercrane-runtime'
export INFERCRANE_KUBERNETES_WORKER_SECRET_NAME='infercrane-worker'
export INFERCRANE_KUBERNETES_WORKER_SECRET_KEY='api-key'
export INFERCRANE_KUBERNETES_IMAGE_DIGEST='vllm/vllm-openai@sha256:REPLACE_WITH_QUALIFIED_DIGEST'
export INFERCRANE_KUBERNETES_GPU_RESOURCE='nvidia.com/gpu'
export INFERCRANE_KUBERNETES_GPU_PRODUCT_LABEL='nvidia.com/gpu.product'
export INFERCRANE_KUBERNETES_IMAGE_CACHE_POLICY='prefer'
export INFERCRANE_KUBERNETES_ARTIFACT_CACHE_POLICY='prefer'
export INFERCRANE_KUBERNETES_ENGINE_INGRESS='pods:app.kubernetes.io/name=infercrane'
```

Configuration is all-or-nothing. The image must be immutable. The adapter always passes an explicit
context and namespace to `kubectl`; it never relies on or changes the current context.

### Keys for stored credentials

A self-hosted control plane stores some credentials itself, such as the key of a server you connect
with `infercrane connect --token-env`. It needs two keys for that, set as separate random values:

| Variable | What it is for |
|---|---|
| `INFERCRANE_CREDENTIAL_ENCRYPTION_KEY` | Encrypts the credentials the control plane stores: a connected server's key, compute connections, and notification destinations. Without it, `infercrane connect --manage-traffic --token-env` fails with "cannot store server credentials". |
| `INFERCRANE_WORKER_CREDENTIAL_KEY` | The master key from which the control plane derives each deployment's own worker credential where the provider supports one. The encryption key requires it. |

Each must be at least 32 bytes. The control plane does not start with either key shorter than that,
or with the encryption key set and the worker key missing. Generate them without a trailing newline:

```bash
export INFERCRANE_CREDENTIAL_ENCRYPTION_KEY="$(openssl rand -hex 32 | tr -d '\n')"
export INFERCRANE_WORKER_CREDENTIAL_KEY="$(openssl rand -hex 32 | tr -d '\n')"
```

If you keep them in files for a Kubernetes Secret, write each with `printf '%s'`, as for the worker
key above. Keep the encryption key stable: a credential stored under another key fails closed until
it is stored again.

### Who can reach engine pods

With the `deployment` workload API, `INFERCRANE_KUBERNETES_ENGINE_INGRESS` is required: it names the
only sources that may reach an engine pod. Name the pods that run the InferCrane control plane,
whose gateway and router send requests and health checks. Each replica then gets a `NetworkPolicy`
beside its Deployment and Service. The policy admits those sources on the engine port only; the
pod's other ports take no traffic. The control plane does not start without a value.

The value is a comma-separated list of up to 16 sources:

| Source | Example | Admits |
| --- | --- | --- |
| Address range | `10.8.0.0/16` | Traffic from that range, such as a control plane outside the cluster |
| `pods:` | `pods:app.kubernetes.io/name=infercrane` | Pods with these labels in the engine namespace |
| `namespace:` | `namespace:kubernetes.io/metadata.name=infercrane-gateway` | Every pod in namespaces with these labels |
| `namespace:…;pods:…` | `namespace:kubernetes.io/metadata.name=gateway;pods:app=router` | Pods with these labels in those namespaces |

Join several labels with `+`, as in `pods:app=infercrane+tier=gateway`. Use your control plane's
own pod labels; the example above is a placeholder. `none` applies no policy. Set it only when
another control already limits traffic to engine pods.

- The cluster's network plugin must enforce `NetworkPolicy` (Calico and Cilium do). Without one the
  policy is stored and has no effect, and `infercrane doctor` cannot tell.
- Kubernetes always allows traffic from the pod's own node, so kubelet probes keep working.
- A metrics scraper that reads engine pods directly, such as Prometheus, must be listed as a source.
- The included Role grants the NetworkPolicy permissions, and `infercrane doctor` checks them when
  sources are set.
- Candidate pods that the [agent](/architecture/agent#candidate-runs) starts get the same policy,
  from its `--engine-ingress` setting.
- KServe mode applies no policy, because KServe owns its pods.
- A replica created before the setting gets its policy the next time it is provisioned. Until then
  it stays ready without one.

### AMD Instinct GPUs

For a cluster with AMD's GPU device plugin and node labeller, set
`INFERCRANE_KUBERNETES_GPU_RESOURCE='amd.com/gpu'` and
`INFERCRANE_KUBERNETES_GPU_PRODUCT_LABEL='amd.com/gpu.product-name'`, and use the node's label value
(for example `AMD_Instinct_MI300X_OAM`) as the spec's GPU. vLLM and SGLang replicas then start their
pinned ROCm images. A GPU whose device plugin does not match the configured resource is refused before
anything is applied. See [AMD Instinct GPUs](/integrations/amd-instinct).

## Pre-pull the immutable runtime image

The default image policy is `prefer`, which renders `imagePullPolicy: IfNotPresent`. For a
latency-critical pool, first use an operator-owned DaemonSet to pull the exact digest onto every
eligible GPU node. A minimal container template is:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: infercrane-runtime-prepull
  namespace: infercrane-system
spec:
  selector:
    matchLabels: {app: infercrane-runtime-prepull}
  template:
    metadata:
      labels: {app: infercrane-runtime-prepull}
    spec:
      nodeSelector:
        nvidia.com/gpu.product: NVIDIA-L40S
      tolerations:
        - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
      containers:
        - name: retain-image
          image: vllm/vllm-openai@sha256:REPLACE_WITH_QUALIFIED_DIGEST
          imagePullPolicy: IfNotPresent
          command: ["/bin/sh", "-c", "trap : TERM INT; sleep infinity & wait"]
```

Wait until the DaemonSet is ready on the complete intended node pool, then set
`INFERCRANE_KUBERNETES_IMAGE_CACHE_POLICY=required`. InferCrane renders `imagePullPolicy: Never` in
that mode, so a missing prewarm fails immediately with `ErrImageNeverPull` instead of silently
turning deploy into a registry transfer. InferCrane does not create this cluster-wide DaemonSet or
change node taints; those remain explicit operator actions. Digest changes require rolling the
pre-pull DaemonSet before deploying the new workload revision.

## Reuse an immutable model cache

For clusters with a shared filesystem or CSI driver that supports multi-reader claims, an
administrator can prepare one PVC containing the Hugging Face cache tree. InferCrane adopts the
claim; it does not create storage or download model bytes through the control API.

The claim must be `Bound`, support `ReadOnlyMany` or `ReadWriteMany`, and carry the exact model
identity digest:

```bash
MODEL_IDENTITY='Qwen/Qwen3-8B@0123456789abcdef0123456789abcdef01234567'
MODEL_DIGEST="sha256:$(printf %s "$MODEL_IDENTITY" | shasum -a 256 | awk '{print $1}')"

kubectl --context production-cluster --namespace infercrane-system annotate pvc/qwen3-cache \
  "infercrane.dev/model-identity-digest=$MODEL_DIGEST"

export INFERCRANE_KUBERNETES_ARTIFACT_CACHE_POLICY='required'
export INFERCRANE_KUBERNETES_ARTIFACT_PVCS_JSON="{\"$MODEL_IDENTITY\":\"qwen3-cache\"}"
```

At launch, the provider verifies the claim before server-side apply, mounts it at `/models`
read-only, and points the Hugging Face cache environment at `/models/huggingface`. A missing,
unbound, single-node-only, or wrongly annotated required claim fails before workload mutation.
`prefer` falls back to the runtime's ordinary immutable download only when no claim is mapped; a
configured but invalid claim never silently falls back.

Record the verified locality through the common artifact API:

```bash
infercrane artifact prefetch ARTIFACT_ID \
  --provider kubernetes \
  --region production-cluster \
  --location kubernetes-pvc://qwen3-cache \
  --idempotency-key qwen3-cache-v1
```

This is a shared-volume path, not a node-local cache or image-streaming claim. CSI performance,
mount propagation, model-read throughput, and real GPU startup remain cluster-specific evidence.

Validate the Kubernetes API, optional KServe CRD, and every required namespaced permission without
creating a workload:

```bash
infercrane doctor --kubernetes
```

## Private models, your own bucket, and LoRA adapters

A private Hugging Face token stays in a Secret in this namespace. Name it with a `kubernetes`
reference and pass its ID as `model_secret_reference_id`; the runtime gets `HF_TOKEN` through a
`secretKeyRef`, and the control plane needs no Secret permissions:

```bash
kubectl --context "$INFERCRANE_KUBERNETES_CONTEXT" -n infercrane-system create secret generic hf-token --from-literal=HF_TOKEN="$HF_TOKEN"
infercrane secret create hf-token --kubernetes hf-token/HF_TOKEN
```

Weights or adapters imported from S3 or GCS (`infercrane models import`) are fetched by an init
container into the Pod's own volume, and every file's sha256 is checked before the server starts.
The fetch uses the runtime service account's workload identity (IRSA or GKE Workload Identity), or
the keys of an optional Secret you name. For an S3-compatible store such as MinIO, put
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_ENDPOINT_URL` in that Secret:

```bash
export INFERCRANE_KUBERNETES_OBJECT_STORE_SECRET='model-bucket-reader'   # optional
export INFERCRANE_KUBERNETES_S3_FETCH_IMAGE='amazon/aws-cli@sha256:...'  # optional, pinned by digest
export INFERCRANE_KUBERNETES_GCS_FETCH_IMAGE='gcr.io/google.com/cloudsdktool/google-cloud-cli@sha256:...'  # optional
```

By default the fetch images are the pinned AWS CLI 2.31.38 and Google Cloud CLI 548.0.0 slim
images; mirror them into a private registry for offline clusters. The serving container never
receives the object store keys. LoRA adapters are rendered for `vllm` and `sglang`. See
[model artifacts](/features/model-artifacts).

## Deploy

The GPU value maps to the configured product-label value. It is never silently substituted.

```bash
infercrane plan Qwen/Qwen3-8B \
  --name qwen-kubernetes \
  --cloud kubernetes \
  --gpu NVIDIA-L40S

infercrane deploy Qwen/Qwen3-8B \
  --name qwen-kubernetes \
  --cloud kubernetes \
  --gpu NVIDIA-L40S \
  --idempotency-key qwen-kubernetes-initial
```

On a 24 GB GPU (L4, A10G), `Qwen/Qwen3-8B`'s own 40960-token context does not fit next to its
weights: vLLM 0.34.0 needs 5.62 GiB of KV cache for it, has 3.72 GiB free, and exits. When the
control plane can read model metadata (`INFERCRANE_HUGGING_FACE_METADATA_ENABLED=true`), InferCrane
sees this before it deploys and sets `--max-model-len 8192`. The deploy output names the length and
why. Without metadata access, or to choose another length, pass it yourself:

```bash
infercrane deploy Qwen/Qwen3-8B \
  --name qwen-kubernetes \
  --cloud kubernetes \
  --gpu NVIDIA-A10G \
  --max-model-len 8192 \
  --idempotency-key qwen-kubernetes-initial
```

A [DeploymentSpec](/deployment-spec) sets the same bound with `runtime.args: ["--max-model-len",
"8192"]`.

A deploy that never becomes ready keeps its operation open, and `infercrane delete` is refused
("unresolved lifecycle operation") until you cancel it:

```bash
infercrane operation list
infercrane operation cancel OPERATION_ID
```

Provisioning uses strict server-side dry-run followed by server-side apply with the
`infercrane-provider-v1` field manager. InferCrane does not use `--force-conflicts`; ownership drift
fails visibly. A lost apply response is safe to retry because resource names and ownership metadata
derive from the durable replica key.

## KServe Standard mode

Install and operate a compatible KServe release separately, apply
`deploy/kubernetes/kserve/provider-rbac.yaml`, then set:

```bash
export INFERCRANE_KUBERNETES_WORKLOAD_API='kserve'
```

The provider verifies the `InferenceService` API and required permissions during `doctor`. KServe
owns generated Deployments, Services, and Pods; InferCrane inventories and deletes only the parent
InferenceService. Raw KServe condition metadata remains available through `infercrane inspect`.

KServe `LLMInferenceService` and llm-d remain separate integration boundaries. Dynamo uses a
distinct `kubernetes-dynamo` adapter with one explicit mutation owner; it is never enabled
implicitly by `workload_api`.

## Expose the logical endpoint

`deploy/kubernetes/gateway-api/httproute.yaml` is an optional placeholder. Replace the Gateway and
hostname, then apply it only if your cluster already has Gateway API and a controller. It routes to
the InferCrane gateway, not directly to revisions or workers - so safe rollout ownership stays singular.

## Migrate an endpoint you connect

`infercrane connect URL --as NAME --manage-traffic --token-env VAR` stores the server's key
encrypted, so a control plane you run needs the two keys in
[Keys for stored credentials](#keys-for-stored-credentials). Without them `connect` answers "cannot
store server credentials". On Kubernetes the engines keep receiving the control plane's API key.

The planner's catalog qualifies Kubernetes with vLLM 0.34.0 on a real cluster for one GPU, the
NVIDIA A10G (`--gpu NVIDIA-A10G`), and proposes setups for it directly. For every other GPU, a
time-sliced label such as `NVIDIA-A10G-SHARED`, or another engine version, the pair is marked
simulated, and `infercrane optimize propose --provider kubernetes` proposes no setup unless you add
`--include-simulated`; the proof still measures every setup it runs.

A `kubernetes-dynamo` setup runs only where NVIDIA Dynamo runs, so InferCrane proposes one only when
it knows Dynamo is there:

- you name the adapter: `--provider kubernetes-dynamo`; or
- the control plane that plans has a Dynamo image and version pair set for that runtime (see
  [NVIDIA Dynamo](/integrations/dynamo#optimization-setups)).

Otherwise `--provider kubernetes` proposes plain Kubernetes setups only, and the proposal's warnings
say which Dynamo setups were left out. See [Migration](/features/migration) for the commands.

## Known limits

- Deploy, the gateway, and optimization runs need the control plane inside the cluster: a replica's
  address is its Service's cluster DNS name. A hosted control plane reaches your cluster through the
  [agent](/architecture/agent) only.
- The only 5% canary is the migration canary (`infercrane migrate canary`); an optimization winner
  is activated, not canaried.
- InferCrane never sets vLLM's `--gpu-memory-utilization`, and vLLM 0.34.0 then takes the whole GPU.
  To share one GPU between servers (time-slicing), give each server its own limit.
- A time-sliced GPU's label (for example `NVIDIA-A10G-SHARED`) matches none of the planner's reviewed
  profiles, so it gets generic setups only.
- There is no Helm chart for the control plane yet.
- The engines' `NetworkPolicy` does nothing without a network plugin that enforces it.

A server the agent found but did not register failed its health probe. The agent pod's log says
why in one `unhealthy` line; see [Troubleshooting](/troubleshooting).
