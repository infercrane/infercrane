# Claims with receipts

InferCrane binds every benchmark to an exact model, runtime, accelerator, workload, and date. A
measured win is not generalized to another provider, GPU, context length, concurrency level, or
production network path.

## Qwen3.8-27B on one H200: September screen, superseded

| Field | Value |
| --- | --- |
| Date | 2026-09-23 |
| Model | `Qwen/Qwen3.8-27B-FP8@017b9c7af6b5689d5dd426a76e0bc077eb5ca20a` |
| Runtime | SGLang 0.5.20 |
| Accelerator | 1× NVIDIA H200 |
| Workload | 4,096 input tokens, 512 output tokens, concurrency 12 |
| Selected recipe | FP8 weights and KV cache, bounded CUDA graphs, native NEXTN/MTP |

This one-run screen measured 1.72× output throughput at concurrency 12 from turning on native
multi-token prediction (with bounded CUDA graphs), the speculation option the model's publisher
documents. Its prompts were synthetic: one sentence repeated to the target length. Repeated text is
unusually easy for speculation to predict.

On 2026-11-23 the same pair was run again on real text (OpenAssistant and CNN/DailyMail prompts)
with three fresh servers per setup. At 12 requests at once the same change gave +12% on short
prompts and +33% on 3,900-token prompts; across the six load and prompt-length cells it ranged from
−22% to +68%. The publisher's documented setup on vLLM 0.34.0 was faster than the recipe selected
here in every cell, by 5% to 113%. The screen's throughput and latency changes are therefore not
cited. Read the [re-run's receipt](/testing/qwen38-27b-fp8-h200-rerun-2026-11-23).

September's receipts stay as a dated record:

- [Inspect the machine-readable receipt](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen38-public-decode-saturation-modal-2026-09-23T044530Z.json)
- [Inspect raw measurements](https://github.com/infercrane/infercrane/blob/main/docs/testing/evidence/qwen38-public-decode-saturation-modal-2026-09-23T044530Z-raw.json)

<Warning>
  A change InferCrane reports now is measured on your traffic against your current setup, confirmed
  again on fresh servers, and, when it changes answers, checked on a scored task set. Read
  [optimization](/features/optimization) and [semantic quality](/features/semantic-quality).
</Warning>

## Rejections are part of the result

The campaign preserved candidates that sounded attractive but lost under the target workload:

- FlashInfer GDN paths preserved correctness but regressed throughput and cold readiness.
- DFlash2 won some lower-concurrency screening lanes but did not replace native MTP at the selected
  saturation boundary.
- The near-262K context run completed correctly but missed its latency SLO.

## Qwen3.8-27B on H100: a speculation setting confirmed on fresh servers

| Field | Value |
| --- | --- |
| Date | 2026-11-23 |
| Model | `Qwen/Qwen3.8-27B-FP8@c3a462cc3d38cf351f3b26cbd763469eeb74ef81` |
| Runtime | vLLM 0.34.0 |
| Accelerator | 1× NVIDIA H100 SXM5 80GB per setup |
| Workload | The first 100 rows of the Mooncake trace, scaled to short chat, real text, 32 requests at once, reasoning on |
| Confirmed | The publisher's documented speculation option: multi-token prediction, 3 draft tokens |

InferCrane's campaign judge measured the speculation option against the publisher's plain vLLM
command at +32.1% output tokens per second in its first window and +33.1% on two fresh H100s; a copy
of the current setup came out −0.1% and was rejected as no measurable difference. Each setup had its
own H100, taking turns with the current setup's. On the fresh servers p95 time to first token
regressed by 31.4%. The answer check was a word-overlap guard on 24 short prompts, not a quality
score. Read the [campaign's receipt](/testing/qwen38-27b-fp8-h100-campaign-2026-11-23).

## Qwen3-8B on one L4: FP8 refused on answers

| Field | Value |
| --- | --- |
| Date | 2026-11-26 |
| Model | `Qwen/Qwen3-8B@b968826d9c46dd6066d109eabc6255188de91218` |
| Runtime | vLLM 0.34.0 |
| Accelerator | 1× NVIDIA L4 per server, three fresh servers per setup |
| Workload | Short chat at 16 and 64, long context at 4 and 16, long output at 16; a 1,000-item task set (GSM8K and MMLU) |
| Candidates | FP8 weights, and FP8 weights with an FP8 KV cache, both quantized at load |

FP8 weights with an FP8 KV cache served 62.1% to 158.7% more output tokens per second than vLLM's
defaults in every cell, and scored 1.10 points lower on the task set (interval −2.20 to −0.002);
FP8 weights alone were 48.2% to 110.8% faster and 1.37 points lower. The run's rules, committed
before any server, confirm a setup nowhere if it is worse on the task set, so neither was confirmed.
Read the [run's receipt](/testing/qwen3-8b-fp8-l4-confirmation-2026-11-26).

A second run checked two published FP8 checkpoints of the same model on answers only, three fresh
L4s per setup. An FP8 checkpoint that also quantizes the KV cache scored 1.33 points lower than the
original (interval −2.57 to −0.10). The model publisher's FP8 checkpoint scored the same, 85.77%
against 85.77% (interval −1.03 to +1.03), which InferCrane's 1-point rule reads as not shown to hold
within 1 point. Read the [checkpoints' receipt](/testing/qwen3-8b-fp8-checkpoints-l4-2026-11-26).

## Reading the evidence

InferCrane distinguishes modeled proposals, screening measurements, qualification evidence, and
public repeated evidence. Only comparable measurements can be ranked. Missing identity, quality,
cost, or workload evidence produces `WAIT` or `REJECT`; it is never converted into a release win.

Read [benchmarking](/features/benchmarking), [optimization](/features/optimization), and
[compatibility and qualification](/compatibility) for the evidence rules.
