# Rules for the EKS agent proof

Written and committed on 2026-11-23, before any cluster exists. The commit that holds this file
is named in the evidence. A change to these rules after the first cluster is created is a
deviation and is reported as one.

## What this run is

One proof that the InferCrane agent works on a real Kubernetes cluster in a customer's cloud:
Amazon EKS in `eu-central-1`, one NVIDIA A10G node, a real model on a real engine. It proves a
path. It measures no speed.

Until this run the agent's Kubernetes path has only run on a laptop cluster with a stand-in
engine and no GPU (`scripts/test-agent-data-plane-kind.sh`).

## What counts as passed

Each line is one criterion. The test has passed when all six pass on one cluster, with the
product code unchanged while that cluster lives.

1. **Install.** The agent's Helm chart installs in the customer's namespace with its namespaced
   Role only, and the agent's pod becomes ready.
2. **Discovery.** The agent registers the customer's model server as an endpoint, and the control
   plane shows its engine, model and health.
3. **Data plane.** After the endpoint is made agent-managed, the agent serves seven chat requests
   to the real model inside the cluster with an InferCrane API key (three streamed), refuses an
   unknown key with HTTP 401, and the control plane's own gateway refuses the endpoint with HTTP
   403.
4. **Candidate run.** One candidate run queued through the control plane ends `succeeded`: the
   agent starts the candidate in the customer's namespace, and each of the three load passes
   (current setup, candidate, current setup again) finishes with no failed request.
5. **Answer check and removal.** The answer check runs on both servers and returns a verdict, the
   result says the candidate was cleaned up, and no candidate Deployment or Service is left.
6. **Teardown.** `90-delete.sh` ends with "nothing billable of this test is left".

The answer check's verdict is reported as it comes. `PASS` is expected, because both servers load
the same weights. `WATCH` or `BLOCK` does not fail criterion 5, but it is a finding and is
reported with the scores.

## What will be reported

- Each criterion, passed or failed, with the check lines behind it (`run/checks.tsv`).
- Every failure, retry and deviation, in order, with its cause when known. A run that fails is
  written up like one that passes.
- The cluster as it was: Kubernetes and AMI versions, the GPU as the driver reports it, node
  labels, images by digest, the IAM roles and stacks that were created.
- Times: cluster creation, model server start, each phase of the candidate run, deletion.
- The candidate run's numbers as the product recorded them, always next to this sentence: two
  servers shared one small GPU, so the numbers are not comparable and not a speed result.
- What the agent reported about hardware. The agent's pod has no GPU, so "unavailable" is the
  expected value; whatever it reports is stated.
- Cost: hours times list price on the day, and the billed amount from AWS when it is available.

## What will not be claimed

- No speed, throughput, latency or cost-per-token claim, for AWS, for the A10G or for the model.
- No claim that the candidate is better or worse than the current setup. They shared a GPU.
- No claim about other clouds or Kubernetes services (AKS, GKE, on-premises), other GPU types,
  multi-GPU servers, EKS Auto Mode, Bottlerocket, private clusters, or clusters that taint their
  GPU nodes. One later check per platform is needed before any of those is stated.
- No claim that nothing but numbers left the cluster. The control plane ran inside the same
  cluster here and the wire capture of the kind proof was not repeated.
- No claim about the hosted control plane or production.
- No reliability or availability claim. This is one run.
- "Unknown" stays unknown. A value that was not read is not estimated.

## Deviations allowed, each reported when used

- **Zone.** If AWS has no `g5.xlarge` capacity in zone `a`, the GPU node group moves to zone `b`.
- **GPU type.** If AWS has no `g5.xlarge` capacity in either zone, the GPU node is `g6.xlarge`
  (NVIDIA L4, 24 GB), with nothing else changed.
- **Model.** If either server cannot start for lack of GPU memory, the run is repeated once with
  `Qwen/Qwen3-1.7B` at revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`. Both attempts are
  reported.
- **Retries.** A phase may be run again after a failure that is not the product's (image pull,
  network, a timeout). The candidate run is queued at most three times. Every attempt is reported.

Anything else that differs from this file is reported as an unplanned deviation, with its reason,
before the result is called passed.

## Stop rules

- No phase starts if it could run into the last 25 minutes of the cluster's 4 hours.
- At the deadline AWS scales both node groups to zero, whether or not anyone is watching.
- A defect that needs a code change ends the cluster: delete, fix on the branch with a test,
  build a new image, and start a new cluster only if the budget still pays for 1.5 hours.
- The test never passes $15 at list prices, counted from the first second of every cluster.

## Amendment, 23 Nov 2026, 15:40 CET, before the second cluster

The first cluster (14:46 to 15:37 CET) never had a node. AWS had no capacity in zone `a` for
`g5.xlarge` and none for `m7g.large` during the 33 minutes EKS kept asking. Nothing of the
product ran on it, so no criterion above was tested, passed or failed. It is reported as the
first attempt, with its cost.

Changed for the second cluster, and written here before it starts:

- **Zone.** Both node groups may start their node in zone `b` or zone `c`, the two zones AWS's
  refusal named. The rule above foresaw only the GPU group moving to `b`; the system node was
  refused too, and two zones leave AWS a second place to try. The load test and the model
  servers may therefore run in different zones. No criterion depends on the zone.
- **GPU type.** Unchanged in meaning: if AWS has no `g5.xlarge` in `b` or `c`, the next cluster
  uses `g6.xlarge`.

Nothing else in this file changes.

## Second amendment, 23 Nov 2026, 18:50 CET, before the third cluster

The second cluster (17:31 CET) got its system node in zone `b` within a minute and no GPU node:
AWS refused `g5.xlarge` in zone `b` and in zone `c`, 19 requests in 32 minutes. With zone `a` at
15:00, Frankfurt had no `g5.xlarge` for this account in any zone that afternoon. Again nothing
of the product ran, so no criterion was tested. It is reported as the second attempt, with its
cost. Its deletion was cut off at 18:28 when the AWS sign-in ended; it was finished and checked
after the next sign-in, and that is reported too.

Changed for the third cluster, and written here before it starts:

- **GPU type.** The case the rule above names has happened, so `g6.xlarge` (NVIDIA L4, 24 GB)
  is allowed. The GPU node group lists `g5.xlarge` first, `g6.xlarge` second and `g6e.xlarge`
  third, and AWS starts the first it has in the zone it tries. It can therefore start an L4 in
  one zone while an A10G would have been free in another; the rule's "in either zone" is not
  checked zone by zone. The evidence names the type and the zone that actually ran. Nothing
  else changes on another GPU: the same model, the same 45% of GPU memory for each of the two
  servers, the same checks.
- **A type the rules did not foresee.** `g6e.xlarge` (NVIDIA L40S, 48 GB, $2.327 an hour) is
  the third choice, for a day on which Frankfurt has neither of the others. It is a new
  deviation, allowed here because no criterion depends on the GPU's type and this proof makes
  no speed claim for any of them. The time limit and the $15 count every hour at this dearest
  price whichever type runs, so one cluster can count up to $10.50. A run that goes to plan
  (1.5 hours) is about $2.22 at list price on an A10G, $1.84 on an L4 and $3.82 on an L40S.
- **Zone.** Both node groups may use zones `a`, `b` and `c`.

Still not claimed, for either GPU: any speed, throughput, latency or cost result.
