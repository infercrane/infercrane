# Rules for the real-cluster qualification of the customer install

Written and committed on 2026-11-26, before any cluster of this run exists. The commit that
holds this file is named in the evidence. A change after the first cluster is created is a
deviation and is reported as one. Changed twice before any cluster existed, both on 26 Nov:
`us-east-1` was added as a second region after Frankfurt had no L4 for this account all
afternoon; then `g5.xlarge` (NVIDIA A10G) was added as a fallback GPU after both regions refused
the L4 in every zone (Frankfurt 13:28-18:59, us-east-1 19:14-19:36) and us-east-1 also refused the
A10G at 19:47. The tuple is otherwise the same. The first run of this tool (23-24 Nov, three clusters, no GPU
node) followed `rules-2026-11-23.md`; this file replaces it for this run.

## What this run is

One end-to-end qualification of what a design partner does on their own GPU Kubernetes cluster:
install, connect, deploy, serve, optimize, canary and roll back, uninstall. It proves a path on one
real GPU. It measures no speed.

## Deviations from a customer's own install, decided now

1. **The control plane runs in the customer's cluster**, not hosted. A Kubernetes replica's address is
   its Service DNS name, so deploy, gateway and campaigns need a control plane inside the cluster.
   A customer of the hosted control plane gets the agent path (steps 1, 2 and the agent checks).
2. **Every server on the shared L4 gets `--gpu-memory-utilization 0.22 --max-model-len 4096`**,
   added to each campaign setup's arguments in the proposal before it is posted (what
   `tools/poc-local/poc.py` does). The product never sets the memory limit, and vLLM 0.34.0 takes
   the whole GPU when it is unset. A customer with one GPU per server does not need this.
3. **One GPU is time-sliced four ways** (the account's quota is one 4-vCPU GPU node). The product
   label then reads `NVIDIA-L4-SHARED`, and the campaign's servers and the customer's share it, so
   no measurement is comparable.
4. **Prices are test values**: the rate card is AWS's list price of the whole g6.xlarge for each
   server; the connected endpoint's contract price is $1.00 / $8.00 per million input / output
   tokens. They exist so a campaign can be approved and a setup can win on cost. No claim uses them.
5. **Two models**: Qwen3-8B where the GPU is whole, Qwen3-0.6B where it is shared (four servers of
   Qwen3-8B do not fit 24 GB).

## Deviations decided during the run (27 Nov, A10G)

Recorded here as they happened, each with its reason; the run record lists them in order.

6. **The eval set grades the answer line, not the exact words.** With `exact_match`, Qwen3-0.6B's
   answers ("32 + 30 = 62.") scored 0 of 40 on both sides, the setup and the connected source, and
   the verdict was UNKNOWN (`quality_bootstrap_insufficient`). `eval/graded-arithmetic.json` v2
   grades `answer_line` (the number after "Answer:", else the last number), as the product's
   `qualitycheck` defines it. Same 40 prompts and expected answers.

## What counts as passed

Each line is one criterion, recorded in `run/checks.tsv`. The qualification passes when every
line passes on one cluster with the product code unchanged while that cluster lives. A line that
cannot be reached because an earlier one failed is "not reached", not passed.

1. **Operator install.** Device plugin and GPU feature discovery label the node; the control plane
   starts with the bootstrap's Role only; `infercrane doctor --kubernetes` is recorded.
2. **Deploy.** The docs' `infercrane deploy` of Qwen3-8B becomes ready on the L4 with a Deployment,
   a Service and a NetworkPolicy.
3. **Policy enforced.** A pod labelled like the control plane gets HTTP 200 from the engine's
   `/health`; a pod with another label cannot connect.
4. **Gateway.** 20 of 20 chat requests answer 200 with a complete answer; an unknown key gets 401.
5. **Delete.** `infercrane delete` leaves no Deployment, Service, NetworkPolicy or pod.
6. **Agent install.** The Helm release with the executor becomes ready.
7. **Agent path.** The criteria of `rules-2026-11-23.md` 2 to 5: discovery, agent-managed data plane
   (7 requests, 401, hosted 403), one candidate run `succeeded` with three load passes without a
   failed request, the answer check's verdict, and no candidate left.
8. **Migration.** The source connects and serves 60 of 60 through the gateway; capture and eval
   set are accepted; the campaign reaches a decision and at least one PASS verdict.
9. **Fresh-server confirmation.** If a setup showed a gain, the record shows it re-measured on
   fresh servers. If no setup gained, this line is "not exercised" and the report says so; it is
   not counted as passed.
10. **Canary.** The 5% canary is admitted on the PASS verdict, and between 4 and 20 of 200 requests
    reach the deployment, all answered 200.
11. **Rollback.** After `migrate rollback`, 60 of 60 answer 200 and none reaches the deployment.
12. **Uninstall.** After deletes, `helm uninstall` and the bootstrap's removal, no object InferCrane
    made is left, namespaced or cluster-wide, except the agent's hashing-key Secret, which the
    chart keeps on purpose and the report names.
13. **Teardown.** `90-delete.sh` ends with "nothing billable of this test is left".

## What will be reported

Each criterion with its check lines; every failure, retry, fix and deviation in order; the
cluster as it was (Kubernetes, AMI, driver, CUDA, node labels, images by digest, add-on settings);
times of each phase; the campaign's record and verdicts as the product wrote them, next to the
sentence that the servers shared one GPU; cost at list price, and AWS's billed amount when known.

## What will not be claimed

A run on the A10G says nothing about the L4, and the reverse; the support statement names the GPU
that ran. Both have 24 GB, the vLLM 0.34.0 image is built for both (`TORCH_CUDA_ARCH_LIST` 8.6
and 8.9), and nothing in this run uses FP8 (the models are BF16; the planner's FP8 mechanisms are
deferred and limited to H100, H200 and L40S).

No speed, throughput, latency, cost-per-token or quality claim of any kind. Nothing about other
clouds, Kubernetes services, GPU types, models or engines than the tuple above. A failure of
AWS capacity is not a failure of the product and is reported as capacity.
