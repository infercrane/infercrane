# Rules: kernels tuned for your shapes, Qwen3.6-35B-A3B-FP8 on one H100 (26 Nov 2026)

Written before any server of this run started. Nothing below changes after launch; a change
means a new rules file and a new run.

## Question

Does tuning vLLM 0.34.0's own fused-MoE kernel (tile settings only, delivered as the
engine's tuned-config file) for one H100 at the map's short-chat loads give more output per
second end to end than the same engine untuned, with answers as good?

Not asked: other models, GPUs, engines, loads, or speculation. A result here says nothing
about them.

## Why this model and this gap

- **Model.** `Qwen/Qwen3.6-35B-A3B-FP8` at revision `c653bba46dfa06e9658dcc0b0dc87fe4685f14a2`
  (Apache-2.0, 37.5 GB). It was the most-downloaded Qwen MoE checkpoint in FP8 on the Hugging
  Face models API on 26 Nov 2026 (2,698,916 downloads; a popularity signal only), and the
  vLLM recipe calls its FP8 variant "single-GPU serving". Its MoE: 256 experts, 8 per token,
  expert intermediate size 512, hidden size 2,048, FP8 weights in 128×128 blocks
  (`config.json` at that revision).
- **The gap.** vLLM 0.34.0 names a tuned file `E=256,N=512,device_name=<GPU>,dtype=fp8_w8a8,
  block_shape=[128,128].json`. It ships that file for the H200, B200, RTX PRO 6000, GB10 and
  MI325 OAM, not for the H100 (`git tree v0.34.0:vllm/model_executor/layers/fused_moe/configs`,
  read 26 Nov). Without it the engine uses its built-in default (`get_default_config`) and logs
  "Using default MoE config". On Hopper with block FP8 and no expert parallelism the FP8 MoE
  oracle puts the Triton kernel first (`oracle/fp8.py`), and `get_moe_configs` reads
  `VLLM_TUNED_CONFIG_FOLDER` before the shipped folder, per file (`fused_moe.py`).
- **The tuned file is data.** It holds tile settings for vLLM's own reviewed kernel, keyed by
  tokens per step; `internal/kerneltuning` accepts only canonical files of the six tile keys
  (and `SPLIT_K` 1), file names in the engine's form, and matching sha256 digests.

## Step 1: find the gap, then tune (first machine only)

1. One unmeasured start of the untuned engine. Its log must name the `TRITON` FP8 MoE backend
   and exactly one fused-MoE file it looked for and did not find on this GPU. Otherwise the
   machine stops before tuning: "nothing to tune" (another backend, a shipped file, or more
   than one shape).
2. `tune_moe.py` tunes that file's shape with the engine's own Python on this GPU:
   - Step sizes: the decode grid up to 128 tokens and the prefill grid up to 8,192 tokens (the
     engine's H100 step budget), loads `{128 running, 8,192 batched}` and `{32 running, 8,192}`;
     plus 5, 9, 17 and 65, which keep the engine's default exact for any step the nearest key
     serves (`kerneltuning.Keys`).
   - Per key: time the engine's own choice twice (start and end), search by coordinate descent
     from the engine's choice and the previous winner, two passes, 45 s per key, 540 s in all.
     Kernel alone, CUDA graph of 10 calls, each call reading the next of 4 weight copies (so no
     call finds its experts in the 50 MB L2 cache), 30 replays, median, uniform random routing
     as vLLM's tuner uses.
   - Keep a setting only when it is at least 3% faster than the engine's choice **and** faster
     by more than twice that key's own spread, it has no NaN or Inf, its error against an FP32
     reference is at most 1.25× the engine's own error (+0.001), and neither time is below 90%
     of the memory floor (each touched expert's FP8 weights read once at 3.35 TB/s). Otherwise
     the key holds the engine's own default.
   - Then the file as the engine reads it (nearest key) against the engine's choice at the
     midpoint of every gap between keys ("hidden" sizes); a hidden size more than 3% slower
     gets a key holding the engine's default.
3. If no key kept a tuned setting, the machine stops: "nothing to measure". No window runs.

Kernel-level times choose what to measure. They are never reported as a serving gain.

## Step 2: the window (each machine)

- Nine engine starts on the one GPU, in order: control, candidate, control, candidate,
  control, candidate, control, candidate, control (the campaign's four bracketed runs).
- Each start, after the engine answers one 4-token request, measures two cells in order:
  - `short/128`: 128 requests at once from prompt set v2 `kinds.short.levels.128` (5,000
    OpenAssistant first turns, `prompts-v2.json` sha256 `2f6b0563…fac984`);
  - `short/32`: 32 at once from prompt set v1 `shapes.short.levels.32` (3,000 prompts,
    `prompts-v1.json` sha256 `c3c912df…d84c989`).
  Each: one user message, temperature 0, reasoning off, at most 295 tokens, streamed; warm-up
  15 s, window 45 s, the same load kept until every request sent in the window ends (at most
  20 s). Output tokens per second counts tokens that arrived inside the window. The prompts are
  the map's, in the same order in every start.
- First machine only: after the cells of starts 1, 2 and 3 (control-1, candidate-1,
  control-2), the 1,000-item task set `quality-v1.json` (500 GSM8K + 500 MMLU, MIT; sha256
  `83c3df7b…72e4`), 64 at once, each item's own limit of 1,024 tokens.
- **Invocation proof, every start:** a candidate's engine log names the tuned file as read
  from `/opt/infercrane/kernel-configs` and reports no default for it; a control's reports the
  default for it and reads no tuned file; the backend is `TRITON`. A start that fails this
  ends the window (recorded, not retried).
- A start with any failed request ends the window. A start that would not fit before the
  machine's cap is not begun.

## Judging (the campaign judge's code)

`infercrane optimize evidence kernel-tuning --file window-first.json --fresh window-fresh.json --set kernel-configs.json`:

- Per cell and window: valid only when every start served what its arm says (above), every
  run is clean, and adjacent control runs differ by at most 15%. The comparison is
  `comparePaired`: each candidate run over the mean of the control runs around it, mean log
  ratio, Student-t interval at confidence 1 − 0.05/2 (two cells judged), plus the campaign's
  0.75% machine allowance. Improved or regressed only when the whole interval is on one side.
- A cell is **confirmed** when it improved on the first machine and again on the fresh one.
  Improved first and not again is **not confirmed**; an invalid or missing fresh window leaves
  it **unknown**.
- Answers: candidate-1 against control-1 on the task set, item by item by answer line; the
  task-set rule (better or worse when the 95% interval excludes zero; no measurable
  difference when it lies within ±3 points; otherwise not settled). The share of identical
  answer texts, control-1/control-2 and control-1/candidate-1, is reported beside it.
- **Decision:** reject if any cell regressed in a valid window or the task set is worse;
  propose if at least one cell is confirmed and the task set shows no measurable difference
  (or better); unknown if a gain is confirmed but answers did not settle, or a cell could not
  be compared; otherwise no measurable gain. Slower p95 first token or time per token in a
  valid window is a warning beside the decision.

The fresh machine runs only when the first window shows a cell the judge calls improved and
nothing it rejects. It tunes nothing: it serves the first machine's set unchanged.

## What gets reported

- The decision and, per cell and window, the paired delta with its interval, the control
  drift, the invocation proof, GPU clock, power and use per cell, and every start's time.
- The tuner's per-key table: engine choice and best time, spread, kept or why not, the share
  of the memory floor each reaches, the reference check, and the hidden sizes.
- If the end-to-end gain is inside the noise, the result is "no measurable gain" and is
  reported as that, with the kernel-level gains beside it labelled kernel-level.
- Company-reported numbers from elsewhere (kernel steps on tuned stacks adding about 4% to
  20%) are context only. Claims compare against the stated baseline only.
